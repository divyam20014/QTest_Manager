## Real bugs found and fixed during this phase (all via actual execution, not inspection)
1. **RLS chicken-and-egg on session lookup**: resolving a session cookie requires reading `sessions` before the tenant is known, but RLS requires the tenant to be known first. Fixed by exempting `sessions`/`mfa_challenges` from RLS (ADR-015) — security for those two tables rests on the row id being an unguessable UUID, same trust model as a password-reset token.
2. **`SET LOCAL` doesn't accept bind parameters** — `set_tenant_context` was passing `:tenant_id` as a parameter to a `SET LOCAL` statement, which PostgreSQL rejects outright. Fixed using `set_config('app.current_tenant', :tenant_id, true)`, which does support parameters.
3. **Empty-string GUC after commit** — a transaction-local custom GUC placeholder reverts to `''` (not `NULL`) once its transaction commits, so the RLS policy's `::uuid` cast threw on the very next transaction. Fixed with `NULLIF(current_setting(...), '')::uuid` (migration `567fa7545de9`).
4. **`expire_on_commit=True` (SQLAlchemy default) broke every commit-then-respond route** — after a service's `db.commit()`, FastAPI building the response from the same ORM object triggered a refresh query in a new transaction with no tenant context, which RLS denied, surfacing as `ObjectDeletedError`. Fixed by setting `expire_on_commit=False` on `SessionLocal` — a systemic fix, not a one-off, since this pattern (commit once, then serialize) is used by every service in this codebase.
5. **Email-only login is architecturally impossible** under correct RLS, since `users.email` is only unique per tenant. Resolved via ADR-017: login requires an explicit `tenant_id` in the request.
6. **`UserOut.model_validate(user)` can't work** — the ORM `User` model has `role_id`, not a `role` code string, so direct validation from the ORM object always failed. Fixed with an explicit `user_service.to_out()` serializer that resolves the role code.

## Three real bugs found and fixed this phase (all via actual execution, not inspection)
1. **8x too slow (20s for 2,000 rows against a 2.5s budget)**: the first implementation called `db.flush()` three times per row (6,000 round-trips for 2,000 rows). Fixed by deferring all flushes to the end of the batch.
2. **That fix immediately hit a real circular-FK violation**: `test_cases.current_version_id` and `test_case_versions.test_case_id` are mutually dependent (ADR-003's `use_alter`), and SQLAlchemy does not resolve that automatically without `relationship(post_update=True)`, which isn't configured. Fixed by inserting cases first with `current_version_id` left `NULL`, then versions/steps, then one single batched `UPDATE ... FROM` statement to link them back — not a per-row Python-side `UPDATE`.
3. **Still 8-11s after both fixes**: SQLAlchemy ORM's per-object unit-of-work/identity-map tracking (not network round-trips) was the dominant cost at ~8,000 constructed `Model(...)` instances. Fixed by switching to SQLAlchemy's documented Core-style bulk insert (`insert(Model)` executed against a list of plain dicts) — brought the service-level time down to ~1.2s, comfortably inside the 2.5s budget. Confirmed with `cProfile` that the *remaining* ~1.3s gap seen only when measuring through `TestClient` is that test harness's own double-threaded ASGI bridging overhead (time spent blocked on a thread lock, not in application code) — not present in a real deployed server, so the performance test now measures the service call directly for the hard budget, with a separate HTTP-level test covering functional correctness at the same scale.

## Two more real bugs found and fixed this phase (same two recurring classes as before, now documented as standing rules in ARCHITECTURE_DECISIONS.md)
1. **Step-count double-counting**: `step_count = sum(verdict_counts.values()) + verdict_counts.pop(None, 0)` counted the unexecuted (`NULL`-verdict) steps twice — `sum()` already included them before the separate `.pop()` added them again, so a 3-step case reported `step_count: 6`. Fixed by computing the total before popping the `None` key out.
2. **`autoflush=False` struck again, this time inside a single service call, not across a commit boundary**: `record_verdict()` set `step.verdict = "fail"` in memory, then immediately queried all of that case's step verdicts to recompute the rollup status — but with autoflush off, that SELECT read the *previous* verdict from the database, silently computing the wrong status (a case with a freshly-failed step still showed `in_progress`). Fixed with an explicit `db.flush()` between the mutation and the dependent query. Documented as a new standing rule in `ARCHITECTURE_DECISIONS.md` alongside the RLS-after-commit gotchas, since both stem from the same session configuration and are easy to re-trip on in Phase 7.

## One more instance of the recurring RLS-after-commit bug (now the third time — same root cause, same fix)
`add_link()` committed, then the route handler called `get_defect()` again to re-fetch for the response — a fresh RLS-protected query in a transaction with no tenant context, silently returning 404 instead of the defect that very much exists. Fixed by having `add_link()` return the already-loaded `Defect` object directly (its `to_out()` already re-asserts tenant context as required) instead of the route re-querying after the commit. This is the same class of bug as Phase 4/6's — the standing rule in `ARCHITECTURE_DECISIONS.md`'s ADR-007 addendum is clearly worth restating prominently before any future phase's `to_out`/route-handler pattern: never issue a fresh RLS-protected query after a commit without re-asserting tenant context first, and prefer returning already-loaded objects over refetching.

## Phase 9 scope note

Since **no frontend screens exist yet** (every phase 2-8 was explicitly backend-only — confirmed with the user before starting this phase), the accessibility/E2E portions are impossible to do for real against a health-check page. Per explicit user direction, this phase was split: the backend-doable work (audit hardening, RLS verification, security review) is done now as Phase 9; the UI-dependent work moves to a new Phase 10 once frontend screens exist, rather than being silently skipped or faked.

An audit against the original Defect Management/traceability build prompt found the lifecycle state machine, version pinning, and creation paths all correct, but the Fail-time dialog showed nothing to the user beyond severity/description (project/case/run/step were hidden ids only), "link to existing defect" existed only as an unexposed API affordance, three named fields (Actual Result, Expected Result, Environment) had zero implementation, there was no history/timeline, the defect detail page had no execution evidence or step-level deep link, filters lacked a reporter/date dimension, and "closing requires verification confirmation" was satisfied only by the Verified status existing earlier in the sequence rather than as a distinct gesture.
- [x] **Visible prepopulation**: the Fail-time dialog now shows project/run/test-case names and the failed step inline, plus an editable auto-suggested title (previously silently applied server-side with no field for it).
- [x] **Link to existing defect**: a "Create New"/"Link Existing Defect" toggle in the dialog; `list_defects(test_run_id=...)` broadened to also match defects linked (not just originally created from) a step in that run, so the console's 🐞 badge correctly reflects linked defects too.
- [x] **Actual Result / Expected Result / Environment**: added as columns (migration `c7d8e9f0a1b2`); `expected_result` defaults from the step's own expected text when created from a failure and not overridden.
- [x] **Defect history**: new `GET /defects/{id}/history`, reusing the existing `audit_logs` table (no new table) filtered by entity; a History card on the detail page.
- [x] **Execution evidence + deep traceability**: `DefectOut` resolves the originating execution step (verdict/duration/timestamps/executed-by) and exposes the test case version number and a direct link into the Execution Console at the exact failed step.
- [x] **Reporter/date filters**: `reported_by` (the one real person-dimension that exists — no assignee column exists on defects, confirmed not invented) plus `created_from`/`created_to` date-range filters.
- [x] **Explicit close confirmation**: a new `verification_confirmed` boolean required (422 if missing) when transitioning to Closed; a checkbox on the detail page gates the button, distinct from the existing Admin/Manager role gate.
- [x] **Reverse navigation**: a new `test_case_id` filter plus "Linked Defects" cards on both `TestCaseDetail.tsx` and `TestRunDetail.tsx`.
- [x] New tests: 9 added to `test_defects.py` (evidence fields, expected-result default, in-run creation, execution evidence resolution, close-confirmation requirement, link-to-existing run-scoped visibility, history tracking, reporter/date filters, test_case_id filter). Full suite: 127/127 passing, `ruff`/`mypy` clean. Frontend: `typecheck`/`lint`/`test`/`build` clean, same pre-existing benign warnings, no new ones (the dialog's refactor into a keyed child component also eliminated a transient `set-state-in-effect` lint warning from an early draft, by computing initial form state directly instead of syncing it via an effect).
- [x] **Driven live** against a full `docker compose up --build`, plus the full Playwright E2E suite (9/9 passing, including both defect-related journeys) rerun against the rebuilt image — `journey4`'s existing test needed one line added (check the new confirmation checkbox) since the Closed transition's actual behavior changed: failed a step and screenshotted the dialog showing all four prepopulated fields plus the editable title and Actual/Expected/Environment inputs; opened the resulting defect and confirmed the Details, Traceability (with version number and a clickable "Step 1 (open in console)" link), Execution Evidence, and History cards all rendered correctly with real data; navigated to the test case and test run detail pages and confirmed both showed the new "Linked Defects" card with the correct defect and status badge. Verification data (test case/run/defect) could not be deleted afterward for the same reason as the prior pass — now referenced by real execution/defect records — left in place as inert artifacts.

## Dashboard and Reporting hardening pass (report filters, execution trends, pie/line charts, missing KPIs, compliance detail/print view, assignee disclosure)
An audit against the original Dashboard and Enterprise Reporting build prompt found the core aggregation logic (tenant/role scoping, no duplicate counting) correct, but seven named items missing or incomplete, including the browser-print-to-PDF fallback ADR-027 itself had promised but never built. Closed all seven:
- [x] **Report filters**: `GET /reports/aggregate` gained `project_id`/`domain`/`assignee_id`/`date_from`/`date_to`/`priority`/`status` query params, applied via a filtered-subquery pattern that composes uniformly across all five metrics' differently-shaped base queries (ADR-038). `Reporting.tsx` gained a Filters card with all six controls, wired into the aggregate query.
- [x] **PDF / print view**: new `GET /reports/compliance-detail` returns the full structured compliance report (summary + per-project test case/defect detail tables) as JSON; a new `/reporting/print` route renders it with `@media print` high-contrast styling and a "Print / Save as PDF" button — no server-side PDF library added, per ADR-027's original decision.
- [x] **Pie/Donut and Line charts**: the Aggregate Report gained a Bar/Pie-donut chart-type toggle; a new `GET /reports/execution-trend` (daily pass/fail/ignore step-verdict counts over a trailing window) backs a new `recharts` `LineChart` section — the first line chart in the system.
- [x] **Missing KPIs**: `DashboardSummary` gained `projects.active`, `test_cases.approved_count`, `defects.critical_count`; `DomainDistributionEntry` gained `pass_percentage`. `Dashboard.tsx` now shows 8 explicit KPI cards (was 4) and the domain cards show pass rate.
- [x] **Reporting Period + detail tables in CSV export**: `get_compliance_report`/`compliance_report_to_csv` split the report-building step from CSV serialization; the CSV now has a Reporting Period header row and per-project "-- Test Cases"/"-- Defects" detail tables alongside the existing summary table.
- [x] **Assignee semantics disclosure**: `Reporting.tsx` shows a hint below Group By whenever "By Assignee" is selected, naming the exact per-metric dimension ADR-027 already defined at the data layer — a frontend-only fix, no backend change needed.
- [x] **Compliance export accuracy tests**: numeric accuracy was previously untested against any known dataset; new tests assert exact counts and row contents for both the JSON detail endpoint and the CSV export against the `_full_scenario` fixture.
- [x] New tests: 9 added to `test_reporting.py` (active/approved/critical counts, per-domain pass percentage, `test_case_status` metric, 3 filter combinations, execution trend, compliance detail, compliance CSV detail tables). Full suite: 136/136 passing, `ruff`/`mypy` clean. Frontend: `typecheck`/`lint`/`test`/`build` clean, same pre-existing benign warnings, no new ones. No new migration needed — every new field is computed at query time from existing columns.
- [x] **Driven live** against a full `docker compose up --build` (reusing the existing tenant; the recreated `db` container's superuser/app-role passwords were reset via a local trusted-socket `ALTER ROLE` to match the dev `.env`, since the named volume's data — and therefore its existing password hashes — persisted across the rebuild), plus the full Playwright E2E suite (8/9 passing — `journey3-test-execution`'s single failure is a pre-existing locator strict-mode ambiguity from an earlier module, unrelated to any file touched in this pass, confirmed by rerunning it in isolation): logged into the real tenant and confirmed all 8 dashboard KPI cards and entity-typed Recent Activity render with real data; opened Reporting and exercised every filter control, the `test_case_status` metric, the Pie/donut chart type, the Execution Trends line chart, and the Assignee grouping hint, all screenshotted; opened `/reporting/print` and confirmed tenant name, generation timestamp, reporting officer, reporting period, summary table, and per-project detail tables all render correctly. Verification screenshots and the temporary E2E spec were deleted afterward.
