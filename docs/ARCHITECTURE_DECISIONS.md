# Architecture Decision Records (ADR)

Status legend: **Decided** (binding for implementation), **Open** (needs stakeholder sign-off before the affected module is built).

BRD source: BRD-QTH-INS-2026-V2.4. These ADRs resolve ambiguities in that document per the architecture-review notes supplied alongside it. None of these change business intent; they fix *how* an ambiguous or under-specified requirement is implemented.

---

## ADR-001: Test case lifecycle split into authoring/approval vs. execution state
**Status:** Decided

The BRD (FR-TC-001, §7.2) lists `Draft, Ready for Review, Approved, In Progress, Assigned, Passed, Failed, Blocked` as one lifecycle, but these are two different concerns: the *document* (is this test case trustworthy enough to run) and *a specific execution of it in a run* (did it pass this time).

**Decision:**
- `test_cases.status` (authoring/approval, governs FR-TC-003 approval gate): `draft`, `ready_for_review`, `approved`, `deprecated`.
- `test_run_cases.status` (per-run execution verdict, FR-EXEC-001): `pending`, `in_progress`, `passed`, `failed`, `blocked`, `ignored`.
- A test case can be `approved` and simultaneously have many `test_run_cases` rows in different states across concurrent/historical runs.
- Editing an `approved` test case creates a new `test_case_versions` row (see ADR-003) and does not change `status` unless the manager explicitly re-drafts it.

## ADR-002: Step references use foreign keys, not raw array indices
**Status:** Decided

The BRD uses 1-based `order` for `TestStep` but a 0-based example (`stepIndex: 2` for "Step 3") for defect linkage — a direct contradiction if indices are used as the join key.

**Decision:** Steps are rows, not array members. `test_case_version_steps.id` (UUID) is the join key everywhere a step must be referenced (`execution_steps.test_case_version_step_id`, `defects.test_case_version_step_id`). `step_number` is retained purely as a **1-based, human-facing display/ordering column** (matches BRD `order` field) and is never used as a lookup key. This eliminates the off-by-one ambiguity entirely rather than picking a side.

## ADR-003: Immutable test case versioning with execution pinning
**Status:** Decided

**Decision:** Every approval-worthy edit to an approved test case writes a new immutable row to `test_case_versions` (+ `test_case_version_steps` snapshot of all steps at that point), and `test_cases.current_version_id` advances. A `test_run_case` stores `test_case_version_id` captured **at run-case creation time**, so historical executions always report against the exact step text that was actually run, even if the test case is edited or re-approved later. `history` as a loose JSON blob (as the BRD literally describes) is rejected in favor of normalized version rows — required for FR-DEF compliance-grade traceability (defect → exact version → exact step).

## ADR-004: Execution state is normalized, not a single JSON blob
**Status:** Decided

The BRD's `TestRun.results` / `stepResults` / `executionTimes` maps are a denormalized, single-document shape. Per the supplied architecture guidance, this is explicitly rejected for the relational implementation.

**Decision:** Four normalized entities: `test_runs` (the cycle) → `test_run_cases` (one row per test case bundled into the run, carries the pinned `test_case_version_id` and rollup `status`) → `execution_steps` (one row per step per run-case, carries verdict `pass|fail|ignore`, `duration_ms`, `executed_by`, `executed_at`). This is required for concurrent execution safety, step-level reporting (FR-REP-001), and because a single wide JSON column cannot be indexed or queried efficiently at the volumes implied by FR-TC-002 (2,000+ cases).

## ADR-005: Defect-step linkage is many-to-many via a join table
**Status:** Decided

BRD FR-EXEC-003 implies one defect per failed step, but FR-DEF-002 and real triage practice require multiple defects to reference one step (duplicate reports) and, less commonly, one root-cause defect to span several steps/cases.

**Decision:** `defects` holds the primary context (`project_id`, `test_case_id`, `test_run_id`, `reported_by`, etc.) for the defect that was created *from* a specific execution event. `defect_links` is a separate join table (`defect_id`, `linkable_type`, `linkable_id`) enabling a defect to additionally reference other `execution_steps`, `test_cases`, or other `defects` (duplicate-of) without losing the original creation context. The "pill badge on the failed step" (FR-EXEC-003) is rendered from `execution_steps.id -> defect_links`, not from a single FK column on the step.

## ADR-006: Audit log is insert-only with hash chaining, not provably tamper-proof against DBAs
**Status:** Decided — residual risk tracked in KNOWN_GAPS

**Decision:** `audit_logs` rows are never updated or deleted by any application code path (no UPDATE/DELETE route exists in the service layer). Each row stores `prev_hash` and `record_hash = sha256(prev_hash || canonical_json(row))`, forming a hash chain per tenant, enabling detection of row tampering or deletion-by-renumbering. Database grants additionally `REVOKE UPDATE, DELETE` on `audit_logs` for the application role; only a separate, non-application migration role can alter the table. **This mitigates but does not cryptographically prevent** tampering by someone holding raw superuser/DBA credentials — that requires external WORM log shipping (e.g., write-once object storage) which is out of scope for this phase and recorded in `KNOWN_GAPS.md`.

## ADR-007: Tenant isolation enforced at both ORM query layer and PostgreSQL RLS
**Status:** Decided

**Decision:** `tenant_id` is never accepted from request payloads; it is derived server-side from the authenticated session on every request. Two independent layers enforce isolation so a bug in one does not cause a breach:
1. **Application layer:** a SQLAlchemy base repository that injects `WHERE tenant_id = :session_tenant_id` on every tenant-scoped query automatically.
2. **Database layer:** PostgreSQL Row-Level Security policies on every tenant-owned table, keyed to a `current_setting('app.current_tenant')` session variable set by the backend at the start of each request's DB transaction.
Platform-level tables (`tenants`, platform superuser accounts) are exempt from RLS and are only reachable via a separate Platform Administration API surface (see ADR-008).

**Addendum (migration `567fa7545de9`):** the policy predicate must be `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid`, not a bare cast. A custom GUC placeholder that has only ever been set via `set_config(..., true)` (transaction-local) reverts to `''` — not `NULL` — once that transaction commits, so a bare `::uuid` cast throws `invalid_text_representation` on the next transaction instead of just failing the predicate (deny). `NULLIF(..., '')` converts the empty string to `NULL` first, so the comparison safely evaluates to `NULL`/false (default-deny) as intended.

**Addendum (SQLAlchemy session config):** `app.current_tenant` is transaction-LOCAL by construction (`set_config(..., true)`), so it does not survive past a `db.commit()`. `SessionLocal` is therefore created with `expire_on_commit=False` (`app/core/db.py`): the common service pattern — do work, `commit()` once, then have the route build a response from the same already-loaded objects — must not trigger a post-commit attribute refresh, because that refresh would run in a new transaction with no tenant context and RLS would deny it. Any service that truly needs to re-query after a commit must re-call `set_tenant_context` first.

**Addendum (Phase 6, recurring gotcha — read this before writing any read-after-write logic in a service):** `SessionLocal` also sets `autoflush=False`. A Python-side attribute assignment on an ORM object (e.g. `step.verdict = "fail"`) is **not** visible to a subsequent `db.execute(select(...))` in the same session unless something flushes first — the SELECT reads what's still committed in the database, not the pending in-memory change. This bit `execution_service.record_verdict()`: it set `step.verdict` then immediately called a helper that re-queried all of that case's step verdicts to recompute the case's rollup status, silently using the *previous* verdict and producing a wrong status. **Rule of thumb:** after mutating an object's columns, call `db.flush()` before any subsequent same-transaction query whose result depends on that mutation — don't rely on autoflush, it's off.

**Addendum (Phase 4, recurring gotcha — read this before writing any new `to_out`/serializer):** `expire_on_commit=False` only protects *attribute access* on already-loaded objects — it does **not** help a serializer that issues a **new** query against another RLS-protected table after a commit (e.g. building a `TestCaseOut` by querying `test_case_versions`/`test_case_version_steps` fresh, after the service that created the case already committed). That new query runs in a new transaction with no tenant context and RLS silently returns zero rows (`NoResultFound`/empty list), not an error that points at the cause. **Rule of thumb:** any `to_out()`/serializer function that itself queries an RLS-protected table must re-assert `set_tenant_context(db, str(<tenant_id known from the already-loaded object>))` as its first line, unconditionally — it's cheap (one `SELECT set_config`) and correct whether or not a commit happened in between. `project_service.to_out` escaped this only because `project_members` (its one extra query) happens to be RLS-exempt by omission, not by design — don't rely on that; prefer the explicit re-assertion in every new serializer.

## ADR-008: First-tenant-admin bootstrap via a Platform Owner role, outside tenant RBAC
**Status:** Decided

The BRD's RBAC matrix only defines `Admin/Manager/Tester` *within* a tenant, but someone must create tenant #1's first Admin, and the BRD says only "Admin" can create tenants (circular for tenant zero).

**Decision:** Introduce a `platform_owner` concept (a flag on a user row with no `tenant_id`, or a small dedicated `platform_admins` table — finalized in DATABASE_SCHEMA.md) used exclusively by the Platform Administration surface. A platform owner can create a tenant and provision its first tenant Admin user. Platform owners cannot access any tenant's test/project data — they are provisioning-only, keeping the "all insurance data is tenant-scoped" guarantee intact. Seeded via a one-time migration/CLI command, not a public signup form.

## ADR-009: GDPR/CCPA erasure reconciled with immutable audit trail via pseudonymization
**Status:** Decided

**Decision:** "Right to be forgotten" purges PII (`name`, `email`, free-text fields that may contain PII) from `users` and from the human-readable fields of historical `audit_logs`/`defects`/etc. by replacing them with a stable pseudonym (`user_<uuid>`), while the row itself, its `user_id` FK, timestamp, and action type are retained. The hash chain (ADR-006) is computed over a canonical form that already excludes mutable PII fields, so pseudonymization does not break chain verification. Full physical deletion of a user row is only permitted if the tenant has zero retained audit/compliance obligations for that user — flagged `KNOWN_GAPS` pending legal sign-off on retention periods per jurisdiction.

## ADR-010: Offline-first claim reinterpreted as resilient synchronous writes, not disconnected operation
**Status:** Decided

The BRD simultaneously requires "offline-first local storage" and "cloud-native multi-tenant" with no sync protocol defined — these are incompatible as literally written for a shared multi-tenant Postgres backend.

**Decision:** The product is server-authoritative (PostgreSQL is the single source of truth, per the stated constraint in the master prompt). "Offline-first" is satisfied as: (a) every execution-step toggle (FR-EXEC-002) is written synchronously to the backend immediately, with sub-50ms perceived latency via optimistic UI update + background confirm; (b) in-progress, not-yet-submitted form state (e.g., a defect being drafted) is held in browser storage only as a recovery buffer against accidental tab close, per the explicit "browser storage only for temporary UI state" engineering principle. True disconnected (no network) operation is **out of scope** for this phase; see `KNOWN_GAPS.md`.

## ADR-011: MFA implemented as a real, configurable mechanism; "simulation" means test-mode only
**Status:** Decided

**Decision:** `mfa_challenges` implements a genuine 6-digit TOTP-or-OTP challenge per FR-AUTH-003 (code, expiry, attempt counter, lockout after 3 failures). A per-tenant/per-environment config flag (`mfa_delivery_mode: real | simulated`) controls whether the code is actually sent via an email/SMS provider or simply logged/returned in non-production environments for test automation — the data model and enforcement logic are identical either way. No push-notification or hardware-key MFA in this phase.

## ADR-012: Attachments stored on disk/object storage, not as Base64 in PostgreSQL
**Status:** Decided

The BRD's `Attachment.data: string (Base64 data URL)` is rejected for storage (bloats the DB, breaks backup/restore performance, contradicts the engineering principle against storing blobs as the "primary database" content).

**Decision:** Client may still *upload* as Base64 or multipart; the backend decodes and writes bytes to a filesystem path (local volume now, swappable for object storage later per the "File Storage: local filesystem initially" stack note) and stores only `attachments(id, tenant_id, owner_type, owner_id, file_name, mime_type, storage_path, size_bytes, checksum, uploaded_by, uploaded_at)` in PostgreSQL.

## ADR-013: Currency, numeric precision, date/time conventions
**Status:** Decided

**Decision:** `projects.budget` is `NUMERIC(14,2)` plus a required `projects.currency_code CHAR(3)` (ISO 4217), defaulted from a per-tenant setting — never a bare float. All instants (`created_at`, `executed_at`, audit timestamps) are `TIMESTAMPTZ` stored in UTC; all calendar-only fields (`start_date`, `end_date`) are `DATE` with no timezone, interpreted in the tenant's configured timezone for display only. Millisecond execution timings (FR-EXEC-002/BR-09) are stored as `INTEGER duration_ms`, computed server-side from step-open/step-close `TIMESTAMPTZ` pairs rather than trusting a client-reported duration.

## ADR-015: `sessions` and `mfa_challenges` are exempt from tenant RLS
**Status:** Decided

Resolving a session cookie into a user requires looking the row up **before** the tenant is known — but ADR-007's RLS policy requires `app.current_tenant` to already be set to read any tenant-scoped row, which is circular for exactly these two tables.

**Decision:** `sessions` and `mfa_challenges` are excluded from the `tenant_isolation` RLS policy (migration `8c1a5e9a7b3f`); every other tenant-owned table keeps it. Security for these two tables instead rests on the session/challenge id being an unguessable random UUID primary key (the same trust model as a password-reset token) plus application-level checks (`expires_at`, `revoked_at`, `attempt_count`). Once a session row is resolved, its `tenant_id` becomes the trusted, server-derived context for the rest of the request (`set_tenant_context`), so every other table's RLS still applies normally from that point on. An admin-facing "list my tenant's active sessions" view filters by `tenant_id` explicitly in the query, same as any other tenant-scoped read — RLS is simply not the enforcement mechanism for these two bootstrap tables.

## ADR-016: Audit hash-chain writes are serialized per tenant with an advisory lock
**Status:** Decided

Two concurrent transactions appending audit rows for the same tenant could both read the same "last hash" before either commits, corrupting the hash chain (ADR-006).

**Decision:** `record_audit_event()` takes `pg_advisory_xact_lock(hashtext(tenant_id))` before reading the previous row's hash and inserting the new one. The lock is automatically released at transaction end (commit or rollback), serializing audit appends per tenant without blocking unrelated tenants or non-audit work.

## ADR-018: Manager's project edit/delete/member-management authority is scoped to assigned projects; viewing is tenant-wide
**Status:** Decided

BRD §3.2 lists "Create/Edit/Delete Projects: Manager — Yes (Assigned)" and "Allocate Team Members: Manager — Yes" (no qualifier) — the parenthetical appears on some rows but not others, and the BRD never defines what "assigned" means operationally for a Manager (project ownership? membership? both?).

**Decision:** "Assigned" means the Manager is either the project's `owner_id` or a row in `project_members` for that project. This gate applies uniformly to `PATCH /projects/{id}`, `DELETE /projects/{id}`, and both member-management endpoints for the Manager role — the member-management row's missing "(Assigned)" qualifier is treated as an omission, not an intentional broader grant, since allowing an unassigned Manager to add/remove members on a project they have no other authority over would be an inconsistent privilege escalation path. Admin bypasses this check entirely (BRD's "Global tenant visibility"). **Viewing** (`GET /projects`, `GET /projects/{id}`) is tenant-wide for both Admin and Manager — only Tester's visibility is restricted to assigned projects (FR-PROJ-002's explicit acceptance criterion: "Testers only see assigned projects in project selectors"). The project creator is automatically added to `project_members` on creation, so a Manager who creates a project is immediately "assigned" to it and can edit/delete what they just made.

## ADR-019: Test case authority is project-assignment-gated only for Tester, not Manager
**Status:** Decided

ADR-018 scoped *project-entity* edit/delete to "assigned" Managers because the BRD explicitly marks those RBAC rows "(Assigned)". The test case rows in the same matrix (`Create & Edit Test Cases`, `Delete Test Cases`, `Approve Test Cases`) carry no such qualifier for Manager — only Tester's rows are qualified ("Own Drafts Only" for delete) and FR-PROJ-002 explicitly restricts Tester's *project visibility* to assigned projects.

**Decision:** Test case operations (`create`, `edit`, `submit-review`, `approve`) are gated purely by the `testcase.*` permission flags for **Admin and Manager** (tenant-wide authority, no project-assignment check), matching the BRD matrix's lack of a qualifier for those roles. **Tester** is additionally required to be assigned to the test case's project (owner or `project_members` row) — consistent with Tester's restricted project visibility elsewhere. `DELETE /test-cases/{id}` is the one operation with an explicit extra rule for every role: Admin/Manager may delete any case; **Tester may delete only their own `draft`-status cases** ("Own Drafts Only," BRD §3.2) — enforced in the service layer rather than via the permission-flag dependency, since it's a data-ownership condition, not a role-wide grant.

## ADR-020: Editing a draft mutates in place; editing an approved case always forks a new version and reverts to Draft
**Status:** Decided

FR-TC-001's acceptance criterion only explicitly covers one case: "Adding or modifying steps on an approved test case automatically increments the version counter and archives the previous state." It doesn't say what happens when editing a `draft` or `ready_for_review` case (never yet approved, never yet pinned by any execution), nor what the case's `status` becomes after a post-approval edit.

**Decision:**
- While `test_cases.status` is `draft` or `ready_for_review`: edits (title, priority, assignee, steps) mutate the **current** `test_case_versions`/`test_case_version_steps` rows in place — no new version is created, since nothing has been approved or executed against this version yet, so there is no history to protect (ADR-003 only requires preserving versions once they matter for traceability).
- While `status` is `approved`: **any** edit creates a new `test_case_versions` row (version N+1, fresh step snapshot) and reverts `test_cases.status` to `draft`, matching the state machine diagram in BRD §7.2 ("Rejection / Rework" arrow back to `[Draft] (Version Increments +1)"). The case must go through `submit-review` → `approve` again before it can be used in a new test run. Already-created `test_run_cases` rows keep pointing at the old, now-superseded version (ADR-003's pinning), so in-flight/historical executions are unaffected.

## ADR-021: CSV import is tenant-scoped (not project-scoped) and processed synchronously, not staged/polled
**Status:** Decided — corrects a Phase 0 planning error

**Problem found during implementation:** the Phase 0 `API_SPECIFICATION.md` put CSV import under `POST /projects/{id}/test-cases/import`. But FR-TC-002's CSV header list includes a per-row **Project Name** column with its own acceptance criterion ("Project name is verified against active tenant projects") — meaningless if the endpoint already pins the project via the URL path. The BRD's own design intends a single CSV to span **multiple projects** within one tenant (consistent with the "250 legacy underwriting cases" bulk-migration journey, which doesn't imply a single project).

**Decision:**
- `POST /test-cases/import` is **tenant-scoped**, not project-scoped. Each row resolves its own project by name (case-insensitive, matching `uq_projects_tenant_name_ci`); a row whose project doesn't exist in the tenant is a per-row validation error, not a whole-batch failure.
- Authorization is per-row: for each resolved project, the normal ADR-019 rule applies (Admin/Manager tenant-wide; Tester must be assigned to that specific project) — so one CSV can partially succeed for a Tester across several projects they're variously assigned to or not.
- `GET /projects/{id}/test-cases/export.csv` stays project-scoped (export naturally pins to one project's test cases; no BRD ambiguity there).

**Second decision, same ADR — synchronous processing, not a staged batch + polling design:** the originally-drafted `GET /test-cases/import/{batchId}/report` polling endpoint is dropped. NFR 8.1 caps the requirement at 2,000 rows in under 2.5s — well within what a single synchronous request can parse, validate, and commit. Building a staging table, a background job, and a polling endpoint for that volume would be unrequested infrastructure (no job queue is in the approved tech stack). `POST /test-cases/import` parses the whole CSV, validates every row, inserts all valid rows in one transaction, and returns the full per-row report directly in the response body — "staged" (ARCHITECTURE.md's import architecture) now means "validated in memory before any row is written," not "written to a separate DB staging table."

## ADR-022: Finishing a test run is a Manager/Admin sign-off gate; a new `testrun.finish` permission is added
**Status:** Decided

BRD §3.2 only lists "Create & Launch Test Runs: Yes/Yes/Yes" (all three roles) — there is no separate RBAC row for *closing* a run. But closing a run computes and locks final verdicts (FR-EXEC-001: "Finishing a run sets `finishedAt` and calculates final run verdicts"), which is a formal sign-off action analogous to test case approval (`testcase.approve`, Manager/Admin-only).

**Decision:** A new permission, `testrun.finish`, is seeded for Admin and Manager only (not Tester) — symmetric with the approval gate, and consistent with the Manager persona's BRD-stated responsibility for "test run assignment" and sign-off, versus the Tester persona's "test run execution." Creating and executing a run remains open to all three roles via the existing `testrun.create`/`executionstep.record` permissions; only the final close-out is gated.

## ADR-023: Execution steps are pre-created (verdict=NULL) at test-run-case creation, not lazily on first open
**Status:** Decided

**Decision:** When a test case is bundled into a run (`test_run_cases` row created), one `execution_steps` row is created immediately for every step of the pinned `test_case_version` (`verdict=NULL`, `opened_at=NULL`). This guarantees `GET /test-run-cases/{id}/steps` always returns the complete step list immediately after run creation — matching FR-EXEC-001's "unexecuted test cases default to Pending" — rather than requiring the client to infer unexecuted steps from an initially-empty list. `POST /execution-steps/{id}/open` and `.../verdict` act on these pre-existing rows (UPDATE, not INSERT).

## ADR-024: Test-run-case status is recomputed from scratch from step verdicts, not tracked incrementally; steps are re-verdictable
**Status:** Decided

BRD Journey 4 describes re-executing a previously-failed step after a fix and marking it Pass **within the same test run** ("Tester marks Step 3 as Pass. The test case status turns Passed") — so `POST /execution-steps/{id}/verdict` must be callable more than once per step, not just on first submission.

**Decision:** `record_verdict()` always recomputes `test_run_cases.status` from the full current set of that case's `execution_steps` verdicts, rather than incrementally patching state: `status = 'failed'` if any step is `fail`; else `'passed'` if every step has a non-null verdict (`pass`/`ignore` both count as resolved); else `'in_progress'` if at least one step has a verdict; else `'pending'`. This is idempotent and self-correcting — re-verdicting a step (e.g., Fail → Pass after a fix) naturally flips the case's rollup status without any special-case "undo" logic. `started_at` is set once, on the first verdict ever recorded for the case, and never cleared; `completed_at` is refreshed to now whenever the recomputed status is `passed`/`failed`, and cleared otherwise (e.g., a corrected verdict that reopens the case).

**Addendum (Phase 10.9):** the backend's re-verdict support had no corresponding frontend control. `ExecutionConsole.tsx`'s `StepCard` only rendered the Pass/Fail/Ignore buttons for the one step with `verdict === null` (`isCurrent`) — once a step had *any* verdict, including a `Fail` that Journey 4 describes fixing and re-running, there was no way to invoke `POST /execution-steps/{id}/verdict` a second time from the UI at all. Caught by the Phase 10.9 E2E suite (`journey4-defect-lifecycle.spec.ts`) attempting to re-verdict a failed step and finding no button to click — not a test-script mistake, a real shipped gap from Phase 10.5. Fixed by adding a "Re-run step" disclosure control to any step that already has a verdict and isn't current, revealing the same three verdict buttons on demand (not shown unconditionally, to avoid accidental misclicks on a settled step).

## ADR-025: Only `approved` test cases can be bundled into a test run
**Status:** Decided

The BRD's state machine (§7.2) shows `Approved → Assigned/In Progress → Passed/Failed/Blocked` as the only path into execution — `draft`/`ready_for_review` cases never appear on that path, and FR-TC-003 exists specifically to gate "formal execution" behind Manager/Admin sign-off.

**Decision:** `POST /projects/{id}/test-runs` rejects (per-row validation error, not a whole-request failure) any `test_case_id` whose current `status` isn't `approved`. This also means the version pinned into `test_run_cases.test_case_version_id` (ADR-003) is always an approved, reviewed version — never a draft snapshot.

## ADR-026: Defect status transitions are strictly sequential; no skipping, no reopening
**Status:** Decided

FR-DEF-001 states the transitions "follow the defined state machine: New → Open → Fixed → Verified → Closed," and §7.2's diagram shows only forward arrows — no path back from `Closed`/`Verified` to an earlier state, and no explicit "reopen" transition.

**Decision:** `PATCH /defects/{id}/status` only accepts a transition to the **immediate next** status in that fixed sequence (`New→Open→Fixed→Verified→Closed`) — no skipping ahead (e.g. `New→Fixed` directly) and no moving backward. There is deliberately no "reopen a closed defect" transition: if a fixed/verified issue recurs, BRD Journey 3's pattern (a failed execution step opens a *new* defect, FR-EXEC-003) is the supported path, not resurrecting an old one — inventing a reopen transition the BRD never describes would be scope creep. Per BRD §3.2, only the transition *to* `Closed` is role-gated (Manager/Admin only, via the existing `defect.close` permission); every other transition is available to any of the three roles that can otherwise access the defect (consistent with "Log Defects: Yes/Yes/Yes" and the matrix's silence on gating `Open`/`Fixed`/`Verified` specifically — BRD Journey 4 shows a Manager performing `Verified`→`Closed`, but nothing in the RBAC matrix restricts Tester from the earlier transitions, so this implementation doesn't invent that restriction either).

## ADR-027: Reporting/Dashboard scope, metric definitions, and the "assignee" dimension
**Status:** Decided

Several things FR-DASH/FR-REP leave unstated:

1. **Tester's viewing scope on the Dashboard.** The RBAC matrix's only explicit qualifier is on the *Reporting* row ("View Executive Reporting & Charts: ... Tester Restricted to Assigned"); the Dashboard FRs carry no such qualifier. **Decision:** apply the same assigned-projects restriction to both, for consistency with every other module in this codebase (ADR-019 et al.) — a QA Director-style "organization at a glance" view for a Tester role would otherwise be the one inconsistent exception in the whole system.
2. **What "Status (Passed, Failed, Pending, Blocked)" refers to.** Those four values are `test_run_cases.status`, not `test_cases.status` (whose enum is `draft/ready_for_review/approved/deprecated` — a different lifecycle entirely, ADR-001). **Decision:** the `status` reporting metric aggregates `test_run_cases.status`.
3. **What "Assignee" means for the Defects grouping dimension.** `defects` has no assignee column (BRD's own schema for `Defect` doesn't include one) — the closest analogous person-dimension is `reported_by`. **Decision:** grouping defects "by Assignee" groups by `reported_by`. For the `priority` metric (test cases), Assignee is `test_cases.assignee_id`; for the `status` metric (test run cases), Assignee is `test_run_cases.assigned_to` (frequently `NULL`/"Unassigned," since no run-case assignment endpoint exists yet — not a gap, just an unused optional column).
4. **PDF generation (resolves GAP-08).** FR-REP-002's own acceptance criterion describes a "Printable view [that] strips navigation menus and formats tables cleanly across standard A4/Letter page bounds" — that is browser print-CSS behavior, a frontend concern, not a server-rendered PDF file. **Decision:** the backend generates the CSV compliance export only (`GET /reports/compliance-export`, CSV with a tenant/timestamp/reporting-officer header per FR-REP-002); no PDF-generation library is added to the stack. "PDF" is produced by the browser's native print-to-PDF against a print stylesheet, built when the Reporting screen's UI is implemented.

## ADR-028: `GET /users` is readable by anyone who can manage project members, not just `user.manage` holders
**Status:** Decided — found while building the Projects UI (Phase 10.2)

FR-PROJ-002 lets a Manager "Allocate Team Members to Projects," but `GET /users` was gated solely by `user.manage` (Admin-only, ADR-014's seed). A Manager assigning a teammate to a project has no way to see who exists in the tenant to pick from — the UI for a BRD-required feature was otherwise unbuildable.

**Decision:** `GET /users` accepts either `user.manage` (Admin) or `project.members.manage` (Admin/Manager) — a new `require_any_permission(*codes)` dependency (`app/core/auth.py`), analogous to the existing `require_permission`. This exposes only the same basic directory fields `UserOut` already returns (id, email, name, role, is_active, created_at — never `password_hash`), which is ordinary tenant-directory information, not a privilege escalation: a Manager already has tenant-wide authority over projects and test cases (ADR-019); knowing colleagues' names/emails/roles to assign them is strictly narrower than that. Tester still cannot list users (neither permission is seeded for Tester).

## ADR-029: Audit log read access is a new `audit.view` permission, Admin-only
**Status:** Decided — found while building the Administration UI (Phase 10.8)

BR-13 had a write path (every module appends to the hash chain, ADR-006) and one narrow read surface (`/dashboard/activity-stream`, the last 10 events for the Dashboard card), but no endpoint for browsing or filtering the full tenant audit trail — the BRD's "Administration → Audit Logs" screen (`docs/MASTER_SPEC.md` module map) had nothing to call. No existing permission code fit: `report.view` is granted to all three roles (Tester included, per the seed migration), but the BRD's RBAC line is unambiguous — "**Admin**: full tenant control, user/role management, **audit access**, all project/testing operations" names audit access as an Admin-specific capability, not a reporting one.

**Decision:** added `audit.view` as its own permission (migration `a3c9e1f2b4d7`), granted to `admin` only — not folded into `report.view` (wrong audience) and not into `user.manage` (orthogonal: an Admin managing users and an Admin auditing the tenant are different concerns that happen to share a role today, but modeling them as one permission would make a future "compliance auditor" role, who needs `audit.view` without `user.manage`, impossible without a migration). `GET /audit-logs` supports `action`/`entity_type`/`user_id` filtering and pagination (capped at 200/page); a separate `GET /audit-logs/verify-chain` endpoint re-walks the full chain and recomputes every hash server-side (the same algorithm `test_audit_integrity.py` already exercised against real data in Phase 9), surfacing tamper-evidence as a UI-visible pass/fail rather than only a test assertion — this is what makes the hash chain's value visible to an actual compliance officer, not just to the test suite.

## ADR-017: Login requires an explicit tenant identifier; there is no global email lookup
**Status:** Decided

`users.email` is only unique **per tenant** (`uq_users_tenant_email`, ADR-007/DATABASE_SCHEMA) — the same email may legitimately belong to different people at different carriers. Since `users` correctly keeps tenant RLS (ADR-007), a login request of just `(email, password)` can't resolve which tenant to even query: without `app.current_tenant` set, RLS returns zero rows for every tenant, and there is no RLS-exempt global email→tenant index to fall back on (deliberately — that would reintroduce a cross-tenant enumeration surface, ADR-007's whole point).

**Decision:** `POST /auth/login` requires `tenant_id` explicitly in the payload, alongside `email`/`password` (the same pattern as Slack's workspace URL or Okta's org-specific login page). The backend sets `app.current_tenant` to the supplied `tenant_id` *before* querying `users`; if the tenant, email, or password is wrong, the result is identical in every case ("Invalid credentials") — the RLS-scoped query simply returns no matching row, so no tenant/email enumeration is possible (satisfies FR-AUTH-002's "clear, non-leaking error feedback"). How the frontend obtains `tenant_id` before showing the login form (subdomain routing, a saved "organization" picker, a magic link) is a UI concern for a later phase, not a backend contract change.

## ADR-014: Roles and permissions are modeled as data, not hardcoded enums, without contradicting "no custom roles in v1"
**Status:** Decided

The BRD's RBAC matrix (§3.2) is fixed to exactly `Admin/Manager/Tester` with no mention of custom roles, yet §4 of the master prompt lists `roles`/`permissions` as tables to evaluate.

**Decision:** `roles` and `permissions` tables exist and are seeded with exactly the three BRD roles and their fixed permission grants (matching §3.2 verbatim), queried by the backend's authorization layer instead of hardcoding role checks in route handlers. Tenants cannot create custom roles or alter the seeded permission set in this phase — the tables exist for correctness/auditability of authorization, not for a role-builder feature. Any future custom-RBAC feature is a scope change requiring the BRD's formal change-request process (§13).

## ADR-030: Login/MFA rate limiting via `slowapi`, per-client-IP, in-memory storage
**Status:** Decided — found during a post-Phase-10 security hardening pass (GAP-16)

GAP-16 flagged that `POST /auth/login` had no throttling at all — only the post-login MFA code had a 3-attempt lockout — and explicitly required an explicit decision before adding anything, since no rate-limiting library was in the originally approved stack.

**Decision:** `slowapi` (a FastAPI/Starlette-native wrapper over the `limits` library), keyed by client IP via its built-in `get_remote_address`, at 10 requests/minute on both `POST /auth/login` and `POST /auth/mfa/verify` (`app/core/rate_limit.py`). A 429 response is normalized into the app's standard `{"data": null, "error": {...}}` envelope (`app/main.py`'s `RateLimitExceeded` handler), not slowapi's default plain-text response. In-memory storage was chosen over a Redis-backed one since no cache layer exists in the stack and this is a single-process deployment; the gap's own closing condition explicitly names per-IP as an acceptable option, with a Redis-backed limiter reserved for if this needs to scale to multiple processes. A per-`(tenant_id, email)` key would be more precise but isn't a drop-in `key_func` — slowapi's key functions read the request/connection, not the JSON body — so it's deferred rather than built speculatively.

Testing note: rate limiting is **disabled by default** for the whole backend test suite (`conftest.py`'s `_disable_rate_limiting` autouse fixture) — with it left on, 74+ tests' worth of logins against the same TestClient "IP" would trip the limiter well before the suite finishes. The one dedicated test (`test_rate_limiting.py`) explicitly re-enables and resets the limiter for just itself.

## ADR-031: Foundation hardening pass — logging, Docker health/restart, env-sourced DB credentials, UI shell completion
**Status:** Decided — found during a gap audit against the original foundation build prompt

A later audit against the original foundation task list (Docker Compose, health checks, logging, UI shell) found several items the fast-moving module-by-module phases had never circled back to: no backend logging at all beyond uvicorn's own access log; `docker-compose.yml` had a health check only on `db`, no `restart:` policy on any service, and hardcoded plaintext credentials (GAP-11); and the UI shell was missing breadcrumbs and a notification area, with the profile area being plain text rather than a usable control.

**Decisions:**
- **Logging**: plain stdlib `logging` (`app/core/logging.py`), one stream handler to stdout, configured once at import time from `settings.log_level`. An ASGI middleware (`app/main.py`) logs method/path/status/duration per request. No structured JSON/correlation-ID logging was added — this is a single-process dev/early-stage deployment with no log aggregator in the stack to justify it; revisit if a real log pipeline (e.g. shipped to a SIEM) is added.
- **Docker health/restart**: added `healthcheck:` to `api` (hits `GET /api/v1/health` via `python -c urllib.request`, avoiding adding `curl` to the slim image) and `web` (`wget --spider`), and `restart: unless-stopped` to all three services. Both new health checks target `127.0.0.1` explicitly, not `localhost` — Alpine/busybox resolves `localhost` to `::1` first, and both `uvicorn`/Vite only bind IPv4 by default, so a `localhost` health check connection-refuses forever even though the service is actually up (caught by driving the actual containers, not by reading the compose file).
- **Credentials**: `docker-compose.yml` now sources `POSTGRES_PASSWORD` as a required (`${VAR:?...}`) substitution and `APP_DB_PASSWORD`/`POSTGRES_USER`/`POSTGRES_DB` as defaulted substitutions, read from a new gitignored root `.env` (template: `.env.example`). The `qtesthub_app` role's password, previously hardcoded directly in the baseline/RLS migration, is now set by a new migration (`c1d2e3f4a5b6`) from `APP_DB_PASSWORD`, defaulting to the original value so existing dev/test setups are unaffected. This doesn't eliminate GAP-11's weak dev default (the `.env.example` placeholder is still `change_me_dev_only`) — it moves the *mechanism* from "hardcoded, uneditable without a code change" to "operator-configurable per environment," which is the actual gap that mattered.
- **UI shell**: added `Breadcrumbs.tsx` (derived from the route path, with a static segment→label map; dynamic id segments render as a generic "Detail" crumb rather than an extra per-route lookup), `NotificationBell.tsx` (an honest empty-state dropdown — no backend notification feed exists yet, so it says "No new notifications" rather than fabricating items), and `UserMenu.tsx` (the former static "name · role" text is now a dropdown with a sign-in confirmation line and the logout action, replacing the always-visible Logout button). All three are hand-rolled with local component state (no Radix/shadcn dependency was ever actually installed despite the `components/ui/` naming — matching the existing pattern in `dialog.tsx`), avoiding a new dependency for click-outside-to-close behavior.

## ADR-032: Auth/tenant hardening pass — tenant status enforcement, password reset, idle timeout, real MFA delivery, Platform Administration UI
**Status:** Decided — found during an audit against the original authentication/tenant/RBAC build prompt

A later audit against the original auth/tenant/RBAC spec (separate from the BRD feature phases) found several gaps the module-by-module phases never circled back to, the most serious being that tenant status was defined and mutable but never actually enforced.

**Decisions:**
- **Tenant status enforcement**: `auth_service.start_login` checks `Tenant.status == 'approved'` *after* credentials are verified, not before — so ADR-017's generic "Invalid tenant, email, or password" error still fires first for any wrong credential, and a non-approved tenant's status is never learnable without a valid password. `core/auth.get_current_context` performs the same check on every authenticated request (not just at login), so suspending a tenant immediately cuts off any already-open session rather than only blocking new logins. As a consequence, `platform_service.create_tenant_with_admin` now sets a newly-provisioned tenant's status to `approved` directly, rather than leaving it at the `pending` default: there is no self-service tenant signup flow in this system, so creating a tenant through the platform-admin-only endpoint already *is* the approval decision. `pending` remains a valid, reachable status (a platform admin can set it via `PATCH /platform/tenants/{id}/status`) for a future self-service signup path, but nothing currently puts a tenant into it automatically.
- **Admin password reset**: `POST /users/{id}/reset-password` (new, `user.manage`-gated) sets a new password hash and revokes every one of that user's existing sessions, so a reset can't be bypassed by a session opened before the compromise was discovered. No self-service "forgot password" flow was added — that needs its own token/expiry/email design and wasn't named as a requirement; only the admin-initiated path was built.
- **Idle session timeout**: `Settings.session_ttl_minutes` existed but was read nowhere. Added `sessions.last_seen_at` (migration `d2e3f4a5b6c7`), updated on every authenticated request; `get_current_context` now revokes a session whose `last_seen_at` is older than `session_ttl_minutes` (default 30 min), independent of and in addition to the existing absolute `expires_at` check (12h by default, set after MFA verification).
- **MFA "real" delivery mode**: previously schema/config-only (`mfa_delivery_mode: "real"` was a valid value with no code path). Added `app/core/mfa.send_mfa_code`, an SMTP email sender used only when `MFA_DELIVERY_MODE=real`; it fails loudly with a new `ConfigurationError` (500, `configuration_error`) if `smtp_host` isn't set, rather than silently not sending the code. No SMS/push/hardware-key provider was added — the stack never named one, and picking a specific third-party service needs real credentials this environment doesn't have. "Simulated" mode (the default outside production) is unchanged: the code is still returned directly in the API response.
- **Platform Administration UI**: added `frontend/src/routes/PlatformAdmin.tsx` at `/platform-admin`, linked only from a small footer link on the tenant Login page — deliberately not part of the main app shell/nav, preserving ADR-008's separation between Platform Administration (HTTP Basic against `platform_admins`) and tenant session auth. Credentials are held only in React component state for the duration of the page, never persisted to storage or cookies. Lists tenants with status badges, creates a tenant + first Admin, and approves/suspends tenants inline, all via the pre-existing `/platform/*` endpoints.

Testing note: the suite's `platform_admin` fixture and `_bootstrap_tenant` helper in `test_auth_flow.py` already exercised tenant creation, but every test that logged in right after bootstrapping relied on tenant status never being checked — once enforcement was added, bootstrap had to start tenants `approved` (see above) or essentially every existing auth test would have broken. New coverage: `tests/test_auth_hardening.py` (suspended/pending login rejection, mid-session suspension, password-reset session revocation, idle timeout, real-mode configuration-error).

## ADR-033: Project Portfolio hardening — list search/filter/sort/pagination, metrics, deletion-guard fix, optional manager FK
**Status:** Decided — found during an audit against the original Project Portfolio Management build prompt

An audit against the original project-portfolio spec found the list screen had none of the explicitly-requested search/filter/sort/pagination, no project-level metrics were surfaced anywhere, the deletion guard was narrower than it looked (and had a latent bug), and the "Manager" field had no relational identity. Two other findings from that same audit were **not** acted on because they are already-documented, deliberate decisions, not gaps: Manager's tenant-wide list visibility (ADR-018, FR-PROJ-002's own acceptance criterion) and `region` being free text (resolved during Phase 3, see the bottom of `KNOWN_GAPS.md`).

**Decisions:**
- **List search/filter/sort/pagination**: `GET /projects` gained `search` (case-insensitive name substring), `domain`/`status`/`priority` (exact-match filters), `sort` (a whitelisted column name, optionally `-`-prefixed for descending), `page`/`page_size` (capped at 100). The response shape changed from a bare array to `{items, total}` — this matches the pagination envelope `API_SPECIFICATION.md` already documented for list endpoints generally but which nothing had actually implemented yet. This is a breaking change to `GET /projects`'s response shape; every caller in the frontend and test suite was updated in the same pass (`DefectsList.tsx`'s project-filter dropdown now requests `page_size=100` to populate a complete list, since a filter dropdown has no pagination UI of its own).
- **Project-level metrics**: `ProjectOut` gained `test_case_count`, `approved_test_case_count`, `test_run_count`, `open_defect_count`. Computed via one grouped `GROUP BY project_id` aggregate query per module (test cases, test runs, defects) across all projects in a list response, not a per-project query — avoiding N+1 for what could otherwise be an expensive list endpoint.
- **Deletion guard fix**: the existing guard only checked for test runs with `finished_at IS NULL`. Since `test_cases`/`test_runs`/`defects` all FK to `projects` with no `ON DELETE CASCADE` (deliberately — physically destroying test history/audit-relevant data is never safe), a project with *finished* runs or any test cases at all would pass the guard and then hit a raw, unhandled `IntegrityError` from Postgres on the actual `DELETE` — a real bug, not just a narrower-than-documented check, found while writing the test the original audit flagged as missing. Fixed by checking for the existence of any test cases, test runs, or defects (any status) before attempting the delete, raising a clean `ConflictError` instead.
- **`manager_user_id`**: `manager_name` remains a free-text field (CSV import, external/contracted managers who aren't system users, and existing data all depend on it staying optional and simple), but a new nullable `manager_user_id` FK to `users` was added alongside it, validated to belong to the tenant when supplied. The frontend's project form shows an optional "Linked manager account" picker; leaving it unset is normal and expected for a manager who isn't a tenant user.

Testing note: because `GET /projects`'s response shape changed, `tests/test_rls_isolation.py`'s cross-tenant list check and two assertions in `tests/test_projects.py` needed updating to read `response["items"]` instead of treating the response as a bare list — this is a mechanical consequence of the shape change, not a behavior regression.

**Status:** Decided — found during an audit against the original Test Case Management build prompt

An audit against the original Test Case Management spec found the "repository" half of the module (search/filter/sort/pagination) was entirely unbuilt despite solid versioning/lifecycle/RBAC underneath, plus several smaller gaps: no step reorder/duplicate UI, no version diff, a missing `description` field, a dead `assignee_id` column, an unreachable `deprecated` status, and — the one finding with real security relevance — no file-type validation on attachments at all.

**Decisions:**
- **Repository search/filter/sort/pagination**: `GET /projects/{id}/test-cases` gained `search`/`priority`/`status`/`assignee_id`/`sort`/`page`/`page_size`, returning `{items, total}` — the same pattern as ADR-033's Project Portfolio list (and the same breaking response-shape change, handled the same way: every caller in the frontend and test suite updated, including the bulk-import test which now asserts `total` rather than fetching all 2000 rows through a paginated endpoint).
- **Step reorder/duplicate**: both were already correctly supported at the data level — `_write_version`/the in-place-edit path renumber steps sequentially from whatever order the client submits, so reordering was always just a matter of resubmitting steps in a different order. Only the UI was missing. Added move-up/move-down (`useFieldArray.move`) and duplicate (`useFieldArray.insert`) buttons to `TestCaseForm.tsx`, plus an Enter-key-on-the-action-field shortcut that inserts a new blank step immediately below, for faster entry.
- **Version comparison**: added `GET /test-cases/{id}/versions/compare?from=X&to=Y`, computing a title/description-changed flag and a per-step diff keyed by `step_number` (since steps are never referenced by array index, ADR-002) with change types `unchanged`/`added`/`removed`/`modified`. The frontend's Version History card became clickable (expand-to-view that version's full content and author) with a Compare Versions picker rendering the diff color-coded inline.
- **`description`**: added to `test_case_versions` (not `test_cases`) — versioned alongside title/steps per ADR-003's immutable-snapshot model, so an edit to an approved case's description forks a new version exactly like a title or step change does, rather than being a side-channel mutable field that would undermine the "complete historical snapshot" guarantee.
- **Assignee wiring**: `assignee_id` already existed as a real FK but had no form field, list column, or filter in the UI — all three were added. No RBAC change was needed since assignment was always just a plain field, not a permission gate.

Terminal: deprecating an already-deprecated case is a 409, not a no-op, so a caller can't silently "succeed" against a case that's already retired.
- **Attachment file-type allowlist**: `attachment_service.upload_attachment` now rejects any file whose extension isn't in an explicit allowlist (images + common documents) before even reading the file size — checked by extension, not the client-supplied `Content-Type` header, which a malicious or careless client can set to anything. Testing note: as with ADR-033, the `GET /test-cases` response-shape change required updating `TestRunsList.tsx`'s approved-case picker (now requests `page_size=100` to populate a complete list for bundling into a run) and several existing test assertions across `test_test_cases.py` and `test_csv_import.py`.

## ADR-035: CSV import hardening — duplicate detection, row-count cap enforcement, downloadable error report, file validation
**Status:** Decided — found during an audit against the original CSV bulk import/export build prompt

An audit against the original CSV import spec found the core parsing/row-validation/RBAC logic solid and precisely matching the spec (header format, step encoding, per-row errors), but five named functionality/rule items were missing: duplicate detection, server-side enforcement of the 2,000-row cap, a downloadable error report, meaningful file validation, and three of the spec's eight named test scenarios.

**Decisions:**
- **Duplicate detection**: implemented in-service, not as a DB constraint. `import_test_cases` preloads `(project_id, lower(title))` pairs for every project referenced in the file and tracks a `seen_in_batch` map while processing rows, flagging a row whose title already exists in that project (in the DB, or earlier in the same file) as an error naming the conflicting row number. Deliberately scoped **per-project**, not tenant-wide (the same title in two different projects is normal, not a duplicate) and **not** promoted to a DB-level unique constraint the way `projects.name` has one — that would change the ordinary single-test-case creation path's behavior too, which the spec doesn't ask for and which could block legitimate same-titled cases in different test suites within a project.
- **Row-count cap**: `import_test_cases` now materializes the full row list before validating anything (`rows = list(reader)`), checks it against `settings.csv_import_max_rows` (2000), and rejects the whole import with a clear message if exceeded — before any project/user lookups or DB writes, so an oversized file never does partial work.
- **Downloadable error report**: implemented entirely client-side in `ImportDialog.tsx` — a "Download Error Report (CSV)" button builds a CSV blob from the `ImportReport.rows` the API already returned and triggers a browser download. No new backend endpoint, no persisted import-batch record: the report data was already in hand, and adding server-side file generation/storage for it would contradict ADR-021's deliberate synchronous, non-staged design.
- **File validation**: added three checks ahead of the existing UTF-8 decode check — a `.csv` extension requirement, an empty-file rejection, and a `csv_import_max_bytes` (5MB) size cap — all returning a clear `ValidationAppError` (422) before the upload is even parsed as CSV.
- **Test coverage**: added the three previously-missing named scenarios. Special characters: Unicode, emoji, embedded commas/quotes in both title and step fields, round-tripped through parse→store→retrieve. Concurrent imports: two real concurrent uploads (via `ThreadPoolExecutor`, two separate `TestClient` instances sharing the authenticated session cookie) against the same project with distinct titles, asserting both succeed independently and the final count is the exact sum — this checks for gross corruption/deadlocks under genuine concurrent access, not full database-isolation-level guarantees, which is adequate confidence for this deployment's scale.

Testing note: the existing bulk-import performance test (`test_bulk_import_2000_rows_under_2_5_seconds`, NFR 8.1) is pre-existing flaky infrastructure, not a consequence of this pass — confirmed by re-running it in isolation (passes consistently in under 1s) every time it failed under full-suite parallel load; left as-is per this project's standing discipline of not touching a passing/pre-existing test on a hunch.

## ADR-036: Test Execution Engine hardening — console context display, live timer, run editing/add-remove cases, assignment, pause/resume, a real concurrency bug fix
**Status:** Decided — found during an audit against the original Test Execution Engine build prompt

An audit against the original spec found the core verdict-rollup/version-pinning/timing logic correct, but the Execution Console displayed almost none of its named context fields, in-progress timing state was preserved server-side but never shown, runs were immutable after creation, the `assigned_to` column was unused, no run-level pause/resume existed, and the console had no keyboard shortcuts or sticky controls. Writing the concurrency test the audit flagged as missing also surfaced a genuine, previously-undiscovered race condition.

**Decisions:**
- **Console context**: added `GET /test-run-cases/{id}/context` returning run/project/case identity in one call (run name, project name, test case title, priority, version number, assignee), fetched alongside the existing steps query rather than folded into it, since the steps endpoint's shape is already relied on elsewhere and a stable, narrow context endpoint is easier to reason about than overloading it.
- **Live timer**: purely a frontend fix — `ExecutionStepOut.opened_at` was already returned by the API; the console simply never rendered an elapsed-time readout for the in-progress step. A `LiveElapsed` component now computes elapsed seconds from the server's `opened_at` and ticks every second, so a browser refresh correctly resumes showing accurate elapsed time rather than nothing.
- **Run editing / add-remove cases**: `PATCH /test-runs/{id}` is blocked once any run case has `started_at` set, matching the spec's own "before execution" qualifier precisely (not an arbitrary stricter or looser rule). Adding cases reuses the same approved-only/same-project validation as initial run creation (refactored into a shared `_validate_bundlable_cases`/`_bundle_case_into_run` pair). Removing a case is blocked if any of its steps have `opened_at` set, to avoid silently discarding recorded execution state — a case can be removed cleanly only if nothing has touched it yet.
- **Assignment**: `PATCH /test-run-cases/{id}/assign` validates the assignee belongs to the tenant (not necessarily the project — consistent with how `test_cases.assignee_id` is validated elsewhere) and is gated by `testrun.create` (the same authority tier that can create/edit runs), not a new permission.
- **Pause/resume**: scoped deliberately narrow, per the spec's own "where supported" qualifier. `test_runs.paused_at` (migration `b6c7d8e9f0a1`); `open_step`/`record_verdict` both reject with 409 while paused. Gated by `testrun.finish` (Admin/Manager only) rather than `testrun.create` (which Testers also hold) — pausing affects every participant on a run, not just the actor, so it's treated as the same tier of authority as finishing one. An explicit run-level "start execution" action was **not** added: the existing implicit-start-on-first-step-open semantics already work correctly and weren't independently identified as a gap worth inventing a new state transition for.
- **Keyboard shortcuts + sticky controls**: P/F/I keys act on the current step (disabled while the defect dialog is open, to avoid keystrokes leaking into its text inputs, or while the run is locked); the action buttons moved from inline-per-card to a `fixed` bottom bar showing the current step's action text, visible regardless of scroll position.
- **Concurrency bug found and fixed, not just documented**: `_recompute_run_case_status` (ADR-024) re-reads every step's verdict and overwrites `test_run_cases.status` from scratch on each call, with no locking. The new concurrency test — three verdicts submitted concurrently for three different steps of the same run case — exposed a real race: each transaction could read the verdicts list before the others' commits, and whichever committed last would overwrite the correct final status with one computed from its own stale read (observed directly: `passed_count` correctly showed 3, but `status` incorrectly stayed `in_progress`). Fixed with a `SELECT ... FOR UPDATE` lock on the run case before recomputing, serializing concurrent verdict submissions for the same case — the identical pattern already used for the MFA attempt-count race (GAP-17). This is a genuine correctness fix, not a test-environment artifact: confirmed by the test failing before the fix and passing after, run repeatedly.

## ADR-037: Defect Management hardening — visible Fail-time prepopulation, link-to-existing, evidence fields, history, traceability deep links, reporter/date filters, explicit close confirmation
**Status:** Decided — found during an audit against the original Defect Management build prompt

An audit against the original Defect Management/traceability spec found the lifecycle state machine, version pinning, and standalone/step-level creation all correctly implemented, but the Fail-time dialog showed nothing visually to the user (ids only), "link to existing defect" was backend-only with zero UI exposure, three named fields (Actual/Expected Result, Environment) didn't exist, there was no history/timeline, the defect detail page had no execution evidence or step-level navigation, filters were missing a reporter and date-range dimension, "closing requires verification confirmation" was satisfied only by the Verified status existing earlier in the sequence (no distinct gesture), and reverse navigation (test artifact → its defects) only existed at the step level inside the Execution Console.

**Decisions:**
- **Visible Fail-time prepopulation**: `ExecutionConsole.tsx` now builds a `FailedStepContext` (project/run/test-case names already available from the console's own context query, plus the failing step's number/action/expected) and passes it into the dialog, which renders a summary panel and an editable title input defaulting to the same auto-suggested string the backend already computed — the backend default is kept as a fallback (still applied if the client sends no title), but the user can now see and change it before submitting.
- **Link to existing defect**: the dialog gained a "Create New"/"Link Existing Defect" toggle; the existing mode lists open defects in the project (reusing `GET /defects?project_id=`) and calls the pre-existing `POST /defects/{id}/links` endpoint rather than adding a new one. The harder part was making a linked defect still show the 🐞 badge on the originating run: `list_defects(test_run_id=...)` was broadened with an `OR` against a `defect_links` subquery (defects linked to any execution_step belonging to that run), and the frontend now checks both `test_case_version_step_id` matches (direct creation) and `links[].linkable_id` matches (linked-in) when deciding whether a step already "has a defect."
- **Actual Result / Expected Result / Environment**: added as plain nullable columns (migration `c7d8e9f0a1b2`). `expected_result` defaults from the originating version-step's own `expected` text when the defect is created from a failed step and the field isn't explicitly overridden — the common case needs no retyping, but an unusual defect (e.g. the expected behavior itself was ambiguous) can still override it.
- **History**: no new table — `get_defect_history` filters the existing hash-chained `audit_logs` table by `entity_type='defect'`/`entity_id`, since every defect mutation already goes through `record_audit_event`. This mirrors the same "reuse audit_logs rather than add a parallel history table" decision already made for audit trails elsewhere in this system.
- **Execution evidence & deep traceability**: `DefectOut` now resolves the originating `execution_steps` row (verdict/timestamps/duration/executed-by) by joining `test_run_id`+`test_case_id`+`test_case_version_step_id` back through `test_run_cases` — these three together uniquely pin the row even though `execution_steps` has no direct FK back to `defects`. Also exposes `test_case_version_number` and `test_run_case_id`, letting the detail page link directly into the Execution Console at the exact failed step rather than only naming it as text.
- **Reporter/date filters**: no assignee column exists on defects (confirmed, not an oversight — only `reported_by`), so per the spec's own "where supported" qualifier, only a `reported_by` filter was added, alongside `created_from`/`created_to` date-range filters.

Frontend: a checkbox rendered only for the Closed transition, gating the same "Advance to" button rather than inventing a separate confirm dialog.
- **Reverse navigation**: added a `test_case_id` filter to `GET /defects` and a "Linked Defects" card to both `TestCaseDetail.tsx` and `TestRunDetail.tsx`.

## ADR-038: Dashboard and Reporting hardening — report filters, execution trends, pie/line charts, missing KPIs, compliance detail/print view, assignee disclosure
**Status:** Decided — found during an audit against the original Dashboard and Enterprise Reporting build prompt

An audit against the original Dashboard and Enterprise Reporting spec found the core aggregation logic (tenant/role scoping, no duplicate counting) correct, but seven named items missing or incomplete: no report filters existed at all on `/reports/aggregate`; no PDF and no print view existed — not even the browser-print-to-PDF fallback ADR-027 itself had promised; no Pie/Donut or Line chart existed and Execution Trends had no backing data; Active Projects, Approved Test Cases (count), Critical Defects, and per-domain Pass % were missing or buried in status-breakdown text instead of being explicit KPIs; the CSV compliance export lacked a Reporting Period header and had aggregate-only tables with no per-test-case/per-defect detail; "Assignee" grouping's per-metric meaning (set by ADR-027) was undisclosed in the UI; and the compliance export's numeric accuracy was untested against a known dataset.

**Decisions:**
- **"Active" project count**: defined as any project whose status is not `Completed` — the only status in the fixed BRD status set (`On Track`/`At Risk`/`Delayed`/`Completed`) that represents finished work, so this needed no new column or enum, only a `status != "Completed"` count over the data `get_dashboard_summary` already fetches.
- **Report filters compose via a filtered-subquery pattern, not per-metric bespoke WHERE clauses**: `get_aggregate_report`'s five metric branches each build structurally different base queries (different joins, different "value" columns). Rather than duplicating filter logic five times, every branch's base `select()` additionally labels `project_id`/`domain` (always present via the `Project` join), `tc_priority`/`tc_status` (`TestCase.priority`/`.status`, via an `outerjoin` for the two defect metrics since `Defect.test_case_id` is nullable), and a per-metric `created_at`. `project_id`/`domain` filter directly on the base select; the remaining four filters (`assignee_id`, `date_from`/`date_to`, `priority`, `status`) apply on a `.subquery()` wrapping it, before the final `GROUP BY`. A standalone defect (no `test_case_id`) is naturally excluded by a `priority`/`status` filter rather than erroring or being wrongly included, since the `outerjoin` leaves `tc_priority`/`tc_status` `NULL` for it.
- **New `test_case_status` metric, kept distinct from `run_status`**: the existing `run_status` metric (per ADR-027 decision #2) aggregates `test_run_cases.status` (`Passed`/`Failed`/`Pending`/`Blocked`), a different lifecycle from `test_cases.status` (`draft`/`ready_for_review`/`approved`/`deprecated`, ADR-001). Rather than overload `run_status` or relabel it, a genuinely new metric was added so both lifecycles remain independently reportable.
- **Execution Trends**: new `get_execution_trend` groups `ExecutionStep` verdicts by `func.date(closed_at)` over a trailing window (`func.make_interval` for the Postgres-native rolling cutoff), respecting the same tenant/role/project scoping as every other reporting query. Rendered as a `recharts` `LineChart` — the first line chart in the system — since a day-bucketed trend is the one reporting shape bar/pie can't represent well.
- **Print/PDF view finally completes ADR-027's deferred fallback**: ADR-027 decision #4 explicitly deferred "PDF is produced by the browser's native print-to-PDF against a print stylesheet, built when the Reporting screen's UI is implemented" — that promise was never kept until this pass. Rather than add a server-side PDF library (which ADR-027 explicitly rejected and this pass does not revisit), `get_compliance_report`/`compliance_report_to_csv` were split so the same structured report data backs both the existing CSV export and a new `GET /reports/compliance-detail` JSON endpoint; a new `/reporting/print` route (outside `AppShell`, so it renders full-bleed with no sidebar) consumes the JSON endpoint and renders tenant name/generation timestamp/reporting officer/reporting period/summary/detailed tables with `@media print` high-contrast styling and a `window.print()` button.
- **Assignee disclosure is a frontend-only fix**: the underlying per-metric "Assignee" semantics were already decided correctly in ADR-027 (test case's `assignee_id` for test-case/run metrics, `reported_by` for defect metrics) — only the UI never told the user which one applied. `Reporting.tsx` shows a one-line hint under the Group By control whenever "By Assignee" is selected, naming the exact dimension for the currently-selected metric; no backend change was needed.
- **No new migration**: every field added this pass (`active`, `approved_count`, `critical_count`, `pass_percentage`, execution-trend points, compliance detail rows) is computed at query time from existing columns — the first hardening pass in this project that needed none.

Testing note: 9 new tests were added to `test_reporting.py` covering active/approved/critical counts, per-domain pass percentage, the `test_case_status` metric, all 6 new aggregate filters, the execution-trend endpoint, and compliance detail/CSV numeric accuracy against the existing `_full_scenario` fixture — directly closing the audit's "compliance export's numeric accuracy untested" finding. All 8 pre-existing reporting tests needed zero changes, confirming the schema/service changes are additive, not breaking.

## ADR-039: System Administration and Audit Management hardening — audit detail/export/filters, self-service account history, reactivate control
**Status:** Decided — found during an audit against the original System Administration and Audit Management build prompt

An audit against the original spec found user CRUD, last-Admin protection, password reset with session revocation, all 11 named audit-engine recording sites, the audit record's 10-field shape at the DB/model level, DB-level `REVOKE` hardening, the SHA-256 hash chain, and the verify-chain endpoint all solidly implemented and matching prior ADRs (ADR-006, ADR-016, ADR-029). Six gaps remained: the `AuditLogOut` API response omitted `metadata` and `prev_hash` entirely, so an admin could never see what an entry actually recorded; there was no row-level detail/expand view; `/audit-logs` had no `entity_id` or date-range filter, and the backend's existing `user_id` filter wasn't exposed in the UI; there was no audit-log-specific export (only a derived compliance-summary CSV existed); users had no way to see their own account's history; and the Users & Roles screen had no control to reactivate a deactivated user, even though the backend already supported it via the same `PATCH` endpoint.

**Decisions:**
- **Return the full audit record, not a projection of it**: `AuditLogOut` already matched the BRD's 10-field shape at the DB/model level (ADR-006) — the gap was purely that the API response schema omitted `tenant_id`/`metadata`/`prev_hash`. Since "do not expose sensitive information in audit metadata" is already enforced at write time (`record_audit_event` call sites never pass passwords/tokens/hashes into `metadata`, confirmed by audit), there was no reason to keep metadata out of the read response — withholding it only hid legitimate investigative detail from the one UI surface built to show it. All three fields were added to the schema and to `audit_service._to_out`.
- **Audit-log filters compose the same way the aggregate-report filters do (ADR-038 precedent)**: `entity_id` and `date_from`/`date_to` were added alongside the existing `action`/`entity_type`/`user_id` params on `list_audit_logs`, factored into a shared `_build_filtered_query` helper reused by both the paginated list and the new CSV export, so the two surfaces can never drift out of sync on what "the same filters" means.
- **Export is a separate, uncapped-by-pagination endpoint, not a param on the list endpoint**: `GET /audit-logs/export` reuses the same filters and the same `audit.view` permission, but is deliberately not limited by `MAX_PAGE_SIZE` (capped instead at `EXPORT_ROW_CAP = 50_000` as a sanity ceiling) — a compliance export is a full-dataset dump for archival/review, not a UI page.
- **Self-service history needs no new permission, only a narrower query**: `GET /users/me/history` uses `get_current_context` (any authenticated session), not `require_permission("audit.view")`, because its query is hard-scoped to `entity_type="user", entity_id=ctx.user_id` — the caller can only ever see events recorded against their own account, which is strictly narrower than what `audit.view` already grants an Admin. This reuses the exact same `AuditLog` rows rather than a parallel table, consistent with how defect/entity history already works elsewhere in this system.
- **Self-service history legitimately includes the user's own login/MFA events, not just profile/role/password changes**: `auth_service` already records `auth.login_attempted`/`auth.mfa_verified`/`auth.logout` with `entity_type="user", entity_id=<the authenticating user>`. Rather than filter those out to keep the feature narrowly scoped to "account edits," they were kept — a personal activity history that excludes a user's own logins would be a strange, incomplete answer to "what happened to my account."
- **Reactivate is a one-line frontend addition, not a backend change**: `UserUpdateRequest.is_active` already accepted `true`, and `update_user`'s last-Admin guard only fires on demotion/deactivation, never on reactivation — so `UsersRoles.tsx` only needed a visible "Activate" button wired to the same `updateUser(id, {is_active: true})` call the role/deactivate controls already use.

Testing note: 6 new tests were added to `test_audit_api.py` (metadata/prev_hash in the response, entity_id + date-range filtering, CSV export contents, Tester forbidden from export, and self-service history scoping) plus one to `test_auth_flow.py` (reactivation via `PATCH .../is_active: true`, appended to the existing last-Admin-guard test). All pre-existing audit/auth tests needed zero changes. Live-verified against the real tenant, including an actual deactivate→reactivate cycle via the UI.

## ADR-040: Idempotency-Key dedup and project optimistic-concurrency version, as opt-in fixes for GAP-66/67/68
**Status:** Decided — a targeted fix pass against three findings from the QA engagement's security/reliability testing

The QA engagement (`Security_Test_Report.md`, `E2E_Test_Report.md`) found and deliberately left undecided three real gaps: file uploads were validated by extension only (no content-sniffing), no create endpoint had duplicate-submission protection, and a concurrent same-field `PATCH /projects/{id}` was a silent lost update. A follow-up request asked for GAP-66/67/68 specifically fixed (GAP-69, the performance findings, was left for separate investigation since it needs root-causing, not a code fix).

**Decisions:**
- **Content-sniffing is signature-based, not a new dependency.** Rather than add `python-magic` (a new runtime dependency with a system `libmagic` requirement that complicates the Docker image), `attachment_service.py` checks the first bytes of the upload against a small hardcoded table of real magic-byte signatures for every binary type already in the allowlist (PNG/JPEG/GIF/BMP/PDF/legacy-OLE .doc+.xls/ZIP-based .docx+.xlsx/WEBP), and a "looks like text" check (no NUL bytes, valid UTF-8) for .csv/.txt/.log, which have no fixed binary signature. This closes the specific attack the QA pass demonstrated (an ELF+shell-script payload disguised as `.txt`) without adding deployment complexity.
- **Idempotency is opt-in via a header, not a default dedup window.** A client-supplied `Idempotency-Key` header, checked against a new per-tenant-per-user-per-operation `idempotency_keys` table (`app/core/idempotency.py::with_idempotency`), returns the original entity on a repeat request with the same key. Omitting the header preserves the exact prior behavior (always creates a new record) — this was a deliberate choice to avoid silently changing the behavior of every existing caller that doesn't yet send the header (e.g. the frontend doesn't send one today; a future pass could add it to `apiFetch`'s POST calls for a true always-on guarantee). Applied to the three create endpoints the QA pass's finding named as likely affected by the same pattern: `POST /defects`, `POST /projects`, `POST /projects/{id}/test-cases`.
- **Idempotency-key recording needed a tenant-context re-assertion.** `create()` (the wrapped service call) commits its own transaction; since `app.current_tenant` (ADR-007's RLS GUC) is transaction-local, it resets after that commit, and the subsequent `INSERT INTO idempotency_keys` would otherwise run with no tenant context and fail its RLS `WITH CHECK` clause. `with_idempotency` re-asserts `set_tenant_context` before that insert.
- **Project optimistic concurrency is opt-in via `expected_version`, not a mandatory version on every PATCH.** `ProjectOut.version` (new integer column, incremented on every update) is always returned so a client *can* track it; `ProjectUpdateRequest.expected_version` is optional — a PATCH without it keeps the exact prior last-write-wins behavior. Supplying it makes a stale write a 409 instead of a silent loss. This is the standard optimistic-concurrency (ETag-like) pattern rather than mandatory pessimistic locking on every PATCH, since forcing every caller to track and send a version would be a breaking API change for a problem that (per the QA finding) only matters under genuine contention.
- **The `expected_version` check needed a row lock to actually be race-safe, not just a plain SELECT-then-compare.** A naive "read the project, compare `expected_version` to its `version` attribute, then update" is itself racy — two concurrent requests can both read `version=1` before either commits, both pass the check, and both overwrite (the exact bug being fixed, just moved one level up). `_get_project_or_404` gained a `for_update: bool = False` parameter; `update_project` passes `for_update=True`, taking a `SELECT...FOR UPDATE` row lock so a concurrent second request blocks until the first commits, then re-reads the now-current `version` under that lock and correctly 409s if it no longer matches. This mirrors the same `SELECT...FOR UPDATE` pattern already used for the two previously-fixed races (GAP-17 MFA attempt-count, GAP-49 run-case rollup) — the first time this codebase has applied it to a plain field edit rather than a recomputed aggregate.
- **A rollback-then-reference-the-expired-object bug was found and fixed while building the fix.** The 409 error path originally called `db.rollback()` (to release the row lock / discard the no-op transaction) and then referenced `project.version` again inside the exception message's f-string — but `db.rollback()` expires every object in the session, and SQLAlchemy's lazy-reload of that expired attribute ran in a now-tenant-context-less transaction, failing RLS and raising a confusing `ObjectDeletedError` instead of the intended 409. Fixed by capturing `current_version = project.version` into a local variable before the rollback.
- **Scoped to `projects` only, not generalized to every resource.** The QA finding was specifically demonstrated and tested against `projects`; the same `version`+`expected_version`+`for_update` pattern is not assumed to apply to test cases, defects, or other mutable resources without separately confirming the same lost-update class exists there (GAP-68's "Open" follow-up note).

Testing note: `test_reliability.py`'s three GAP-66/67/68 tests were updated in place to demonstrate the fix (the previously-documented "FINDING" tests now show both the fix working with the new opt-in mechanism, and the legacy no-header/no-version behavior preserved unchanged for backward compatibility) rather than duplicated into new files. `test_security_hardening.py`'s file-upload test was similarly updated from "documents the gap" to "confirms the fix," plus two new assertions (a genuine file with a matching extension is still accepted; the same bytes under a mismatched extension are rejected). Full regression: 225/225 backend tests passing (one pre-existing, confirmed-flaky-under-full-suite-load hash-chain-ordering test, unrelated to this fix, passes cleanly in isolation — same category as the already-documented CSV-import timing flake). `ruff`/`mypy` clean. Frontend unaffected (no UI surfaces the new header/field yet) — `typecheck`/`lint` confirmed clean, same pre-existing benign warnings.

## ADR-042: Phase 0 assessment for the AI-Powered QA Operations & Quality Intelligence Platform vision — no code changed, governance docs only

The user presented a large new directive positioning QTestHub as a commercially marketable, AI-enabled SaaS platform, spanning 11 new/expanded modules (Requirements Management, expanded AI-Powered QA Intelligence, Automation & CI/CD Integration, deeper Defect/QA Manager Intelligence, Test Assets, Collaboration & Workflow, an optional Insurance QA Pack, and Enterprise SaaS items beyond `SAAS_GAP_ANALYSIS.md`), with an explicit, twice-stated instruction: **begin with Phase 0 only** (read-only assessment), and **stop for approval before any Phase 1 implementation**. - **Two new authentication surfaces are flagged for a dedicated security review beyond normal functional testing**: the Automation/CI machine-auth plane (Phase 12) and SSO/SAML/OIDC (Phase 19) — both touch the auth layer directly and get the same route-discovery security-hardening sweep pattern already used elsewhere, applied to the new surface, as a named approval-gate condition rather than folded into regular phase testing.

## ADR-043: Phase 1 — tenant self-service settings, built directly on the existing `tenants` table (GAP-80 closed)

**Status:** Decided and implemented — first approved phase of the AI-Powered QA Operations & Quality Intelligence Platform roadmap.

The user approved `DEVELOPMENT_ROADMAP.md` as proposed and specifically "proceed with phase 1" (tenant settings infrastructure), alongside three other Phase 0 clarifications: Gemini as the AI provider for Phase 3+, both email and in-app channels for Phase 9's notifications, and SCIM (Phase 20) confirmed as needed. Only Phase 1 was implemented in this pass — the others are recorded as roadmap decisions for when their own phases start.

**Decisions:**
- **No new table, no JSONB settings blob.** `default_currency_code`/`default_timezone` already exist as real columns on `tenants`, set once at provisioning with no edit path, and are already read as new-project defaults (`project_service.py`). The actual gap was "no edit path," not "no storage" — so Phase 1 is a `GET/PATCH /api/v1/settings` pair operating directly on those existing columns, not a new settings table or an EAV/JSONB mechanism. This keeps faith with the project's established no-speculative-schema, no-custom-field-mechanism convention (the Collaboration & Workflow module, Phase 22, is where tenant-configurable/extensible fields are deliberately scoped, not here). Future settings-needing phases (AI credentials, notification preferences, branding) each get their own explicit typed column(s) on their own approval, rather than all competing for space in one generic blob.
- **New permission, not reuse of `user.manage`.** `tenant.settings.manage`, granted to Admin only, is a distinct permission from `user.manage` even though both are Admin-only today — settings and user management are conceptually different capabilities, and a future role model where they diverge (e.g., a finance-only settings role) shouldn't require retrofitting a shared permission.
- **Changes are audit-logged, not tracked via new `updated_at`/`updated_by` columns on `tenants`.** The existing hash-chained audit log (`entity_type="tenant"`, `entity_id=tenant_id`, action `tenant.settings_updated`, metadata recording the from/to per changed field) already answers "who changed what and when" — adding redundant tracking columns to `tenants` itself would duplicate information the audit log already owns, consistent with how Defect History (ADR-037) and the self-service "My Account" history page (ADR-039) both reuse the same audit log rather than building bespoke per-entity history columns.
- **Partial updates preserve untouched fields exactly** — `TenantSettingsUpdateRequest`'s fields are both optional; omitting one leaves it unchanged (tested explicitly), matching the same "opt-in doesn't change existing behavior" principle used for `Idempotency-Key` and `expected_version` (ADR-040).
- **A real bug surfaced in the first implementation and was fixed the same way as the earlier `ObjectDeletedError` (ADR-040's project version-check bug)**: calling `db.commit()` to persist the `tenants` row update before calling `record_audit_event` reset the transaction-local `app.current_tenant` RLS GUC (commit resets it, not just rollback), so the subsequent audit-log INSERT failed with "new row violates row-level security policy." Fixed by reordering: mutate the tenant row, call `record_audit_event` (which only flushes, not commits) within the same transaction, then commit once at the end — one transaction, one GUC lifetime, no reset in between. This is the third time this exact GUC-reset-on-commit subtlety has caused a bug this project (idempotency-key INSERT, project optimistic-concurrency re-read, now this) — worth remembering for every future phase that mutates a row and writes an audit entry in the same request.

Testing: 5 new backend tests (`test_settings.py`: read/update happy path, invalid-currency-code validation rejection, partial-update-preserves-other-field, non-Admin 403 on both GET and PATCH, tenant isolation + audit-log-content assertion). Full backend regression: 233/234 passing — the one failure (`test_bulk_import_2000_rows_under_2_5_seconds`) is the already-documented GAP-69 timing flake, unrelated to this change. Frontend: `typecheck`/`lint`/`build`/unit tests clean, same 3 pre-existing benign lint warnings, no new ones (an initial draft introduced a `set-state-in-effect` warning populating form fields from the query response — fixed by extracting a child `SettingsForm` component that takes the fetched settings as a prop and initializes its local state directly, rather than syncing via `useEffect`, the same pattern already used for the AppShell mobile-nav-close fix in ADR-041). Live-verified via Playwright against a freshly bootstrapped tenant: Admin sees and edits the real default values, a save persists across reload, and a Tester gets no "Settings" nav item and a 403 if they hit the API directly. Full Playwright regression: 10/11 passing — the one failure (`journey3-test-execution.spec.ts`'s `getByText('failed')` strict-mode collision) is the already-documented pre-existing flake, confirmed unrelated by rerunning in isolation with the same result.

## ADR-044: Phase 2 — Requirements Management foundation, mirroring TestCase's shape but without an approval workflow (GAP-71 closed)

**Status:** Decided and implemented — second approved phase of the AI-Powered QA Operations & Quality Intelligence Platform roadmap.

**Decisions:**
- **`Requirement`/`RequirementVersion` mirror `TestCase`/`TestCaseVersion`'s model shape** (denormalized title + `current_version_id` pointer on the parent, immutable version snapshots) — same proven pattern (ADR-001/ADR-003), not a new design. The one deliberate divergence: **no draft/approved workflow**. TestCase's edit logic branches on status (ADR-020: approved edits fork a new version and revert to draft; draft edits mutate in place) because test cases have an execution-readiness gate to protect. Requirements have no equivalent concept in the vision document, so every edit unconditionally forks a new version — simpler code, and doesn't invent a workflow nobody asked for.
- **Requirement↔TestCase linking is a many-to-many join table (`requirement_test_case_links`) keyed on the requirement itself, not a specific version.** Coverage asks "does this requirement have a test case," not "does this exact wording of it" — versioning the link would be over-engineering for a Phase 2 foundation with no stated need for point-in-time coverage snapshots.
- **New `requirement.manage` permission, granted to Admin and Manager only** (not Tester, unlike `testcase.create`/`testcase.edit` which all three roles hold). Requirements are traditionally BA/PM-owned authoring, and the vision document gives no reason to extend authorship to Testers the way test-case authoring already is. Viewing follows the existing test-case visibility rule unchanged (project-scoped access check inside the service, not gated by the new permission) — a Tester assigned to the project can see requirements and coverage, just not create/edit/link them.
- **Coverage computation lives in `requirement_service.py`, not `reporting_service.py`** — despite the roadmap's own phrasing suggesting the latter. The computation is a straightforward per-project count over the new linking table with no shared logic with the existing reporting engine's aggregate/groupby machinery; routing it through `reporting_service.py` would have meant an import-only pass-through for no real benefit. Revisit if a future phase needs coverage folded into the existing Aggregate Report or compliance export.
- **No cross-project Requirements overview page**, matching the same judgment already made for Test Cases (which has no cross-project list outside the merge-client-side Test Repository). A `/projects/{id}/requirements` page reached from Project Detail is enough for Phase 2's stated scope; a cross-project rollup can be added later if real usage shows it's needed, following the same `useQueries`-per-project merge pattern already used for Test Repository/Test Runs/Execution Overview.
- **No new Requirements item in `AppShell`'s sidebar** — it's a project-scoped page, same as Test Cases, reached via Project Detail's action row, not the global nav.

## ADR-045: Phase 3 — AI Test Case Generator, provider-agnostic abstraction with a first Gemini implementation (GAP-72 partially closed)

**Status:** Decided and implemented — third approved phase of the AI-Powered QA Operations & Quality Intelligence Platform roadmap, and the first of the three sequenced AI capabilities the user's note commits to (generation → review → impact analysis).

**Decisions:**
- **Provider-agnostic interface, not a direct Gemini SDK dependency.** `app/core/ai/base.py` defines `AIProvider` (one method: `generate_test_cases`) and plain dataclasses (`GeneratedTestCase`/`GeneratedStep`/`AIGenerationResult`); `app/core/ai/registry.py` maps a provider name string to a concrete instance. The service layer (`ai_service.py`) calls only this abstraction. `GeminiProvider` is the only concrete implementation today, built against Gemini's plain REST `generateContent` endpoint via `httpx` rather than the `google-generativeai` SDK — one fewer heavyweight dependency, and the REST shape (JSON in, JSON out, a documented `responseSchema` for structured output) is simple enough that the SDK buys nothing here. Swapping or adding a provider later means writing one new class and registering it, not touching `ai_service.py` or any API route.
- **Reuses Phase 1's tenant-settings mechanism for AI config, exactly as `DEVELOPMENT_ROADMAP.md` Phase 3 specified.** `tenants` gained three columns (`ai_enabled`, `ai_provider`, `ai_api_key_encrypted`) rather than a new table — same no-new-table, no-JSONB-blob judgment as ADR-043. `GET/PATCH /api/v1/settings` was extended (not replaced) with the new fields, gated by the same existing `tenant.settings.manage` permission; no new permission was introduced for settings management.
- **The API key is Fernet-encrypted at rest (`app/core/crypto.py`), keyed by a new `AI_CREDENTIAL_ENCRYPTION_KEY` env var, and is write-only at the API boundary.** `TenantSettingsUpdateRequest.ai_api_key` accepts the plaintext key (or `""` to clear it) but `TenantSettingsOut` only ever exposes `ai_api_key_configured: bool` — the ciphertext itself, let alone the plaintext, is never returned by any response, matching the project's existing convention of never echoing secrets back (passwords are hashed and never re-serialized either). Clearing the only configured key auto-disables `ai_enabled` in the same request (unless that request also explicitly sets `ai_enabled`), so a tenant can't be left "enabled" with nothing to call.
- **Generating draft test cases reuses the exact same project-access authorization as manually creating one** (`_require_project_access`/`is_assigned`, ADR-019) — Admin/Manager tenant-wide, Tester must be assigned. No new permission was invented for this action: an AI-assisted draft is not a different kind of authorship than a typed-in one, so it shouldn't need a different gate. Enabling/disabling AI and managing the key, by contrast, stays Admin-only via `tenant.settings.manage` — that's tenant configuration, not authorship.
- **The draft-not-published invariant is structural, not a new status value.** `generate_test_cases_for_requirement` calls the exact same `test_case_service.create_test_case` that manual creation uses, so every generated case starts at `status="draft"` through the same code path, then gets linked to the requirement via the existing `requirement_service.link_test_case`. There was no temptation to add an "ai_generated" flag or a different creation path — reusing the real creation function means the draft/review/approve workflow (ADR-020) applies identically regardless of who or what authored the first version.
- **Prompt-injection resistance is structural, not purely prompt engineering.** The requirement's title/description are delimited inside an explicit `<requirement>...</requirement>` block in the prompt, with an instruction telling the model to treat that content as data to write tests for, never as instructions to follow (tested directly in `test_gemini_provider.py`, which asserts the delimiters and the instruction text, not model behavior — an LLM prompt can't be unit-tested for "did it obey," only for "was it told correctly"). The actual backstop is architectural: even a fully successful injection can only ever produce a `draft` test case through the same creation path everything else uses, which a human must still review and approve — it cannot escalate privilege, bypass review, or execute anything, because nothing in this feature gives model output any authority beyond "proposed draft content."
- **Usage/token metering is a dedicated `ai_usage_logs` table, not reuse of the general audit log.** Each AI call writes one row (tenant, user, provider, action, optional requirement, prompt/completion/total token counts, success/failure) regardless of outcome — a failed provider call is metered too, at zero tokens, so usage reporting isn't silently blind to errors. `GET /ai/usage` (Admin-only, same `tenant.settings.manage` permission) returns a simple aggregate summary; a full per-call log view was judged unnecessary scope for this phase and can be added later if needed.
- **AI-disabled is the default and fully inert.** A tenant that never touches AI settings has `ai_enabled=False`, and the generate endpoint fails closed with a 409 rather than silently no-op'ing — core test management, execution, reporting, and traceability are completely unaffected (verified directly: `test_ai_disabled_core_test_case_creation_is_unaffected` exercises ordinary manual test-case creation on a tenant that never enabled AI).

Testing: 5 new Gemini-provider unit tests (`test_gemini_provider.py`, via `httpx`'s own `MockTransport`-equivalent monkeypatch — no real network call to Gemini: prompt delimiting/injection-instruction assertion, successful parse incl. usage metadata, non-200 handling, malformed-JSON handling, unexpected-shape handling, max-cases truncation) plus 7 new service/API tests (`test_ai.py`, with the provider swapped for a deterministic `FakeProvider` via monkeypatch: AI-disabled 409, successful generation creates linked draft test cases, usage metered on both success and provider failure, Tester-without-membership 403, AI-disabled path leaves manual test-case creation unaffected, usage tenant isolation) plus 4 extended `test_settings.py` cases (enabling without a key rejected, setting a key then enabling succeeds with the key never appearing in any response body, clearing the key auto-disables AI). Full backend regression and live Playwright/Docker verification recorded in `IMPLEMENTATION_STATUS.md`.

## ADR-046: Phase 4 — AI Test Case Reviewer, reusing Phase 3's provider layer (GAP-72 further closed); plus a real audit hash-chain tiebreak bug found and fixed

**Status:** Decided and implemented — fourth approved phase of the AI-Powered QA Operations & Quality Intelligence Platform roadmap, and the second of the three sequenced AI capabilities.

**Decisions:**
- **Reuses Phase 3's `AIProvider` interface rather than introducing a second one.** `generate_test_cases` and the new `review_test_case` are both abstract methods on the same `AIProvider` (`app/core/ai/base.py`); `GeminiProvider` implements both against the same REST pattern, sharing a new `_call_gemini` helper for the request/parse/usage-extraction plumbing that both methods need (extracted during this phase — it was duplicated between the two methods until refactored out). A second AI capability was the first real test of whether the Phase 3 abstraction generalizes, and it did: no changes were needed to `registry.py` or to how `ai_service.py` obtains a provider.
- **Strictly read-only — the no-auto-mutation invariant is structural, not a policy note.** `review_test_case` never calls any test-case mutation function; it only reads the case (`test_case_service.get_test_case` + `to_out`) and returns suggestions. There is no "apply suggestion" endpoint or button — a human reads the suggestion and edits the test case themselves through the existing edit flow, same as reading a code review comment. Verified directly: `test_review_returns_suggestions_and_does_not_mutate_the_test_case` snapshots the test case before and after a review call and asserts byte-for-byte equality.
- **Authorization reuses view-level access (`test_case_service.get_test_case`'s existing project-visibility check), not the create/edit permission.** Requesting a review doesn't change anything, so it shouldn't need more privilege than viewing the case already requires — an assigned Tester can request a review even in projects where only Admin/Manager can approve, consistent with "read access implies you can ask AI about what you can already read."
- **Same prompt-delimiting injection mitigation as Phase 3, applied to test-case content instead of requirement content** (`<test_case>...</test_case>` tags + an explicit "treat as data" instruction in `_build_review_prompt`), with the same structural backstop: a successful injection could at most produce a misleading suggestion string, which a human reads and can ignore — it has no path to mutate anything, unlike generation's drafts which at least enter the normal review workflow.
- **Usage metering reuses the existing `ai_usage_logs` table and `_record_usage` helper**, now parameterized by `action` (`generate_test_cases` vs. `review_test_case`) rather than hardcoded, so `GET /ai/usage`'s aggregate summary already covers both capabilities with no changes needed.
- **No new permission, no schema migration.** This phase is the cheapest so far in the roadmap: `ai_usage_logs.requirement_id` is already nullable (a review has no requirement to attach to), and reuse of existing view-level access meant no new `role_permissions` seeding was needed.
- **A real, pre-existing bug was found and fixed during this phase's full-regression run, unrelated to any AI code**: `test_audit_api.py::test_verify_chain_reports_valid_for_untampered_log` failed intermittently under full-suite load (reproducible: passed 5/5 in isolation, failed under the full ~280-test run). Root cause: `record_audit_event`'s `prev_hash` lookup (`app/core/audit.py`) ordered candidate rows by `created_at DESC` with no tiebreaker, while `verify_chain` (`app/services/audit_service.py`) walks rows ordered by `(created_at, id)`. `created_at` is computed in Python before the insert (not a DB-generated timestamp), so two audit events written in very close succession can tie; under a tie, Postgres's row order for the untiebroken query is unspecified and can disagree with the tiebroken walk order used by `verify_chain` — which looks exactly like tamper/corruption even though nothing was tampered. Fixed by adding the same `id` tiebreaker to the write-time query (`.order_by(AuditLog.created_at.desc(), AuditLog.id.desc())`), so the two queries are now guaranteed to agree on ordering regardless of timestamp ties. This is unrelated to this phase's actual feature work (no AI file touches `audit.py`/`audit_service.py`), but surfaced while verifying this phase and was safe and small enough to fix in place rather than deferring to a new gap entry for a correctness bug in a security-relevant feature (the hash chain).

Testing: 2 new Gemini-provider unit tests added to `test_gemini_provider.py` plus 2 more extending coverage (prompt delimiting/injection-instruction assertion for the review prompt, successful parse incl. usage metadata, empty-suggestions case, non-200 handling) and 6 new service/API tests in `test_ai.py` (AI-disabled 409, suggestions returned with the before/after no-mutation assertion, usage metered on success and provider failure, Tester-without-membership 403, Tester-with-membership succeeds via view-level access). Full backend regression (after the audit tiebreak fix): 280/281 passing — the one failure (`test_bulk_import_2000_rows_under_2_5_seconds`) is the already-documented GAP-69 timing flake, unrelated. Frontend: `typecheck`/`lint`/`build`/unit tests clean, no new lint warnings. Live Playwright/Docker verification recorded in `IMPLEMENTATION_STATUS.md`.

This is a deliberate asymmetry from the other two capabilities (which always call the provider once invoked): there is a genuinely free, always-correct answer here ("no test cases to flag") that doesn't need a model's opinion.

Verified directly: a before/after snapshot of both the requirement and a linked test case around an analysis call asserts byte-for-byte equality.
- **Authorization reuses the existing requirement view-level access** (`requirement_service.get_requirement`'s project-visibility check), not `requirement.manage` — consistent with Phase 4's reasoning that read-only AI assistance needs no more privilege than the read it's assisting.
- **Usage metering reuses the same `ai_usage_logs` table and `GET /ai/usage` endpoint** under a third `action` value (`analyze_requirement_change`); no new table, no new permission, no schema migration — the cheapest phase in the roadmap so far, matching Phase 4's trend.

## ADR-048: Phase 6 — Defect Intelligence additive analytics: root cause, aging/SLA, trend (GAP-77's additive portion closed)

**Status:** Decided and implemented — sixth approved phase of the overall roadmap, and the first phase of Release 2 (defect/QA intelligence, test assets, automation foundation), which has no AI dependency.

**Decisions:**
- **Root cause is a fixed, simple taxonomy** (`requirements_gap`, `code_defect`, `design_flaw`, `test_data_issue`, `environment_issue`, `third_party_integration`, `other`), nullable on `Defect`, settable at any time via a new `PATCH /defects/{id}/root-cause` — not required at creation, since the actual root cause is usually unknown until investigation happens. No new permission: setting it reuses the exact same project-access check as `update_status`/`add_link`, since it's classification metadata, not a workflow gate. A `defect_root_cause` audit action records the from/to, consistent with how every other defect mutation is tracked.
- **Aging/SLA-breach is computed, not stored.** A fixed `SLA_DAYS_BY_SEVERITY` budget (Critical: 2 days, High: 5, Medium: 10, Low: 20) lives in `defect_service.py` as a plain constant — not a tenant-configurable table. Tenant-configurable thresholds belong with Phase 22's broader tenant-configurable-taxonomy work; introducing a second, narrower configuration mechanism here would be exactly the kind of premature generalization this project's conventions reject. `compute_aging(defect)` returns `(age_days, sla_breached)` from `created_at`/`closed_at`/`severity` alone, with no new columns, and is called both per-defect (every `DefectOut` now carries `age_days`/`sla_breached`, so every existing list/detail view gets this for free) and in aggregate (`GET /reports/defect-aging`, a per-severity open/breached bucket summary for currently-open defects, reusing `reporting_service.py`'s existing accessible-project scoping).
- **`age_days`/`sla_breached` measure the full lifecycle, not just "still open" overdue-ness.** For an open defect, age is time-since-reported; for a closed one, age is time-to-close. `sla_breached` flags either case exceeding budget — a currently-overdue open defect, or a closed one that took longer than its budget to resolve. This is more informative than only flagging live overdue defects, and required no extra branching since `compute_aging` already has both timestamps.
- **Defect trend reuses `get_execution_trend`'s exact shape** (`GET /reports/defect-trend`, daily counts over a trailing window, optional `project_id`) — opened-count from `created_at`, closed-count from `closed_at`, each a separate grouped query unioned by date in Python. This mirrors an already-proven pattern rather than inventing a new one for a structurally identical problem (two time-series counts instead of three).
- **`defect_root_cause` is a fourth value on the existing `Metric` enum for `GET /reports/aggregate`**, not a dedicated endpoint — it shares all the existing filter/group-by machinery (project/domain/assignee, date range, priority/status) for free, consistent with `defect_severity`/`defect_status` already being metrics on the same enum rather than separate endpoints. A `NULL` root cause groups as `"uncategorized"` (via `COALESCE` in the query) rather than vanishing from the report, so an uncategorized backlog is visible, not silently excluded.
- **No new table, no new permission, no schema change beyond one nullable column.** This is the cheapest phase in the roadmap after Phases 4/5 — true to the roadmap's own framing of Phase 6 as "additive analytics."
- **Explicitly out of scope, per the roadmap's own phase boundary**: duplicate-defect similarity detection (PV-6.1) and external tracker sync (PV-6.6) were not touched — they're not listed in this phase's PV references. Reopened-defect analysis (PV-6.3) remains deliberately deferred to Phase 13, since it requires reversing ADR-026's forward-only status constraint, a real design decision that needs its own explicit sign-off, not just an analytics addition.

## ADR-051: Phase 9 — Real notifications, three bounded trigger events (GAP-74's notifications sub-item closed)

**Status:** Decided and implemented — ninth approved phase of the overall roadmap, fourth phase of Release 2, replacing `NotificationBell.tsx`'s honest placeholder with a real backend per the user's earlier confirmed decision ("both email and in-app channels, not email-only").

**Decisions:**
- **Three bounded trigger events, not a generic configurable-notification-rules engine**: a comment @-mention (Phase 8's new capability — the obvious first trigger), a test case being assigned to you, and a defect you reported being closed. The roadmap's own PV-9.2 text doesn't enumerate specific triggers, and building a rules engine (subscribe to arbitrary event types, per-user notification preferences) is a much larger, unrequested feature. These three cover the clearest "someone needs to know about this" moments already present in the product, and more triggers can be added the same way later without a redesign.
- **Email delivery reuses MFA's exact simulated/real pattern (ADR-032), not a new delivery abstraction.** A new `notification_email_delivery_mode` setting mirrors `mfa_delivery_mode`: `"simulated"` (default outside production) only writes the in-app row; `"real"` also sends via the same SMTP settings MFA already uses, failing loudly (`ConfigurationError`, surfaced as a 500) if SMTP isn't configured rather than silently dropping the email — the identical trade-off ADR-032 already made and tests already proved out for MFA codes.
- **`notify()` is called synchronously, inline in the same transaction as the triggering action** (right alongside `record_audit_event`, before the caller's own `db.commit()`) — not queued to a background worker. This project has no task queue, and three low-volume, non-urgent notification types don't justify introducing one; the in-app row and the triggering action either both commit or both roll back together, which is the simpler and more correct invariant for this scope. Email sending happens inside that same window, which is a small timing imperfection shared with the "real" risk window already accepted for MFA fail-loud errors — acceptable here for the same reason.
- **Never self-notifies.** `notify()` takes an `actor_user_id` and silently no-ops if the recipient is the actor — mentioning yourself, assigning a test case to yourself, or closing your own reported defect produces no notification. This needed no special-casing per trigger site; it's centralized in `notify()` itself.
- **No new permission.** `GET /notifications`, `GET /notifications/unread-count`, `PATCH /notifications/{id}/read`, and `POST /notifications/mark-all-read` are all scoped to `recipient_id == ctx.user_id` inside the service — a notification is inherently private to its recipient, not something any permission grants broader access to. Marking another user's notification as read 404s (the row simply isn't found when queried under your own `recipient_id`), not 403 — consistent with not leaking whether a given notification id exists for someone else.
- **In-app delivery doesn't gate on project membership**, by design. `notify()` fires independent of whether the recipient can currently see the triggering entity (e.g. assigning a test case to someone not yet on the project still notifies them) — membership is a separate, pre-existing concern (`_require_project_access`) that the notification's own entity link will enforce if/when they click through. This avoids coupling two independent access concepts.
- **Frontend: `NotificationBell.tsx` polls on a 30s interval** (`refetchInterval`) rather than a push channel (WebSocket/SSE) — the simplest thing that satisfies "real notifications," with nothing in scope asking for live push delivery. The unread-count badge and the notification list are separate queries (count always polls; the list only fetches once the bell is opened), so the common case (closed bell) stays cheap. Clicking a notification marks it read and, for `test_case`/`defect` entity types, navigates to the owning entity's detail page; `execution_step` notifications show as plain text with no link, since an execution step has no detail route of its own independent of the run-case id the notification doesn't carry — a minor, documented limitation rather than inventing an extra lookup to resolve one.

## ADR-052: Tier 0 — Production readiness (backup/restore, production Docker, platform-admin hardening, rate-limit expansion, structured logging/error monitoring, documentation re-sync)

**Status:** Decided and implemented — the first tier of the post-audit remediation plan (`docs/DEVELOPMENT_ROADMAP.md`'s Tier 0), triggered by the 2026-11-10 implementation audit (`docs/audit/`) finding "no artifact that could be deployed to a real environment at all" and several other Critical/High operational gaps. Unlike prior ADRs, this one bundles six previously-separate roadmap items because the user explicitly asked for Tier 0 "completely," as one pass, expanded by a pasted 16-item production-readiness checklist.

**Decisions:**
- **Database backup & restore is plain `pg_dump`/`pg_restore` shell scripts (`scripts/db_backup.sh`, `scripts/db_restore.sh`), not a managed-service integration.** The approved stack has no managed Postgres provider named yet, so scripting against the owner role directly (parameterized entirely by env vars, no embedded credentials) is the only thing that can be verified today; a future managed-backup integration (e.g. a cloud provider's snapshot API) can replace the script's internals without changing the operational runbook around it. Attachment files (`ADR-012`'s on-disk storage, no object storage yet per the audit's finding #3) are backed up as a parallel `tar` of the `attachments_dir` volume, documented alongside the DB dump in the same runbook, not folded into the same script — they have different restore semantics (file tree vs. SQL replay) and different retention needs.
- **Production frontend build is a real multi-stage Docker build** (`node:22-alpine` → `npm run build` → `nginx:alpine` serving `dist/`), replacing the dev-server-only `CMD npm run dev` the audit flagged as meaning no deployable frontend artifact existed at all. The nginx config inside that stage handles SPA fallback routing and proxies `/api/` to the backend service by container DNS name, so the same compose file works whether or not an additional reverse-proxy layer sits in front of it.
- **A documented, cert-mountable nginx reverse-proxy config is provided for HTTPS termination; ACME/Let's Encrypt automation is deliberately NOT implemented.** Automating certificate issuance needs a real, owned domain this engagement doesn't have — scripting against one that doesn't exist would be unverifiable. The provided config documents exactly where a cert/key pair (from certbot or any CA) mounts in, which is the actual decision point a real deployment needs, without fabricating a domain-specific automation step nobody can run.
- **`docker-compose.prod.yml` is a new, separate file alongside the existing dev `docker-compose.yml`, not a profile/override on it.** The dev compose file's job (fast rebuilds, `npm run dev`, exposed Postgres port, no reverse proxy) and the prod file's job (built artifacts, internal-only DB, healthchecked restart policy, a proxy layer) differ enough that an overlay would need to override most of the dev file's settings anyway; a second, independently-readable file is clearer for an operator who only ever needs to reason about one of the two.
- **Explicit SQLAlchemy connection-pool settings (`pool_size`, `max_overflow`, `pool_timeout`, `pool_recycle`) were added to `app/core/config.py`/`db.py`, defaulted to SQLAlchemy's own built-in defaults.** This is additive-only: dev/test behavior is unchanged (same defaults as before, when nothing was set explicitly), and a prod deployment can now actually tune pool sizing to its real concurrency instead of inheriting whatever SQLAlchemy ships with by accident.
- **Platform-admin hardening is a pragmatic hardening pass on the existing HTTP Basic plane, NOT a full replacement with a session+MFA flow.** A full replacement was investigated and rejected for this tier: it would need a new non-tenant-scoped `PlatformSession`/`PlatformMfaChallenge` model pair (the existing `Session`/`MfaChallenge` are `TenantScopedMixin`-RLS-protected and platform admins have no tenant), a rewrite of the real frontend flow (`PlatformAdmin.tsx`/`platformAdmin.ts` currently hold credentials in React state and resend them via Basic auth on every call, with no login/session concept at all), and mechanical edits across 23 call sites in 20 backend test files that authenticate platform actions with `auth=(platform_admin["email"], platform_admin["password"])`. That is out of proportion for a Tier 0 pass whose other five items are comparatively cheap, and the pragmatic hardening below closes the actual findings the audit cited (no lockout, no attribution, no throttling) without that blast radius. A future phase can still do the full replacement; this ADR's hybrid is the interim, auditable state, not a final one.
  - **Brute-force lockout** on `platform_admins` itself (`failed_login_count`/`locked_until` columns, migration `b7c8d9e0f1a2`) rather than a new session table: 5 consecutive failures locks the account for 15 minutes (both configurable), mirroring the spirit of the existing tenant MFA challenge's `attempt_count` without needing a new identity plane.
  - **Rate limiting** (`60/minute`, uniformly across all `/platform/*` routes) added via the same `slowapi` limiter GAP-16 already established for `/auth/login` (`10/minute` there) — applied to the shared `require_platform_admin` dependency itself, not a `@limiter.limit` decorator on each route function, since FastAPI resolves a route's `Depends()` parameters (this one included) before ever calling the route function body; a decorator on the route function never gets a chance to block a request this dependency already rejects with 401. The cap is looser than login's because this dependency also gates the read-only tenant list (re-polled by the frontend after every mutation) and because live verification surfaced that a tight 10/minute cap left near-zero headroom for this project's own Playwright regression suite, whose `bootstrapTenant` fixture calls the create-tenant route once per spec file — two consecutive full suite runs within the same window tripped 429s on otherwise-passing specs. The per-admin lockout above is the primary brute-force defense on this plane; this rate limit is supplementary, so the looser cap doesn't meaningfully weaken it.
  - **Audit attribution fixed**: `audit_logs` gained a nullable `platform_admin_id` FK (migration `b7c8d9e0f1a2`) alongside the existing nullable `user_id`, rather than widening `user_id`'s FK target — platform admins and tenant users are deliberately separate identities (ADR-008), and a row should be attributable to exactly one of them. `platform_service.py`'s `tenant.created`/`tenant.status_changed` events now carry the real admin's id instead of `user_id=None` with no attribution at all. This changes the audit hash-chain's canonical payload shape (adds a `platform_admin_id` key, always present, null or not) — safe to do now since the audit itself confirmed no real production tenant data exists yet to have pre-existing chains computed under the old payload shape.
- **Rate limiting expanded to CSV import (`10/minute`) and all three attachment-upload routes (`30/minute`)** — the other write-heavy/resource-intensive endpoints the audit's finding #8 named as uncovered (previously only `/auth/login` and `/auth/mfa/verify` were limited).
- **Structured logging is plain stdlib `logging` with a custom `JsonFormatter`, not a third-party structured-logging library.** One JSON object per line (timestamp, level, logger, message, plus a `request_id` when bound) is all finding #7 actually needed; pulling in `structlog` or similar for a single formatter class would be an unrequested dependency. The correlation id is propagated via a `contextvars.ContextVar` set by a new outermost `correlation_id` ASGI middleware in `app/main.py` (honoring an incoming `X-Request-ID` header if present, generating one otherwise, and echoing it back on the response) — read by the formatter at log-emit time so no call site needs to thread it through explicitly.
- **Error monitoring is an optional Sentry integration, strictly off unless `SENTRY_DSN` is set**, matching the existing fail-quiet-when-unconfigured convention (distinct from `smtp_host`'s *fail-loud* convention, since losing error reporting is a lesser risk than silently not sending an MFA code) — `sentry_sdk.init()` is skipped entirely in dev/test, so no behavior changes for any existing test.
- **Documentation re-sync applies the audit's own identified stale-label corrections** (`PRODUCT_VISION.md` PV-9.7, several `SAAS_REQUIREMENTS.md`/`SAAS_GAP_ANALYSIS.md` items the audit itself upgraded after direct code verification, `REQUIREMENT_TRACEABILITY.md`'s stale BR-01/BR-03 "backend only" suffix) and adds three new operator-facing documents (`docs/PRODUCTION_DEPLOYMENT_GUIDE.md`, `docs/ADMINISTRATOR_GUIDE.md`, `docs/USER_GUIDE.md`) that did not exist before this tier, per the pasted production-readiness checklist's explicit deliverables list.

## ADR-053: Tier 1 — SaaS commercial foundations (subscription schema, user-invite flow, background job queue, pluggable attachment storage)

**Status:** Decided and implemented — the second tier of the post-audit remediation plan, following directly on from Tier 0 (ADR-052). Covers four items: Subscription/Billing schema (SR-3, SAAS-GAP-1), Tenant user-invite flow (SR-2.4/5.11, SAAS-GAP-8), Background job queue (SR-6.10), Object storage abstraction for attachments (SR-6.5, SAAS-GAP-3).

**Decisions:**
- **Subscription/Billing is schema and platform-admin assignment only — explicitly no payment gateway, no billing engine, no invoicing.** A platform-wide `plans` catalog (no tenant_id, no RLS — same category as `roles`/`permissions`) and a per-tenant `subscriptions` row (RLS-protected, one row per tenant via a unique constraint on `tenant_id`). Two default plans (Trial, Standard) are seeded, and every pre-existing tenant is backfilled onto Trial by the migration itself (a plain `INSERT ... SELECT ... WHERE NOT EXISTS`, safe to run as the migration's owner-role connection, which bypasses RLS regardless of `FORCE ROW LEVEL SECURITY`). Assignment (`PUT /platform/tenants/{id}/subscription`) is platform-admin-only; the tenant side (`GET /settings/subscription`) is read-only — there is no tenant-facing write endpoint at all, by design, since collecting payment or letting a tenant self-upgrade is explicitly out of scope for this tier and needs its own future approval.
- **Tenant user-invite flow creates no `users` row until the invite is accepted.** A separate `user_invites` table (email/name/role chosen by the inviter, a hashed single-use token, an expiry) replaces admin-sets-the-password-directly provisioning (`UserCreateRequest`, kept as-is for scripts/back-compat, not removed). The accept endpoint (`POST /users/invite/{token}/accept`) is public and unauthenticated by necessity — exactly the same circular problem ADR-015 solved for `sessions`/`mfa_challenges` (a row must be resolved, and therefore its `tenant_id` known, before any tenant RLS context can be set) — so `user_invites` is deliberately exempt from RLS from its creation, trusting the token's unguessability plus `expires_at`/`accepted_at` instead, the identical trust model ADR-015 already established. The token itself is `{invite_id}.{secret}`: the id half makes the row lookup possible without a tenant-scoped query, the secret half (argon2-hashed at rest, via the same `hash_password`/`verify_password` already used for both real passwords and MFA codes) is the actual credential. Email delivery reuses `notification_email_delivery_mode`'s existing simulated/real split (ADR-032/051) rather than introducing a second delivery setting — "simulated" returns the raw token in the API response (and the frontend's Invite dialog surfaces it as a copyable link) for dev/test without a mail server.
- **Background job queue is a lightweight DB-backed table (`background_jobs`) with a polling worker, not Celery/Redis.** The approved stack has no cache/broker layer at all (the same constraint `app/core/rate_limit.py`'s own in-memory-limiter note already documents) — introducing one for a single low-volume job type (CSV import) would be a disproportionate new piece of infrastructure for this tier. The worker claims the oldest queued row with `SELECT ... FOR UPDATE SKIP LOCKED`, which lets multiple worker processes/containers poll the same table concurrently without blocking on each other or double-claiming — a concurrent claimant simply skips a row someone else is mid-claim on. `background_jobs` is deliberately exempt from RLS for the same structural reason as `user_invites`/`sessions`: the worker must scan across ALL tenants to find the next queued job, before any single job's `tenant_id` is known; every tenant-facing read (`GET /test-cases/import/jobs/{id}`) is still explicitly filtered by `tenant_id == ctx.tenant_id` at the service layer, the same unguessable-id-plus-explicit-filter trust model `Session` already uses. Tenant context is set **per job**, inside the worker's own transaction, never reused across jobs — ADR-007's RLS GUC is transaction-local and resets on both commit and rollback, a recurring bug class in this codebase, so the worker re-sets it explicitly after any rollback in its own failure-handling path rather than assuming it survives.
  - **The existing synchronous `POST /test-cases/import` is kept exactly as-is, not replaced.** NFR 8.1's 2.5s/2,000-row budget is proven against that exact code path (`test_bulk_import_2000_rows_under_2_5_seconds`), and forcing it onto the job queue would both risk that timing contract and remove a legitimate "small import, want the result immediately" use case. A new `POST /test-cases/import/async` enqueues the identical `csv_import_service.import_test_cases` logic as a job and returns a job id immediately; `GET /test-cases/import/jobs/{id}` polls for completion. Both paths exist side by side.
- **Object storage abstraction is schema-agnostic, exactly as the audit itself framed it** — `Attachment.storage_path` stays an opaque reference string regardless of backend (a filesystem path for `LocalFilesystemStorage`, an `s3://bucket/key` URI for `S3CompatibleStorage`), so no migration was needed. A new `app/core/storage.py` defines the `StorageBackend` interface; `attachment_service.py` now calls it instead of writing/reading/deleting the filesystem directly. Selected via `STORAGE_BACKEND=local|s3` (default `local`, so existing dev/prod deployments are unaffected without any action). `S3CompatibleStorage` uses `boto3` with a configurable `endpoint_url`, so it targets AWS S3 or any S3-compatible service (MinIO, DigitalOcean Spaces) equally. The attachment download route (`GET /attachments/{id}/download`) now reads bytes through the abstraction and returns a plain `Response` instead of `FileResponse` streaming straight off local disk — the one behavior change needed to stay correct across backends (loses `FileResponse`'s range-request optimization, acceptable given the existing 10MB attachment cap).

Testing: `test_subscriptions.py` (default Trial on tenant creation, platform-admin assignment, unknown-plan-code rejection, tenant read-only enforcement — no write route exists, tenant isolation), `test_user_invites.py` (invite → accept creates the user, single-use token, wrong/malformed token rejected, duplicate-pending-invite and already-has-an-account rejections, cross-tenant scoping of the same invited email, permission gate), `test_background_jobs.py` (async CSV import end-to-end via a directly-invoked `job_service.run_once` standing in for the worker process, failure recorded on the job, cross-tenant job-read isolation, a concurrency test seeding 20 jobs and racing 4 threads/sessions against `claim_one` asserting every job is claimed exactly once with none left behind), `test_storage_backends.py` (both backends parametrized against the same save/read/delete behavioral assertions, the S3 backend via `moto`, the local backend still doing real disk I/O). ## ADR-054: Tier 4 — Enterprise SaaS foundations (tenant branding, IP allowlist, data residency readiness, tenant-wide data export, SSO via OIDC, SCIM provisioning)

**Status:** Decided and implemented — the fourth tier of the post-audit remediation plan, following on from Tiers 0-3. Covers six items: Tenant branding (PV-11.4), Tenant-wide data export (PV-11.5), IP restriction/allowlisting (PV-11.3), SSO (PV-11.1), SCIM provisioning (PV-11.2), Data residency readiness (PV-11.6). Automation/CI-CD's machine-to-machine auth plane and external defect-tracker sync were explicitly descoped from this tier by the user and remain untouched.

**Decisions:**
- **Tenant branding reuses Phase 1's tenant-settings mechanism and Tier 1's storage abstraction, not new ones.** `display_name`/`primary_color`/`logo_ref` are plain columns on `Tenant`, same pattern as the existing AI settings. The logo goes through `app/core/storage.py`'s `StorageBackend`, not a separate upload path — `LocalFilesystemStorage`/`S3CompatibleStorage` work unchanged. Reading branding is open to any authenticated tenant member (the app shell needs it for every user, not just admins); writing it requires `tenant.settings.manage`, the same bar as every other tenant-settings field.
- **IP allowlisting is enforced at the session-resolution layer (`core/auth.py::get_current_context`) and again at login (`auth_service.start_login`), not just one or the other.** An empty/unset allowlist means no restriction — existing tenants are unaffected until they opt in. `X-Forwarded-For` is only trusted when a new `trust_proxy_headers` setting is explicitly on (default off) — a bare client-supplied header is never trusted by default, since Tier 0's reverse-proxy config is the only thing that would make that header meaningful. **This has a real self-lockout risk, by design, not a bug**: a tenant admin who sets an allowlist that excludes their own current network loses access with no in-app recovery path — only a platform administrator (direct DB access in this sandbox; an equivalent support/ops process in a real deployment) can clear it. The Settings UI warns about this explicitly rather than trying to prevent it, since preventing it would require guessing the admin's "real" network, which this app has no reliable way to do.
- **Data residency readiness is metadata only, platform-admin-settable, never tenant-settable.** A `data_region` column on `Tenant` (free-text, `us` default), settable at tenant creation and via a dedicated `PATCH /platform/tenants/{id}/data-region` route. No per-region deployment topology exists — `docs/DATA_RESIDENCY.md` documents what one would actually require (separate DB per region, region-aware routing/DNS, data-transfer/replication constraints) and says plainly that this is readiness, not an implemented capability.
- **Tenant-wide data export runs through Tier 1's background job queue, not a blocking endpoint**, and exports each entity's own raw columns as flat JSON rather than each API's richly joined/computed read-model (`DefectOut`'s `project_name`/`reviewer_name` etc.) — reusing those would mean duplicating every service's per-project, permission-scoped listing logic for a job that is intentionally tenant-wide, not per-project; the raw columns are sufficient for a genuine data export and are themselves the source the computed fields are derived from. Attachment bytes are listed by reference/metadata only, never inlined, keeping the archive size bounded regardless of how much binary content a tenant has accumulated — an opt-in "include attachment bytes" mode is a reasonable future addition if a real need surfaces, not built here. The archive is a zip of one JSON file per entity type plus a `manifest.json` row-count summary, written through the storage abstraction (so it works under either backend) and downloaded via a dedicated authenticated endpoint, never a raw filesystem path.
  - **Operational finding, fixed in this tier**: the `worker` container had no volume mount for `/data/attachments` at all in `docker-compose.yml`/`docker-compose.prod.yml`, and separately ran as root while `api` dropped to the unprivileged `app` user — a worker-written file was both invisible to `api` (different, unmounted filesystem) and, once the volume was added, unwritable-into by `api` afterward (root-owned directory). Both `compose` files now mount the shared volume into `worker` and give it the same chown-then-drop-privileges entrypoint `api`'s own Dockerfile `CMD` already uses — `command:` overrides in compose bypass a Dockerfile's `CMD` entirely, so the worker was never getting that treatment despite sharing the same image.
- **SSO is OIDC only — SAML is explicitly out of scope for this tier.** No real external IdP (Okta/Azure AD/Google/etc.) is reachable from this sandbox to validate against either protocol; OIDC is simpler to implement correctly, more broadly supported by modern IdPs, and well served by a standard library (`PyJWT` for ID-token verification against the IdP's JWKS). SAML remains a real future option if a specific customer requires it, needing its own proposal. Tenant-level config (`sso_configs`, RLS-protected like any ordinary tenant table — unlike `Session`/`BackgroundJob`, `tenant_id` is always already known from the URL path before this table is ever queried, so there is no chicken-and-egg problem requiring an RLS exemption here) stores the issuer/client id/Fernet-encrypted client secret (`app/core/crypto.py`, the same helper Phase 3's AI credentials already use — not a new encryption mechanism). Login is a standard authorization-code redirect (`GET /auth/sso/{tenant_id}/login` → IdP → `GET /auth/sso/{tenant_id}/callback`), state/CSRF protection via a short-lived httponly cookie compared against the callback's `state` parameter, never a server-side session store. A first-time SSO login auto-provisions a `User` row (email from the verified ID token's `email` claim, a fixed default role chosen by the tenant admin at config time — never a role claimed by the token) and issues this app's own existing `Session` mechanism directly, reusing `set_session_cookie`, not a parallel session type.
  - **MFA decision**: a successful SSO login issues a session with `mfa_verified=True` immediately, bypassing this app's own MFA challenge — the identity provider is treated as the trust anchor and is assumed to enforce its own MFA policy. This is a genuine security-relevant trade-off, made deliberately and documented here, not an oversight; password-based login is unaffected and still requires this app's own MFA exactly as before.
  - **Verification caveat, stated plainly**: this flow is tested against a stub/mocked OIDC provider (fake discovery document, token endpoint, and a locally-signed RS256 ID token), not a real production IdP. A real pre-launch validation pass against an actual IdP (Okta, Azure AD/Entra, Google Workspace, etc.) is a required follow-up before any tenant relies on this in production — a stub proves the protocol logic is correct, not that every real IdP's quirks are handled.
- **SCIM is a minimal SCIM 2.0 server scoped to Users only — no Groups/Roles sync.** Every SCIM-provisioned user gets a single fixed default role; a role or group claim in the SCIM payload is never trusted, the same no-role-claim-trusted stance SSO auto-provisioning already takes. Authentication is a per-tenant bearer token (`scim_tokens`, RLS-protected for the same reason `sso_configs` is — tenant_id is always known from the URL), hashed at rest with the same argon2 helper every other credential in this codebase uses, generated/rotated/revoked by a tenant admin through its own small authenticated API (`/scim-tokens`) — never editable, only created or revoked. **SCIM `DELETE` deactivates (`is_active = false`), never hard-deletes** — preserving audit-log and FK integrity matters more here than literal SCIM `DELETE` semantics, the same deactivate-don't-delete stance this codebase already takes for removal elsewhere. `PATCH` supports the common case real IdPs actually send (a flat `replace` of `active`/`displayName`/`userName`); anything else (add/remove on multi-valued attributes, nested paths) is intentionally ignored rather than erroring, documented as a scope limit rather than silently incomplete.
  - **Same verification caveat as SSO**: validated against the SCIM 2.0 spec's own documented request/response shapes directly, not against a real IdP's SCIM client (Okta/Azure AD Entra's SCIM provisioning connector, etc.) — there is no real IdP reachable from this sandbox. A real pre-launch validation pass against an actual IdP's SCIM client is a required follow-up before any tenant relies on this in production.

## ADR-055: Tier 5 — Tenant-configurable severities/priorities + custom fields, Insurance QA Pack

**Status:** Decided and implemented — the fifth tier of the post-audit remediation plan, following on from Tiers 0-4. Covers two items the user named explicitly: tenant-configurable statuses/severities/priorities + custom fields (PV-9.5/9.6), and the Insurance QA Pack (PV-10.1). Flagged in the original roadmap as "the most structurally invasive item in the entire roadmap" — the decisions below were made specifically to keep that true to its word without actually destabilizing anything already built on the fixed enums.

**Decisions:**
- **Severity (`Defect.severity`) and priority (`TestCase.priority`) are fully converted to tenant-configurable value sets — status is deliberately NOT.** The distinction is whether transition logic depends on the fixed values: severity/priority are pure labels nothing branches on, so the DB `CheckConstraint` and the Pydantic `Literal` type that used to pin both to exactly Low/Medium/High/Critical were both removed outright, replaced by a single `field_options` table (`tenant_id`, `field_key` in `('defect_severity','test_case_priority')`, `code`, `label`, `color`, `sort_order`) validated at the service layer (`field_option_service.validate_code`) on every create/update. One consolidated table rather than three separate `DefectSeverity`/`DefectPriority`/`TestCasePriority` tables, both because `Defect` has no priority field to convert in the first place (only severity) and because three near-identical tables would be needless duplication for what is structurally the same concept twice. Every tenant — existing (migration backfill) and new (`platform_service.create_tenant_with_admin`, mirroring Tier 1's subscription-seed pattern) — gets the same four defaults, so nothing changes for anyone unless an admin acts. The underlying columns stay the plain strings they always were (not converted to FK references) — reporting (`reporting_service.py` groups by `Defect.severity`/`TestCase.priority` directly in several places) and `SLA_DAYS_BY_SEVERITY`'s lookup (`.get(severity, 10)`, already degrades gracefully for an unrecognized value) both keep working completely unchanged, which is the main reason this stayed a validation-only change rather than a full relational conversion touching every call site that reads severity/priority.
- **Status, by contrast, gets only an additive display-label overlay (`status_labels`), not a value-set conversion.** `Defect.status`/`TestCase.status` and their fixed `CheckConstraint`s are completely untouched — Tier 2's reopen-counter detection and Tier 3's review-approval state machine both depend on knowing exactly which fixed codes exist and what "terminal" vs. "active" means for each, and ADR-026's forward-only sequence is itself a deliberate constraint this tier was explicitly warned not to casually reverse. `status_labels` lets a tenant rename what a status is *called* (e.g. "Closed" → "Resolved") without changing what it *is* — a missing row for a given `(entity_type, status_code)` simply means "use the built-in label," so there's no requirement to cover every code. This is a deliberate, narrower reading of "tenant-configurable statuses" than a literal one, made because the literal reading is exactly the destabilizing case the roadmap itself called out — not an oversight.
- **Custom fields are a genuine tenant-defined extra-field system** (`custom_field_definitions`: entity_type/field_key/label/field_type/options/required/sort_order; `custom_field_values`: polymorphic, mirroring Attachment/Comment/Notification's existing `owner_type`/`owner_id` pattern rather than a new one) for test cases, defects, and requirements — the latter needed a new `requirement` case added to `owner_access.py`'s dispatcher, which didn't support Requirements before this tier. Six field types (text/number/boolean/date/select/multi_select), values stored as a single JSON column (one shape handles all six without a column-per-type). **Values are read inline on every entity's existing `GET` response** (`custom_fields: dict` on `TestCaseOut`/`DefectOut`/`RequirementOut`) but **written only through a dedicated endpoint** (`PUT /custom-fields/values/{owner_type}/{owner_id}`), not folded into each entity's own create/update request schema — threading custom-field values through `TestCaseCreateRequest`/`DefectCreateRequest`/the CSV import path/the AI test-case generator would touch every creation code path in the app for a feature whose definitions can change at any time after those paths were written. One consequence of that choice, stated plainly: a field marked `required` is enforced only when values are explicitly submitted through the dedicated endpoint, never retroactively against entities that already existed before the field was defined, and entity creation itself never blocks on a missing required custom field. Authorization for both reading and writing values mirrors Comments/Attachments exactly (ADR-049/050): visibility of the owning entity is the gate, not a separate edit permission — the same precedent those features already set, not a new, stricter bar invented for this feature alone.
- **Two real bugs found and fixed during this tier's own verification, both the same recurring class already documented elsewhere in this file: the RLS GUC (`app.current_tenant`) is transaction-local and resets on every commit.** `custom_field_service.set_values_for_owner` committed its writes and then immediately queried `custom_field_definitions`/`custom_field_values` again (to return the fresh merged values) without re-asserting tenant context first — every such call returned an empty result (RLS silently filtering everything out) until fixed. `template_service.import_templates` chains three separate service calls that each commit their own transaction (`test_module_service.create_module`, `test_case_service.create_test_case`, `test_module_service.assign_test_case`) — without re-asserting tenant context between them, `assign_test_case` couldn't see the test case `create_test_case` had just committed moments earlier, failing with a false "Test case not found." Both fixed by re-asserting `set_tenant_context` immediately after each commit and before the next RLS-protected read, the same pattern already established in every `_to_out` across this codebase.
- **Insurance QA Pack is static in-code template data, not a database table of its own.** `app/data/insurance_templates.py` holds ~15 generic (no real customer/claims data) test-case templates across three categories (Claims, Underwriting, Policy Admin); importing creates real `TestCase` rows via the existing `test_case_service.create_test_case` (so versioning, audit logging, and the new tenant-configurable priority validation all apply exactly as they would to any hand-authored test case) organized into a same-named `TestModule` per category, auto-created the first time a tenant imports into it (Tier 3's module system). **Re-importing the same templates is deliberately not idempotent** — it creates a second, separate copy rather than being silently skipped or requiring an import-tracking table, since the whole point of a template is to hand the tenant a starting point they're expected to then edit freely, not a synced read-only asset.

Testing: `test_field_options.py` (tenant isolation, CRUD, in-use options can't be deleted, can't delete the last remaining option, migration backfill produces the four original defaults for pre-existing tenants, new tenants get them at creation), `test_status_labels.py` (built-in label returned when unset, override round-trip, reset via `label: null`, invalid status code rejected, reopen-counter and review-approval transitions behave identically regardless of label customization), `test_custom_fields.py` (definition CRUD per entity type, select/multi_select option-membership validation, required-field enforcement on explicit value submission only, tenant isolation of both definitions and values across test cases/defects/requirements, deleting a definition cascades its values), `test_insurance_templates.py` (import creates the expected test cases and modules, re-import creates a second copy rather than erroring or being skipped, tenant isolation, unknown template id rejected). Verification performed and results are recorded in the completion report for this tier rather than duplicated here.

Testing: `test_tier4_saas_foundations.py` — branding round-trip/permission-gate/tenant-isolation plus a real logo upload-and-download byte-for-byte round trip, IP allowlist default-unrestricted/blocks/allows/malformed-rejected/enforced-at-login-too/tenant-isolation (the matching/blocking tests patch `core.auth.client_ip` since Starlette's `TestClient` reports a literal `"testclient"` host, not a real IP, for the underlying transport), data region set-at-creation/defaults-to-us/platform-admin-only, tenant export producing a byte-valid zip with the expected manifest and never leaking another tenant's rows (verified via a direct `job_service.run_once` call standing in for the worker, same pattern Tier 1 established) plus its own permission gate, SSO status-is-public/config-permission-gate/a full login-flow-against-a-stub-IdP-provisions-and-signs-in/mismatched-state-rejected/password-login-still-works-once-SSO-is-configured, SCIM token-creation-and-bearer-auth/create-list-patch-and-deactivate/tenant-isolation/token-revocation. Verification performed (lint/typecheck/pytest regression, Docker rebuild, live end-to-end checks against real running containers, frontend typecheck/lint/unit-tests/build, Playwright regression) and its results are recorded in the completion report for this tier rather than duplicated here.

## ADR-056: Production Deployment Preparation — a gap-analysis hardening pass on top of Tiers 0-5

**Status:** Decided and implemented. Unlike Tiers 0-5, this was not a new feature tier against the audit's backlog — it's a formal "prepare for secure production deployment" directive, executed as a gap-analysis pass rather than a rebuild, since Tier 0 (ADR-052) had already built most of what such a directive asks for (production Dockerfiles, `docker-compose.prod.yml`, backup/restore scripts, structured logging, a reverse proxy config, rate limiting). See `docs/deployment/DEPLOYMENT_ASSESSMENT.md` for the full inventory of what already existed versus what this pass added, and the full `docs/deployment/` set (`PRODUCTION_DEPLOYMENT_GUIDE.md`, `DATABASE_MIGRATION.md`, `BACKUP_AND_RESTORE.md`, `SECURITY_CONFIGURATION.md`, `ADMINISTRATOR_GUIDE.md`, `USER_GUIDE.md`) for the operator-facing documentation this ADR summarizes the reasoning behind.

**Decisions:**
- **Requested root-level `Dockerfile.frontend`/`Dockerfile.backend`/`docker-compose.yml` (production) layout was deliberately NOT adopted verbatim** — this repo keeps `backend/Dockerfile`, `frontend/Dockerfile.prod`, `docker-compose.prod.yml` (distinct from the dev-focused `docker-compose.yml`, already referenced throughout five prior tiers of docs/tooling). Renaming would mean either repointing `docker-compose.yml`'s meaning to production (breaking every existing doc/script/muscle-memory command that assumes it's the dev file) or relocating the Dockerfiles to the repo root (changing their build context and every `COPY` path inside them, demanding a full re-verification this pass's time budget was better spent on the security/backup/logging work below). What genuinely is new at the exact requested paths: `deployment/scripts/` (`backup_database.sh`/`restore_database.sh`/`backup_files.sh` are thin delegates to the canonical `scripts/*.sh` — one source of truth, no drift risk; `health_check.sh` and `verify_backup.sh` are genuinely new), `deployment/nginx/nginx.conf` (a synced copy of the canonical, actually-mounted `deploy/nginx/reverse-proxy.conf`), and `deployment/README.md`.
- **Session-ID rotation on MFA completion, a real fix, not just documentation.** `auth_service.verify_mfa` previously flipped `mfa_verified=True` on the same pre-MFA session row; it now mints a new session row (fresh id, `mfa_verified=True`) and revokes the pre-MFA one. A pre-MFA session cookie — sent over the wire and briefly held client-side before full authentication completes — can no longer be replayed to reach an authenticated state once MFA succeeds. Standard session-fixation mitigation (rotate the identifier after a privilege change), not a cosmetic change — see `test_auth_flow.py::test_mfa_verification_rotates_session_id`, which explicitly confirms the old cookie is rejected as revoked afterward.
- **Startup configuration validation** (`app/core/config.py::validate_for_production`, called at import time in `app/main.py`, only active when `ENVIRONMENT=production`): refuses to boot if `MFA_DELIVERY_MODE=simulated` (which returns one-time codes directly in API responses — correct for dev/test, a critical leak in production), `DATABASE_URL` is still the hardcoded local-dev default, or `CORS_ALLOW_ORIGINS` is unset/the dev default/a wildcard. This is a second, application-level check alongside `docker-compose.prod.yml`'s existing `${VAR:?...}` guards — those only help when that exact compose file is used; this catches a deployment run any other way. Reports every problem found at once, not just the first.
- **A general rate-limit backstop** (`Limiter(default_limits=["300/minute"])` in `app/core/rate_limit.py`) now covers every route that doesn't have its own specific `@limiter.limit` decorator, via `SlowAPIMiddleware` — confirmed, by reading slowapi's own dispatch logic, that routes with an explicit decorator are exempted from double-counting against this backstop (checked once, by their own tighter limit), so this is purely additive coverage for routes nobody had previously added a specific limit to, not a change to any existing limit's behavior.
- **Security-event logging**: failed tenant logins, MFA lockouts, platform-admin login failures/lockouts, IP-allowlist rejections, and rate-limit trips now each emit a distinct `security_event=...` JSON log line (alongside the existing generic per-request access log), and the JSON formatter now includes a `service` field (`qtesthub-api`/`qtesthub-worker`) — making it possible to build an alert on repeated auth failures by grepping log output, which wasn't previously distinguishable from ordinary request logs.
- **nginx security headers and request limits**, both layers (`frontend/nginx.conf` and `deploy/nginx/reverse-proxy.conf`): `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` on both; `Strict-Transport-Security` at the edge proxy only (where a real certificate is already a precondition for that server block existing at all); `client_max_body_size 20m` (above the 10MB application-level attachment limit, so a legitimate upload is never cut short at the proxy) and explicit proxy timeouts, neither previously set.
- **A real backup-verification script** (`deployment/scripts/verify_backup.sh`), genuinely new rather than documentation: test-restores a dump into a disposable, uniquely-named temporary database on the same server, runs a real query against it, reports the result, and drops the temporary database — never touching the real application database. A backup that merely exists on disk is not evidence it's restorable (truncated transfer, wrong `pg_dump` version, silent corruption); this is the directive's required "practical restore verification procedure," not just a checklist item in a doc.
- **The `worker` container's long-standing false "unhealthy" Docker status, root-caused and fixed.** It had been inheriting the `api` image's Dockerfile `HEALTHCHECK` (an HTTP GET against `/api/v1/ready`) ever since Tier 1 — but `worker` never serves HTTP at all, so that probe failed on every check despite the worker correctly processing jobs. Replaced with a `/proc`-based Python one-liner confirming the `app.worker` process is actually running (no new OS package needed — `pgrep`/procps isn't in the `python:3.12-slim` base image), in both `docker-compose.yml` and `docker-compose.prod.yml`.
- **CSRF explicitly evaluated, not reflexively added.** This app's auth model is a `SameSite=Lax` session cookie plus a JSON-only API (no HTML form-POST targets) — the classic cross-site-form-POST pattern CSRF tokens exist to stop is already closed by that combination. A CSRF token layer was deliberately not added on top, since it would add real complexity (token issuance/rotation/validation on every mutating request) for an attack surface that doesn't otherwise exist given the current request shape. The one genuine state-changing GET in the app — Tier 4's `GET /auth/sso/{tenant_id}/callback`, a GET by necessity since it's an OAuth redirect target — already has its own dedicated protection (the `state` parameter checked against a short-lived `HttpOnly` cookie), the standard OAuth CSRF mitigation for that exact shape of endpoint, not an oversight this pass needed to close. Documented in `docs/deployment/SECURITY_CONFIGURATION.md` §1.
- **SSO/SCIM real-IdP validation, HTTPS-against-a-real-certificate, and real-cloud-object-storage validation remain explicitly out of reach in this environment** — restated here, not newly discovered: no real OIDC/SCIM identity provider, no real domain/TLS certificate, and no real S3-compatible account exist in this sandbox. Each was already disclosed when its originating tier shipped (Tier 0 for HTTPS, Tier 1 for S3, Tier 4 for SSO/SCIM) and remains a required follow-up before production reliance, not something this pass could close.

Verification performed (lint/typecheck/pytest regression — including new tests for session rotation, the startup validator, and the rate-limit backstop — Docker rebuild of both dev and prod compose, a real clean-deployment-from-empty pass, live checks against real running containers, frontend typecheck/lint/unit-tests/build, Playwright regression) and its results, using the directive's own required Implemented/Verified/Partially Verified/Pending deliverables table, are recorded in the completion report for this pass rather than duplicated here.

## ADR-057: Gap-closure pass on the audit's own `KNOWN_GAPS.md` backlog

**Status:** Decided and implemented, with several items deliberately scoped down or deferred and disclosed as such — this pass covered 11 named items in one go, several of which (the fastapi/starlette major-version bump especially) were individually larger than some entire prior tiers, so honest, visible scoping was treated as more important than claiming blanket completion. See `docs/KNOWN_GAPS.md` GAP-85 through GAP-88, and the corrected GAP-75/77/78/69 entries (each had drifted stale across Tiers 2-3 and this pass's own findings).

Also fixed the Environments nav item's gating to match the `environment.manage` permission Managers already hold (was `adminOnly` only).

Without re-asserting `set_tenant_context` at the start of `record_ci_result`, every webhook call failed with a false "test run case not found" even for a valid, correctly-scoped id. Fixed by re-asserting tenant context at that function's entry, matching the established defensive pattern used everywhere else in this codebase.

## ADR-060: Full RBAC role builder, strict assignee-based execution, self-service test case creation (reverses GAP-05/ADR-014)

**Status:** Decided and implemented, per the user's explicit, deliberate approval to reverse a long-standing prior decision. ADR-014 and GAP-05 (`docs/KNOWN_GAPS.md`) both framed custom/tenant-defined roles as "out of BRD scope... needs a formal BRD change-request" — this pass **is** that formal change request, made explicitly by the user, not a silent architectural drift. Pass 1 of a user-approved 2-pass plan; Pass 2 (UI/UX audit, app-wide toast rollout, Test Case/Defect schema realignment, bulk import/template updates) is separate, later work.

**Role data model**: `roles` gained `tenant_id` (nullable), `is_system`, `is_active`. System roles (Admin/Manager/Tester) keep `tenant_id IS NULL` exactly as before — shared globally, zero duplication per tenant, unchanged seed behavior — and are protected from edit/deactivation at the service layer. A custom role is a normal tenant-scoped row (RLS: `tenant_id IS NULL OR tenant_id = current_tenant`, so system rows stay visible unconditionally — including before any tenant context is set, needed for tenant-provisioning's own system-role lookup). `code` stays unique-but-nullable (Postgres treats multiple NULLs as distinct) since only system roles are ever referenced by a fixed code string; custom roles are only ever looked up by id.

**Permission catalog, not invented**: the role builder (`GET /roles/permissions`) only ever exposes the real, already-enforced permission codes (grepped directly from every `require_permission(...)` call site in the codebase, plus the new `project.view.all`) — never a phantom permission with no corresponding check anywhere.

**The core design decision — composability without touching ~60 call sites**: converting every one of the ~20 hardcoded `role_code in ("admin","manager")` / `role_code == "tester"` comparisons scattered across 7 service files (`project_service.py`, `test_case_service.py`, `defect_service.py`, `execution_service.py`, `reporting_service.py`, `requirement_service.py`, `csv_import_service.py`) — plus every one of their ~60 call sites across 15 API files, several reached only indirectly via `owner_access.py`'s dispatcher — would have been the highest-risk, highest-effort part of this pass if done by renaming parameters everywhere. Instead: `SessionContext.role_code` now carries an **effective access-tier value** rather than always the literal DB role code — unchanged (`"admin"`/`"manager"`/`"tester"`) for the 3 system roles (zero behavior change, zero regression risk for every existing user/test), and for a custom role, computed once in `core/auth.py` as `"manager"` if the role holds `project.view.all` (full tenant-wide access) else `"tester"` (assignment-restricted access) — whichever existing access tier its real permissions most closely match. Every pre-existing comparison, in every file, including ones reached only through `owner_access.py`/`ai_service`/`search_service`/etc., now composes correctly with custom roles automatically, with **zero changes needed to any of those 7 files or their callers**. A new `SessionContext.display_role` field (the role's real name — "Admin"/"Manager"/"Tester" for system roles, or the custom role's actual name) replaces `role_code` at the one place that needs the true identity for display: `GET /auth/me`.

**A disclosed limitation of this design**: dozens of frontend conditionals (`role === 'admin'`, found across ~10 files) key off `/auth/me`'s displayed role name, which for a custom role is its real name (e.g. "QA Lead"), never literally `'admin'`/`'manager'`. A custom-role user with full admin-equivalent permissions is correctly and securely enforced on the backend, but won't see admin-gated UI buttons the system Admin role sees — a real UX gap, not a security gap, and explicitly scoped as Pass 2's UI/UX audit territory (migrating these conditionals to permission-based checks), not attempted in this pass.

**Self-service test case creation**: already functionally true before this pass — `testcase.create` was already granted to the system Tester role in the original BRD seed (`7bca6b69ef88`). No backend change was needed; only confirmed and covered by a new end-to-end test (a custom role holding only `testcase.create` can create a test case but not edit or submit it for review, since it lacks `testcase.edit`).

**User role assignment**: `UserCreateRequest`/`UserUpdateRequest` gained an optional `role_id` (assign any tenant-visible role, system or custom) alongside the existing `role` code field (kept for every existing caller/test, unchanged) — exactly one must be given, validated in `user_service.resolve_role_id`. The invite flow (`UserInviteRequest`) deliberately was **not** extended to `role_id` this pass — scoped to direct user creation only, to keep this pass's blast radius bounded.

**Strict assignee-based execution**: a new `execution_service._require_execution_rights` check, called in both `open_step` and `record_verdict` right after the existing (unchanged) project-visibility check. A role without full access (`role_code` not in `("admin","manager")` — composes automatically with the custom-role mapping above) may execute only a run case whose `assigned_to` is literally them — no unassigned-run-case fallback, exactly as confirmed. Read-only visibility (viewing a run case, its attachments, its context) is unaffected — only the actual execute actions gained this stricter gate.

**New migration** `053233f28383`. **New API**: `app/api/roles.py` (`GET /roles`, `GET /roles/permissions`, `POST/PATCH/DELETE /roles/{id}`), gated by the existing `user.manage` permission (no new permission invented for managing roles themselves). **New frontend**: `/admin/roles` (Roles & Permissions page — permission matrix + role CRUD), `UsersRoles.tsx`'s role dropdowns now source the tenant's real role list instead of a hardcoded 3-value array.

**Two real bugs found and fixed during this pass's own verification, both disclosed rather than quietly patched over:**
1. The baseline schema's `roles.code` column was `NOT NULL`; the model was updated to allow a custom role to omit it, but the migration never actually relaxed the database constraint — a genuine model/schema mismatch, not caught until the very first live `create_role` call. Fixed by adding `op.alter_column("roles", "code", ..., nullable=True)` to the migration.
2. `roles.tenant_id` was originally given a real foreign key to `tenants.id`. This table now mixes permanent global seed rows (`tenant_id IS NULL`) with per-tenant custom rows in one table — and Postgres's `TRUNCATE ... CASCADE` (used by this project's own test-suite cleanup fixture, and plausibly future tenant-deletion tooling) empties an **entire** referencing table when CASCADE is invoked, not just the rows matching the truncated parent — wiping every system role, for every tenant, after the very first test. Fixed by deliberately not giving `tenant_id` a hard FK (kept indexed and service-layer-validated instead), documented directly in both the migration and the model.
3. Separately, the RLS policy's own first draft reused the bare `current_setting(...)::uuid` cast this project's own `567fa7545de9` migration had already identified and fixed as unsafe elsewhere (an unset GUC reads back as `''`, not `NULL`, and raises on cast rather than just failing the predicate) — missed on the first pass, caught via live reproduction, fixed with the same established `NULLIF(...,'')` guard used by every other RLS policy in this codebase.

**Verified**: backend `ruff`/`mypy` clean, **559/559 passing** in a genuinely isolated full regression (including all 6 new `test_custom_roles.py` tests and the new strict-execution tests in `test_execution.py`) — zero failures, not even the usually-flaky GAP-69 timing test this run. Migration applied cleanly against the real running dev database; extensive **live verification** against it: created a custom role via the real API, assigned a user to it, confirmed its exact permission boundary end-to-end (can create a test case, correctly 403s on edit/submit-review), confirmed `/auth/me` shows a custom role's real name rather than a mapped generic value, confirmed system-role edit/deactivate protection and deactivation-blocked-while-in-use, and confirmed a second custom role without `project.view.all` is correctly blocked from executing an unassigned run case and then correctly allowed once assigned — composing with the strict-execution rule exactly like today's Tester, entirely automatically. Frontend `typecheck`/`lint`/unit-tests/`build` all clean. Full Playwright regression: 10/13 on the first (4-worker) pass; the 2 non-`journey3` failures did not reproduce on an isolated single-worker rerun (load-dependent, consistent with this project's own documented login-rate-limit-collision pattern), leaving only the long-documented, unrelated `journey3` locator strict-mode flake — no real regression from this pass.

**Assessment for Pass 2**: this pass is solid to build on. The permission-composability design (effective `role_code` computed centrally) means Pass 2's planned schema realignment and UI/UX work won't need to touch any of the 7 already-converted service files again. The one disclosed limitation — frontend role-name conditionals not recognizing custom roles as admin-equivalent — is real but cosmetic (backend enforcement is correct regardless) and is explicitly Pass 2's territory to fix, not a blocker to starting it.

## ADR-061: Pass 2 — custom-role frontend fix, toast rollout, Test Case/Defect schema realignment, bulk import/template updates

**Scope**: ADR-061 (Pass 2) extended the `ToastProvider`/`useToast` system (Tier 3) to defects, Roles & Permissions, project creation, and two requirement mutations, explicitly leaving the rest of the app untouched and tracked as GAP-90. This pass closes that remainder.

**Extended to**: Execution Console (verdict recording — error-only by design, see below), Attachments (upload/delete), Comments (post/delete), every remaining Platform Admin action (tenant status/data-region, subscription assignment, tenant creation), every Settings card (organization settings, AI settings, branding + logo upload, SSO config, SCIM tokens, service tokens, custom field definitions, field options, status labels, data export), Users & Roles (invite/direct-create/role-change/deactivate/activate/reset-password), Environments (create/delete), Project Detail (update/delete/member add-remove/builds/releases create-delete), Test Repository (inline next-action/delete/create), Requirement Detail (unlink/delete), Test Runs (create run; pause/resume/finish/remove-case/assign-case/edit/add-cases on the detail page), and the `CustomFieldsCard` value-save component shared by test cases/defects/requirements.

**A real, previously-silent failure path found and fixed**: `TestRepository.tsx`'s inline quick-action (Submit/Approve/Deprecate) and delete mutations had *no error handling at all* — a failed action (e.g. an invalid status transition) failed completely silently with no feedback of any kind. Found during the app-wide `useMutation` sweep this pass used to find gaps, not reported by a user. Fixed with both success and error toasts.

**Deliberately left without a toast — each a stated UX reason, not an oversight**:
- **Execution Console's verdict recording**: error-only. A verdict's own badge renders immediately as visible confirmation on success, and this mutation fires on every P/F/I keypress during a long execution run — a success toast per step would be noise, not help. A failure *does* get a toast, since nothing else would surface it.
- **Login/MFA**: the existing inline error display is the correct pattern for a two-step credential-then-code auth flow; a toast would be a redundant second signal for the same failure.
- **AcceptInvite**: already shows its own clear "Account activated. Redirecting…" on-screen confirmation before navigating away.
- **AI Assistant panel and AI-suggestion dialogs** (Defect root-cause suggestion, Requirement change-analysis/test-generation): each already renders a richer inline chat-bubble or result-panel display for both success and failure than a transient toast could — this mirrors the same no-duplicate-indicator principle applied below.
- **CSV import dialogs** (test case and defect): already show a detailed created/error-count summary with a downloadable error report — a toast on top would just repeat what's already on screen.
- **NotificationBell's mark-read/mark-all-read**: high-frequency, low-signal, often auto-triggered — a toast here would be noise.

**Four pre-existing "Saved." inline-message patterns replaced, not duplicated**: `SettingsForm`, `AISettingsForm`, `BrandingForm`, and `SsoForm` each had their own local `savedMessage` state rendering a static "Saved." span next to the submit button. Per this pass's own principle (confirmed by a real strict-mode collision bug fixed in ADR-061), a mutation gets exactly one success/failure indicator, not two — these four were converted to toasts and their local state removed, rather than kept alongside a new toast.

**Verified**: frontend `typecheck`/`lint`/unit tests/`build` all clean. The `web` Docker container was explicitly rebuilt and its live-served source confirmed (via a direct dev-server source fetch) to contain new toast strings before any further verification — directly guarding against the exact stale-build trap ADR-061 (and the production-hardening pass before it) hit. **Live end-to-end verification**: a scratch Playwright spec confirmed both the Environments "Environment added" toast and the Settings "Organization settings saved" toast (replacing the removed inline message) render correctly against a real running container, then was deleted. Full Playwright regression at 4 workers: 10/13 passing; all 3 failures (`journey3`'s long-documented strict-mode locator collision, one accessibility spec, one `journey4` spec) individually reconfirmed as the known 4-worker-load-dependent flakes by passing clean in isolation single-threaded — no real regression.

**GAP-90 is now closed**, with its one genuinely separate remaining item (the reviewer-picker's role-name filter, blocked on the users-list API not exposing per-user permissions) and the dedicated UI/UX audit both still correctly tracked as open, not folded into this closure.
