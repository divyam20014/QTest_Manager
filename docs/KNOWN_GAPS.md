# Known Gaps, Residual Risks & Deferred Decisions

Tracks items that are intentionally not fully solved in this phase, with the reason and what would need to happen to close them. Cross-references `ARCHITECTURE_DECISIONS.md` (ADR) where a decision was made but carries a residual gap.

| ID | Gap | Related ADR | Why deferred | Closing condition |
|----|-----|--------------|---------------|--------------------|
| GAP-01 | Audit log is not cryptographically tamper-proof against a privileged database administrator (hash chain + revoked grants only deter/detect, not prevent). | ADR-006 | Full WORM (write-once-read-many) external log shipping (e.g., object storage with object-lock, or a separate append-only ledger service) is additional infrastructure not requested in the stack list. | Add external log shipping if a specific regulator (NAIC/PRA/EIOPA/APRA) audit requires it — stakeholder/compliance sign-off needed before building. |
| GAP-02 | True offline (disconnected network) operation is not supported; only synchronous-write resilience and draft-recovery via browser storage. | ADR-010 | BRD's "offline-first" and "cloud-native multi-tenant" requirements are mutually exclusive as written; no sync/conflict-resolution protocol was specified. | Needs an explicit product decision + CRDT/sync-queue design if disconnected field use becomes a real requirement. |
| GAP-03 | GDPR/CCPA full physical erasure of a user is not implemented — only PII pseudonymization, to preserve audit continuity. | ADR-009 | Retention-period rules vary by jurisdiction and regulator; BRD does not specify them. | Needs legal/compliance sign-off per tenant jurisdiction on minimum retention before physical deletion can be exposed. |
| GAP-04 | MFA delivery is "simulated" (logged/returned) by default outside production; no real SMS/push/hardware-key provider is integrated. | ADR-011 | Stack list does not name an SMS/email OTP provider; BRD explicitly says "MFA simulation." | Pick and integrate a provider (e.g., email OTP via existing mailer, or TOTP apps) before go-live; data model already supports it. |
| GAP-05 | Custom/tenant-defined roles are not supported — only the three BRD-fixed roles (Admin/Manager/Tester). | ADR-014 | Out of BRD scope (§3.2 is a closed matrix); building a role-builder would be unrequested scope expansion. | Formal BRD change-request per document §13 if a future release needs it. |
| GAP-06 | No automated statutory/regulatory calculation logic (NCB tiers, co-insurance formulas, deductible math) is implemented in the platform. | — (by design) | BRD §5 explicitly states the platform manages *testing of* insurance logic, not insurance calculations themselves (master prompt §5 confirms this boundary). | Not a gap to close — documented here only so it isn't mistaken for missing scope. |
| GAP-07 | File storage is local filesystem only; no object storage (S3-compatible) backend yet. | ADR-012 | Stack list says "local filesystem initially." | Swap `storage_path` resolution to an object-storage client when multi-node/horizontal scaling is needed; schema already storage-backend-agnostic. |
| GAP-08 | ~~Reporting/compliance PDF export engine unresolved~~ **Resolved in Phase 8** (ADR-027): no server-side PDF library is added; FR-REP-002's "printable view" acceptance criterion describes browser print-CSS, not a generated PDF file. Backend exports CSV only. | ADR-027 | FR-REP-002's own wording describes print-stylesheet behavior, not a PDF generator. | Revisit only if a future requirement explicitly needs a server-generated (non-interactive) PDF, e.g. for scheduled email delivery. |
| GAP-09 | ~~CSV import concurrency/locking unresolved~~ **Resolved in Phase 5** (ADR-021): import is processed synchronously within a single request/transaction — no separate staging table, so there is no cross-request staging state to race on. Two simultaneous imports naming the same project name are each a normal transaction; worst case is the usual duplicate-name-rejection (`uq_projects_tenant_name_ci` doesn't apply here, but duplicate *test case* titles aren't constrained, so concurrent imports can create rows with the same title — acceptable, matches single-row creation behavior). | ADR-021 | — | — |
| GAP-10 | ~~Exact password complexity policy unresolved~~ **Resolved in Phase 2**: enforced as minimum 12 characters + upper/lower/digit (`app/schemas/common.py`, `StrongPassword`). | — | Both figures appeared in the BRD itself; enterprise recommendation was chosen for a regulated product. | Still worth an explicit stakeholder confirmation if the policy needs to change later. |
| GAP-11 | `docker-compose.yml` and `backend/.env.example` contain plaintext dev-only credentials (`qtesthub`/`qtesthub`, `qtesthub_app`/`qtesthub_app`). | — | Fine for local development; never acceptable for a deployed environment. | Before any non-local deployment, source DB credentials from a secrets manager / environment-specific `.env`, never commit real credentials, and rotate the seeded dev passwords. |
| GAP-12 | Audit hash-chain writes for the same tenant are serialized with a `pg_advisory_xact_lock` (ADR-016), but this has only been verified logically, not load-tested under real concurrent write traffic. | ADR-016 | No concurrency/load testing has been part of this phase's scope. | Add a concurrency test (parallel audit writes to the same tenant) before relying on the hash chain for a compliance audit under production load. |
| GAP-13 | Platform-level actions (tenant creation, status changes) are **not** attributed to a specific platform admin's identity in `audit_logs` — `user_id` is `None`, since `audit_logs.user_id` FKs to `users`, not `platform_admins`. | ADR-008 | Platform admins are intentionally outside tenant RBAC; adding a second actor-identity column was out of scope for this phase. | If platform-level actions need individual attribution for compliance, add a nullable `platform_admin_id` column to `audit_logs` (or a separate `platform_audit_logs` table) in a later phase. |
| GAP-14 | Platform Administration authentication uses HTTP Basic against the `platform_admins` table (`app/core/platform_auth.py`) — no session, no MFA, no credential rotation workflow. | ADR-008 | ADR-008 frames Platform Administration as provisioning-only/out-of-band; building a full second auth system for a bootstrap-only actor was judged disproportionate for this phase. | Revisit if Platform Administration grows beyond tenant bootstrap (e.g., if it needs its own UI) — likely wants the same session+MFA treatment as tenant auth at that point. |
| GAP-15 | ~~Test case attachments (screenshots/documents, FR-TC-001) are not implemented~~ **Resolved** (post-Phase-10): `POST/GET /test-cases/{id}/attachments`, `GET/DELETE /attachments/{id}[/download]` built on the existing `attachments` table/ADR-012 design — bytes on disk (`attachments_dir`, 10MB cap), metadata in Postgres, access gated by the owning test case's own project-visibility rule (ADR-019). Frontend: an Attachments card on `TestCaseDetail.tsx` (upload/list/download/delete). Tests: `test_attachments.py` (upload/list/download, size-limit and empty-file rejection, delete, tester-must-be-assigned). | ADR-012 | — | — |
| GAP-16 | ~~No rate limiting or brute-force throttling on `POST /auth/login`~~ **Resolved** (post-Phase-10): `slowapi`, per-client-IP, 10/minute on both `/auth/login` and `/auth/mfa/verify`, returning the standard error envelope with `code: "rate_limited"` (`app/core/rate_limit.py`). Keyed by IP rather than `(tenant_id, email)` since slowapi's key functions read the connection, not the JSON body, without extra plumbing — still a real brute-force mitigation, and explicitly one of the gap's own acceptable options. Verified against the real running server (10× 401, 11th request 429) in addition to `test_rate_limiting.py` (which must explicitly re-enable the limiter — it's off by default for the rest of the suite, see `conftest.py`, since 74+ other tests' logins would otherwise trip it). | — | A per-(tenant_id, email) key, or a Redis-backed limiter for multi-process deployments, if this needs hardening beyond a single-process deployment. |
| GAP-17 | ~~`MfaChallenge.attempt_count` read-then-incremented without a row lock~~ **Resolved** (post-Phase-10): added `.with_for_update()` to the challenge fetch in `auth_service.verify_mfa`, closing the window where concurrent parallel verify requests could each read the same pre-increment `attempt_count`. Covered by the existing `test_mfa_lockout_after_three_attempts` (unchanged pass/fail behavior under the row lock); the race itself isn't independently testable without real concurrency, which was already judged low-severity enough not to warrant a dedicated concurrency test. | — | — | — |
| GAP-18 | ~~`verify_password()` only caught `VerifyMismatchError`~~ **Resolved in Phase 9**: now also catches `VerificationError`/`InvalidHashError` and fails closed (`app/core/security.py`), covered by `test_verify_password_fails_closed_on_malformed_hash`. | — | In practice every stored hash was produced by `hash_password()`, so this couldn't occur through normal operation — found via code review, not a reproduced failure, and cheap enough to just fix immediately rather than defer. | — |
| GAP-19 | ~~No automated dependency vulnerability scanning~~ **Resolved** (post-Phase-10): `pip-audit==2.10.1` wired into `requirements-dev.txt` (run manually — `python -m pip_audit -r requirements.txt` — no CI pipeline exists yet in this project to wire it into automatically); `npm audit` on the frontend reports 0 vulnerabilities. Baseline run found 26 known CVEs across `python-multipart` and `starlette`. `python-multipart` bumped `0.0.20`→`0.0.31` (only a `>=0.0.18` floor from fastapi, full 75→80-test suite re-verified green) and is now fully clean. `starlette` 0.41.3 (transitive via `fastapi==0.115.6`) remains vulnerable — fully remediating it needs `starlette>=1.3.1`, which needs `fastapi>=0.140.0` (the exact minimum was checked by inspecting each release's `Requires-Dist: starlette` constraint, not guessed), a ~25-minor-version jump with real regression risk across routing/DI/OpenAPI generation. Deliberately **not** attempted in this pass — a dependency bump that large deserves its own dedicated, carefully-tested effort with explicit sign-off, not a quiet drive-by alongside three other gap fixes. | — | A dedicated fastapi/starlette upgrade phase: bump to `fastapi>=0.140.0`, re-run the full test/lint/typecheck/e2e suite, and manually smoke-test every endpoint category for behavior changes before considering it done. |
| GAP-20 | ~~No backend query to look up defects by step~~ **Resolved in Phase 10.6**: `GET /defects?test_run_id=` lets a client fetch every defect for a run in one call and match client-side by `test_case_version_step_id`, scoped to that run so same-step defects from *other* runs/reruns don't false-positive. | — | Found while building the Execution Console (Phase 10.5); fixed while building Defects management (10.6), which needed richer filtering anyway. | — |

Revisit as a constrained enum only if a future compliance requirement needs region-based reporting rollups that free text can't reliably support.
