## Real bugs found and fixed during this phase (all via actual execution, not inspection)
1. **RLS chicken-and-egg on session lookup**: resolving a session cookie requires reading `sessions` before the tenant is known, but RLS requires the tenant to be known first. Fixed by exempting `sessions`/`mfa_challenges` from RLS (ADR-015) — security for those two tables rests on the row id being an unguessable UUID, same trust model as a password-reset token.
2. **`SET LOCAL` doesn't accept bind parameters** — `set_tenant_context` was passing `:tenant_id` as a parameter to a `SET LOCAL` statement, which PostgreSQL rejects outright. Fixed using `set_config('app.current_tenant', :tenant_id, true)`, which does support parameters.
3. **Empty-string GUC after commit** — a transaction-local custom GUC placeholder reverts to `''` (not `NULL`) once its transaction commits, so the RLS policy's `::uuid` cast threw on the very next transaction. Fixed with `NULLIF(current_setting(...), '')::uuid` (migration `567fa7545de9`).
4. **`expire_on_commit=True` (SQLAlchemy default) broke every commit-then-respond route** — after a service's `db.commit()`, FastAPI building the response from the same ORM object triggered a refresh query in a new transaction with no tenant context, which RLS denied, surfacing as `ObjectDeletedError`. Fixed by setting `expire_on_commit=False` on `SessionLocal` — a systemic fix, not a one-off, since this pattern (commit once, then serialize) is used by every service in this codebase.
5. **Email-only login is architecturally impossible** under correct RLS, since `users.email` is only unique per tenant. Resolved via ADR-017: login requires an explicit `tenant_id` in the request.
6. **`UserOut.model_validate(user)` can't work** — the ORM `User` model has `role_id`, not a `role` code string, so direct validation from the ORM object always failed. Fixed with an explicit `user_service.to_out()` serializer that resolves the role code.

## Three real bugs found and fixed this phase (all via actual execution, not inspection)
1. **8x too slow (20s for 2,000 rows against a 2.5s budget)**: the first implementation called `db.flush()` three times per row (6,000 round-trips for 2,000 rows). Fixed by deferring all flushes to the end of the batch.
2. **That fix immediately hit a real circular-FK violation**: `test_cases.current_version_id` and `test_case_versions.test_case_id` are mutually dependent (ADR-003's `use_alter`), and SQLAlchemy does not resolve that automatically without `relationship(post_update=True)`, which isn't configured. Fixed by inserting cases first with `current_version_id` left `NULL`, then versions/steps, then one single batched `UPDATE ... FROM` statement to link them back — not a per-row Python-side `UPDATE`.
3. **Still 8-11s after both fixes**: SQLAlchemy ORM's per-object unit-of-work/identity-map tracking (not network round-trips) was the dominant cost at ~8,000 constructed `Model(...)` instances. Fixed by switching to SQLAlchemy's documented Core-style bulk insert (`insert(Model)` executed against a list of plain dicts) — brought the service-level time down to ~1.2s, comfortably inside the 2.5s budget. Confirmed with `cProfile` that the *remaining* ~1.3s gap seen only when measuring through `TestClient` is that test harness's own double-threaded ASGI bridging overhead (time spent blocked on a thread lock, not in application code) — not present in a real deployed server, so the performance test now measures the service call directly for the hard budget, with a separate HTTP-level test covering functional correctness at the same scale.

## Two more real bugs found and fixed this phase (same two recurring classes as before, now documented as standing rules in ARCHITECTURE_DECISIONS.md)
1. **Step-count double-counting**: `step_count = sum(verdict_counts.values()) + verdict_counts.pop(None, 0)` counted the unexecuted (`NULL`-verdict) steps twice — `sum()` already included them before the separate `.pop()` added them again, so a 3-step case reported `step_count: 6`. Fixed by computing the total before popping the `None` key out.
2. **`autoflush=False` struck again, this time inside a single service call, not across a commit boundary**: `record_verdict()` set `step.verdict = "fail"` in memory, then immediately queried all of that case's step verdicts to recompute the rollup status — but with autoflush off, that SELECT read the *previous* verdict from the database, silently computing the wrong status (a case with a freshly-failed step still showed `in_progress`). Fixed with an explicit `db.flush()` between the mutation and the dependent query. Documented as a new standing rule in `ARCHITECTURE_DECISIONS.md` alongside the RLS-after-commit gotchas, since both stem from the same session configuration and are easy to re-trip on in Phase 7.

## One more instance of the recurring RLS-after-commit bug (now the third time — same root cause, same fix)
`add_link()` committed, then the route handler called `get_defect()` again to re-fetch for the response — a fresh RLS-protected query in a transaction with no tenant context, silently returning 404 instead of the defect that very much exists. Fixed by having `add_link()` return the already-loaded `Defect` object directly (its `to_out()` already re-asserts tenant context as required) instead of the route re-querying after the commit. This is the same class of bug as Phase 4/6's — the standing rule in `ARCHITECTURE_DECISIONS.md`'s ADR-007 addendum is clearly worth restating prominently before any future phase's `to_out`/route-handler pattern: never issue a fresh RLS-protected query after a commit without re-asserting tenant context first, and prefer returning already-loaded objects over refetching.

## Phase 9 scope note
Phase 9 as originally planned (`docs/MASTER_SPEC.md`'s phase list) bundled backend hardening together with an accessibility pass and a Playwright E2E suite "across all journeys." Since **no frontend screens exist yet** (every phase 2-8 was explicitly backend-only — confirmed with the user before starting this phase), the accessibility/E2E portions are impossible to do for real against a health-check page. Per explicit user direction, this phase was split: the backend-doable work (audit hardening, RLS verification, security review) is done now as Phase 9; the UI-dependent work moves to a new Phase 10 once frontend screens exist, rather than being silently skipped or faked.
