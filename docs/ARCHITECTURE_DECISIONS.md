# Architecture Decision Records (ADR)

Status legend: **Decided** (binding for implementation), **Open** (needs stakeholder sign-off before the affected module is built).

BRD source: BRD-QTH-INS-2026-V2.4. These ADRs resolve ambiguities in that document per the architecture-review notes supplied alongside it. None of these change business intent; they fix *how* an ambiguous or under-specified requirement is implemented.

---

## ADR-001: Test case lifecycle split into authoring/approval vs. execution state
**Status:** Decided

The BRD (FR-TC-001, §7.2) lists `Draft, Ready for Review, Approved, In Progress, Assigned, Passed, Failed, Blocked` as one lifecycle, but these are two different concerns: the *document* (is this test case trustworthy enough to run) and *a specific execution of it in a run* (did it pass this time).

**Decision:**
- `test_cases.status` (authoring/approval, governs FR-TC-003 approval gate): `draft`, `ready_for_review`, `approved`, `deprecated`.
- `test_run_cases.status` (per-run execution verdict, FR-EXEC-001): `pending`, `in_progress`, `passed`, `failed`, `blocked`, `ignored`.
- A test case can be `approved` and simultaneously have many `test_run_cases` rows in different states across concurrent/historical runs.
- Editing an `approved` test case creates a new `test_case_versions` row (see ADR-003) and does not change `status` unless the manager explicitly re-drafts it.

## ADR-002: Step references use foreign keys, not raw array indices
**Status:** Decided

The BRD uses 1-based `order` for `TestStep` but a 0-based example (`stepIndex: 2` for "Step 3") for defect linkage — a direct contradiction if indices are used as the join key.

**Decision:** Steps are rows, not array members. `test_case_version_steps.id` (UUID) is the join key everywhere a step must be referenced (`execution_steps.test_case_version_step_id`, `defects.test_case_version_step_id`). `step_number` is retained purely as a **1-based, human-facing display/ordering column** (matches BRD `order` field) and is never used as a lookup key. This eliminates the off-by-one ambiguity entirely rather than picking a side.

## ADR-003: Immutable test case versioning with execution pinning
**Status:** Decided

**Decision:** Every approval-worthy edit to an approved test case writes a new immutable row to `test_case_versions` (+ `test_case_version_steps` snapshot of all steps at that point), and `test_cases.current_version_id` advances. A `test_run_case` stores `test_case_version_id` captured **at run-case creation time**, so historical executions always report against the exact step text that was actually run, even if the test case is edited or re-approved later. `history` as a loose JSON blob (as the BRD literally describes) is rejected in favor of normalized version rows — required for FR-DEF compliance-grade traceability (defect → exact version → exact step).

## ADR-004: Execution state is normalized, not a single JSON blob
**Status:** Decided

The BRD's `TestRun.results` / `stepResults` / `executionTimes` maps are a denormalized, single-document shape. Per the supplied architecture guidance, this is explicitly rejected for the relational implementation.

**Decision:** Four normalized entities: `test_runs` (the cycle) → `test_run_cases` (one row per test case bundled into the run, carries the pinned `test_case_version_id` and rollup `status`) → `execution_steps` (one row per step per run-case, carries verdict `pass|fail|ignore`, `duration_ms`, `executed_by`, `executed_at`). This is required for concurrent execution safety, step-level reporting (FR-REP-001), and because a single wide JSON column cannot be indexed or queried efficiently at the volumes implied by FR-TC-002 (2,000+ cases).

## ADR-005: Defect-step linkage is many-to-many via a join table
**Status:** Decided

BRD FR-EXEC-003 implies one defect per failed step, but FR-DEF-002 and real triage practice require multiple defects to reference one step (duplicate reports) and, less commonly, one root-cause defect to span several steps/cases.

**Decision:** `defects` holds the primary context (`project_id`, `test_case_id`, `test_run_id`, `reported_by`, etc.) for the defect that was created *from* a specific execution event. `defect_links` is a separate join table (`defect_id`, `linkable_type`, `linkable_id`) enabling a defect to additionally reference other `execution_steps`, `test_cases`, or other `defects` (duplicate-of) without losing the original creation context. The "pill badge on the failed step" (FR-EXEC-003) is rendered from `execution_steps.id -> defect_links`, not from a single FK column on the step.

## ADR-006: Audit log is insert-only with hash chaining, not provably tamper-proof against DBAs
**Status:** Decided — residual risk tracked in KNOWN_GAPS

**Decision:** `audit_logs` rows are never updated or deleted by any application code path (no UPDATE/DELETE route exists in the service layer). Each row stores `prev_hash` and `record_hash = sha256(prev_hash || canonical_json(row))`, forming a hash chain per tenant, enabling detection of row tampering or deletion-by-renumbering. Database grants additionally `REVOKE UPDATE, DELETE` on `audit_logs` for the application role; only a separate, non-application migration role can alter the table. **This mitigates but does not cryptographically prevent** tampering by someone holding raw superuser/DBA credentials — that requires external WORM log shipping (e.g., write-once object storage) which is out of scope for this phase and recorded in `KNOWN_GAPS.md`.

## ADR-007: Tenant isolation enforced at both ORM query layer and PostgreSQL RLS
**Status:** Decided

**Decision:** `tenant_id` is never accepted from request payloads; it is derived server-side from the authenticated session on every request. Two independent layers enforce isolation so a bug in one does not cause a breach:
1. **Application layer:** a SQLAlchemy base repository that injects `WHERE tenant_id = :session_tenant_id` on every tenant-scoped query automatically.
2. **Database layer:** PostgreSQL Row-Level Security policies on every tenant-owned table, keyed to a `current_setting('app.current_tenant')` session variable set by the backend at the start of each request's DB transaction.
Platform-level tables (`tenants`, platform superuser accounts) are exempt from RLS and are only reachable via a separate Platform Administration API surface (see ADR-008).

**Addendum (migration `567fa7545de9`):** the policy predicate must be `tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid`, not a bare cast. A custom GUC placeholder that has only ever been set via `set_config(..., true)` (transaction-local) reverts to `''` — not `NULL` — once that transaction commits, so a bare `::uuid` cast throws `invalid_text_representation` on the next transaction instead of just failing the predicate (deny). `NULLIF(..., '')` converts the empty string to `NULL` first, so the comparison safely evaluates to `NULL`/false (default-deny) as intended.

**Addendum (SQLAlchemy session config):** `app.current_tenant` is transaction-LOCAL by construction (`set_config(..., true)`), so it does not survive past a `db.commit()`. `SessionLocal` is therefore created with `expire_on_commit=False` (`app/core/db.py`): the common service pattern — do work, `commit()` once, then have the route build a response from the same already-loaded objects — must not trigger a post-commit attribute refresh, because that refresh would run in a new transaction with no tenant context and RLS would deny it. Any service that truly needs to re-query after a commit must re-call `set_tenant_context` first.

**Addendum (Phase 6, recurring gotcha — read this before writing any read-after-write logic in a service):** `SessionLocal` also sets `autoflush=False`. A Python-side attribute assignment on an ORM object (e.g. `step.verdict = "fail"`) is **not** visible to a subsequent `db.execute(select(...))` in the same session unless something flushes first — the SELECT reads what's still committed in the database, not the pending in-memory change. This bit `execution_service.record_verdict()`: it set `step.verdict` then immediately called a helper that re-queried all of that case's step verdicts to recompute the case's rollup status, silently using the *previous* verdict and producing a wrong status. **Rule of thumb:** after mutating an object's columns, call `db.flush()` before any subsequent same-transaction query whose result depends on that mutation — don't rely on autoflush, it's off.

**Addendum (Phase 4, recurring gotcha — read this before writing any new `to_out`/serializer):** `expire_on_commit=False` only protects *attribute access* on already-loaded objects — it does **not** help a serializer that issues a **new** query against another RLS-protected table after a commit (e.g. building a `TestCaseOut` by querying `test_case_versions`/`test_case_version_steps` fresh, after the service that created the case already committed). That new query runs in a new transaction with no tenant context and RLS silently returns zero rows (`NoResultFound`/empty list), not an error that points at the cause. **Rule of thumb:** any `to_out()`/serializer function that itself queries an RLS-protected table must re-assert `set_tenant_context(db, str(<tenant_id known from the already-loaded object>))` as its first line, unconditionally — it's cheap (one `SELECT set_config`) and correct whether or not a commit happened in between. `project_service.to_out` escaped this only because `project_members` (its one extra query) happens to be RLS-exempt by omission, not by design — don't rely on that; prefer the explicit re-assertion in every new serializer.

## ADR-008: First-tenant-admin bootstrap via a Platform Owner role, outside tenant RBAC
**Status:** Decided

The BRD's RBAC matrix only defines `Admin/Manager/Tester` *within* a tenant, but someone must create tenant #1's first Admin, and the BRD says only "Admin" can create tenants (circular for tenant zero).

**Decision:** Introduce a `platform_owner` concept (a flag on a user row with no `tenant_id`, or a small dedicated `platform_admins` table — finalized in DATABASE_SCHEMA.md) used exclusively by the Platform Administration surface. A platform owner can create a tenant and provision its first tenant Admin user. Platform owners cannot access any tenant's test/project data — they are provisioning-only, keeping the "all insurance data is tenant-scoped" guarantee intact. Seeded via a one-time migration/CLI command, not a public signup form.

## ADR-009: GDPR/CCPA erasure reconciled with immutable audit trail via pseudonymization
**Status:** Decided

**Decision:** "Right to be forgotten" purges PII (`name`, `email`, free-text fields that may contain PII) from `users` and from the human-readable fields of historical `audit_logs`/`defects`/etc. by replacing them with a stable pseudonym (`user_<uuid>`), while the row itself, its `user_id` FK, timestamp, and action type are retained. The hash chain (ADR-006) is computed over a canonical form that already excludes mutable PII fields, so pseudonymization does not break chain verification. Full physical deletion of a user row is only permitted if the tenant has zero retained audit/compliance obligations for that user — flagged `KNOWN_GAPS` pending legal sign-off on retention periods per jurisdiction.

## ADR-010: Offline-first claim reinterpreted as resilient synchronous writes, not disconnected operation
**Status:** Decided

The BRD simultaneously requires "offline-first local storage" and "cloud-native multi-tenant" with no sync protocol defined — these are incompatible as literally written for a shared multi-tenant Postgres backend.

**Decision:** The product is server-authoritative (PostgreSQL is the single source of truth, per the stated constraint in the master prompt). "Offline-first" is satisfied as: (a) every execution-step toggle (FR-EXEC-002) is written synchronously to the backend immediately, with sub-50ms perceived latency via optimistic UI update + background confirm; (b) in-progress, not-yet-submitted form state (e.g., a defect being drafted) is held in browser storage only as a recovery buffer against accidental tab close, per the explicit "browser storage only for temporary UI state" engineering principle. True disconnected (no network) operation is **out of scope** for this phase; see `KNOWN_GAPS.md`.

## ADR-011: MFA implemented as a real, configurable mechanism; "simulation" means test-mode only
**Status:** Decided

**Decision:** `mfa_challenges` implements a genuine 6-digit TOTP-or-OTP challenge per FR-AUTH-003 (code, expiry, attempt counter, lockout after 3 failures). A per-tenant/per-environment config flag (`mfa_delivery_mode: real | simulated`) controls whether the code is actually sent via an email/SMS provider or simply logged/returned in non-production environments for test automation — the data model and enforcement logic are identical either way. No push-notification or hardware-key MFA in this phase.

## ADR-012: Attachments stored on disk/object storage, not as Base64 in PostgreSQL
**Status:** Decided

The BRD's `Attachment.data: string (Base64 data URL)` is rejected for storage (bloats the DB, breaks backup/restore performance, contradicts the engineering principle against storing blobs as the "primary database" content).

**Decision:** Client may still *upload* as Base64 or multipart; the backend decodes and writes bytes to a filesystem path (local volume now, swappable for object storage later per the "File Storage: local filesystem initially" stack note) and stores only `attachments(id, tenant_id, owner_type, owner_id, file_name, mime_type, storage_path, size_bytes, checksum, uploaded_by, uploaded_at)` in PostgreSQL.

## ADR-013: Currency, numeric precision, date/time conventions
**Status:** Decided

**Decision:** `projects.budget` is `NUMERIC(14,2)` plus a required `projects.currency_code CHAR(3)` (ISO 4217), defaulted from a per-tenant setting — never a bare float. All instants (`created_at`, `executed_at`, audit timestamps) are `TIMESTAMPTZ` stored in UTC; all calendar-only fields (`start_date`, `end_date`) are `DATE` with no timezone, interpreted in the tenant's configured timezone for display only. Millisecond execution timings (FR-EXEC-002/BR-09) are stored as `INTEGER duration_ms`, computed server-side from step-open/step-close `TIMESTAMPTZ` pairs rather than trusting a client-reported duration.

## ADR-015: `sessions` and `mfa_challenges` are exempt from tenant RLS
**Status:** Decided

Resolving a session cookie into a user requires looking the row up **before** the tenant is known — but ADR-007's RLS policy requires `app.current_tenant` to already be set to read any tenant-scoped row, which is circular for exactly these two tables.

**Decision:** `sessions` and `mfa_challenges` are excluded from the `tenant_isolation` RLS policy (migration `8c1a5e9a7b3f`); every other tenant-owned table keeps it. Security for these two tables instead rests on the session/challenge id being an unguessable random UUID primary key (the same trust model as a password-reset token) plus application-level checks (`expires_at`, `revoked_at`, `attempt_count`). Once a session row is resolved, its `tenant_id` becomes the trusted, server-derived context for the rest of the request (`set_tenant_context`), so every other table's RLS still applies normally from that point on. An admin-facing "list my tenant's active sessions" view filters by `tenant_id` explicitly in the query, same as any other tenant-scoped read — RLS is simply not the enforcement mechanism for these two bootstrap tables.

## ADR-016: Audit hash-chain writes are serialized per tenant with an advisory lock
**Status:** Decided

Two concurrent transactions appending audit rows for the same tenant could both read the same "last hash" before either commits, corrupting the hash chain (ADR-006).

**Decision:** `record_audit_event()` takes `pg_advisory_xact_lock(hashtext(tenant_id))` before reading the previous row's hash and inserting the new one. The lock is automatically released at transaction end (commit or rollback), serializing audit appends per tenant without blocking unrelated tenants or non-audit work.

## ADR-018: Manager's project edit/delete/member-management authority is scoped to assigned projects; viewing is tenant-wide
**Status:** Decided

BRD §3.2 lists "Create/Edit/Delete Projects: Manager — Yes (Assigned)" and "Allocate Team Members: Manager — Yes" (no qualifier) — the parenthetical appears on some rows but not others, and the BRD never defines what "assigned" means operationally for a Manager (project ownership? membership? both?).

**Decision:** "Assigned" means the Manager is either the project's `owner_id` or a row in `project_members` for that project. This gate applies uniformly to `PATCH /projects/{id}`, `DELETE /projects/{id}`, and both member-management endpoints for the Manager role — the member-management row's missing "(Assigned)" qualifier is treated as an omission, not an intentional broader grant, since allowing an unassigned Manager to add/remove members on a project they have no other authority over would be an inconsistent privilege escalation path. Admin bypasses this check entirely (BRD's "Global tenant visibility"). **Viewing** (`GET /projects`, `GET /projects/{id}`) is tenant-wide for both Admin and Manager — only Tester's visibility is restricted to assigned projects (FR-PROJ-002's explicit acceptance criterion: "Testers only see assigned projects in project selectors"). The project creator is automatically added to `project_members` on creation, so a Manager who creates a project is immediately "assigned" to it and can edit/delete what they just made.

## ADR-019: Test case authority is project-assignment-gated only for Tester, not Manager
**Status:** Decided

ADR-018 scoped *project-entity* edit/delete to "assigned" Managers because the BRD explicitly marks those RBAC rows "(Assigned)". The test case rows in the same matrix (`Create & Edit Test Cases`, `Delete Test Cases`, `Approve Test Cases`) carry no such qualifier for Manager — only Tester's rows are qualified ("Own Drafts Only" for delete) and FR-PROJ-002 explicitly restricts Tester's *project visibility* to assigned projects.

**Decision:** Test case operations (`create`, `edit`, `submit-review`, `approve`) are gated purely by the `testcase.*` permission flags for **Admin and Manager** (tenant-wide authority, no project-assignment check), matching the BRD matrix's lack of a qualifier for those roles. **Tester** is additionally required to be assigned to the test case's project (owner or `project_members` row) — consistent with Tester's restricted project visibility elsewhere. `DELETE /test-cases/{id}` is the one operation with an explicit extra rule for every role: Admin/Manager may delete any case; **Tester may delete only their own `draft`-status cases** ("Own Drafts Only," BRD §3.2) — enforced in the service layer rather than via the permission-flag dependency, since it's a data-ownership condition, not a role-wide grant.

## ADR-020: Editing a draft mutates in place; editing an approved case always forks a new version and reverts to Draft
**Status:** Decided

FR-TC-001's acceptance criterion only explicitly covers one case: "Adding or modifying steps on an approved test case automatically increments the version counter and archives the previous state." It doesn't say what happens when editing a `draft` or `ready_for_review` case (never yet approved, never yet pinned by any execution), nor what the case's `status` becomes after a post-approval edit.

**Decision:**
- While `test_cases.status` is `draft` or `ready_for_review`: edits (title, priority, assignee, steps) mutate the **current** `test_case_versions`/`test_case_version_steps` rows in place — no new version is created, since nothing has been approved or executed against this version yet, so there is no history to protect (ADR-003 only requires preserving versions once they matter for traceability).
- While `status` is `approved`: **any** edit creates a new `test_case_versions` row (version N+1, fresh step snapshot) and reverts `test_cases.status` to `draft`, matching the state machine diagram in BRD §7.2 ("Rejection / Rework" arrow back to `[Draft] (Version Increments +1)"). The case must go through `submit-review` → `approve` again before it can be used in a new test run. Already-created `test_run_cases` rows keep pointing at the old, now-superseded version (ADR-003's pinning), so in-flight/historical executions are unaffected.

## ADR-021: CSV import is tenant-scoped (not project-scoped) and processed synchronously, not staged/polled
**Status:** Decided — corrects a Phase 0 planning error

**Problem found during implementation:** the Phase 0 `API_SPECIFICATION.md` put CSV import under `POST /projects/{id}/test-cases/import`. But FR-TC-002's CSV header list includes a per-row **Project Name** column with its own acceptance criterion ("Project name is verified against active tenant projects") — meaningless if the endpoint already pins the project via the URL path. The BRD's own design intends a single CSV to span **multiple projects** within one tenant (consistent with the "250 legacy underwriting cases" bulk-migration journey, which doesn't imply a single project).

**Decision:**
- `POST /test-cases/import` is **tenant-scoped**, not project-scoped. Each row resolves its own project by name (case-insensitive, matching `uq_projects_tenant_name_ci`); a row whose project doesn't exist in the tenant is a per-row validation error, not a whole-batch failure.
- Authorization is per-row: for each resolved project, the normal ADR-019 rule applies (Admin/Manager tenant-wide; Tester must be assigned to that specific project) — so one CSV can partially succeed for a Tester across several projects they're variously assigned to or not.
- `GET /projects/{id}/test-cases/export.csv` stays project-scoped (export naturally pins to one project's test cases; no BRD ambiguity there).

**Second decision, same ADR — synchronous processing, not a staged batch + polling design:** the originally-drafted `GET /test-cases/import/{batchId}/report` polling endpoint is dropped. NFR 8.1 caps the requirement at 2,000 rows in under 2.5s — well within what a single synchronous request can parse, validate, and commit. Building a staging table, a background job, and a polling endpoint for that volume would be unrequested infrastructure (no job queue is in the approved tech stack). `POST /test-cases/import` parses the whole CSV, validates every row, inserts all valid rows in one transaction, and returns the full per-row report directly in the response body — "staged" (ARCHITECTURE.md's import architecture) now means "validated in memory before any row is written," not "written to a separate DB staging table."

## ADR-022: Finishing a test run is a Manager/Admin sign-off gate; a new `testrun.finish` permission is added
**Status:** Decided

BRD §3.2 only lists "Create & Launch Test Runs: Yes/Yes/Yes" (all three roles) — there is no separate RBAC row for *closing* a run. But closing a run computes and locks final verdicts (FR-EXEC-001: "Finishing a run sets `finishedAt` and calculates final run verdicts"), which is a formal sign-off action analogous to test case approval (`testcase.approve`, Manager/Admin-only).

**Decision:** A new permission, `testrun.finish`, is seeded for Admin and Manager only (not Tester) — symmetric with the approval gate, and consistent with the Manager persona's BRD-stated responsibility for "test run assignment" and sign-off, versus the Tester persona's "test run execution." Creating and executing a run remains open to all three roles via the existing `testrun.create`/`executionstep.record` permissions; only the final close-out is gated.

## ADR-023: Execution steps are pre-created (verdict=NULL) at test-run-case creation, not lazily on first open
**Status:** Decided

**Decision:** When a test case is bundled into a run (`test_run_cases` row created), one `execution_steps` row is created immediately for every step of the pinned `test_case_version` (`verdict=NULL`, `opened_at=NULL`). This guarantees `GET /test-run-cases/{id}/steps` always returns the complete step list immediately after run creation — matching FR-EXEC-001's "unexecuted test cases default to Pending" — rather than requiring the client to infer unexecuted steps from an initially-empty list. `POST /execution-steps/{id}/open` and `.../verdict` act on these pre-existing rows (UPDATE, not INSERT).

## ADR-024: Test-run-case status is recomputed from scratch from step verdicts, not tracked incrementally; steps are re-verdictable
**Status:** Decided

BRD Journey 4 describes re-executing a previously-failed step after a fix and marking it Pass **within the same test run** ("Tester marks Step 3 as Pass. The test case status turns Passed") — so `POST /execution-steps/{id}/verdict` must be callable more than once per step, not just on first submission.

**Decision:** `record_verdict()` always recomputes `test_run_cases.status` from the full current set of that case's `execution_steps` verdicts, rather than incrementally patching state: `status = 'failed'` if any step is `fail`; else `'passed'` if every step has a non-null verdict (`pass`/`ignore` both count as resolved); else `'in_progress'` if at least one step has a verdict; else `'pending'`. This is idempotent and self-correcting — re-verdicting a step (e.g., Fail → Pass after a fix) naturally flips the case's rollup status without any special-case "undo" logic. `started_at` is set once, on the first verdict ever recorded for the case, and never cleared; `completed_at` is refreshed to now whenever the recomputed status is `passed`/`failed`, and cleared otherwise (e.g., a corrected verdict that reopens the case).

**Addendum (Phase 10.9):** the backend's re-verdict support had no corresponding frontend control. `ExecutionConsole.tsx`'s `StepCard` only rendered the Pass/Fail/Ignore buttons for the one step with `verdict === null` (`isCurrent`) — once a step had *any* verdict, including a `Fail` that Journey 4 describes fixing and re-running, there was no way to invoke `POST /execution-steps/{id}/verdict` a second time from the UI at all. Caught by the Phase 10.9 E2E suite (`journey4-defect-lifecycle.spec.ts`) attempting to re-verdict a failed step and finding no button to click — not a test-script mistake, a real shipped gap from Phase 10.5. Fixed by adding a "Re-run step" disclosure control to any step that already has a verdict and isn't current, revealing the same three verdict buttons on demand (not shown unconditionally, to avoid accidental misclicks on a settled step).

## ADR-025: Only `approved` test cases can be bundled into a test run
**Status:** Decided

The BRD's state machine (§7.2) shows `Approved → Assigned/In Progress → Passed/Failed/Blocked` as the only path into execution — `draft`/`ready_for_review` cases never appear on that path, and FR-TC-003 exists specifically to gate "formal execution" behind Manager/Admin sign-off.

**Decision:** `POST /projects/{id}/test-runs` rejects (per-row validation error, not a whole-request failure) any `test_case_id` whose current `status` isn't `approved`. This also means the version pinned into `test_run_cases.test_case_version_id` (ADR-003) is always an approved, reviewed version — never a draft snapshot.

## ADR-026: Defect status transitions are strictly sequential; no skipping, no reopening
**Status:** Decided

FR-DEF-001 states the transitions "follow the defined state machine: New → Open → Fixed → Verified → Closed," and §7.2's diagram shows only forward arrows — no path back from `Closed`/`Verified` to an earlier state, and no explicit "reopen" transition.

**Decision:** `PATCH /defects/{id}/status` only accepts a transition to the **immediate next** status in that fixed sequence (`New→Open→Fixed→Verified→Closed`) — no skipping ahead (e.g. `New→Fixed` directly) and no moving backward. There is deliberately no "reopen a closed defect" transition: if a fixed/verified issue recurs, BRD Journey 3's pattern (a failed execution step opens a *new* defect, FR-EXEC-003) is the supported path, not resurrecting an old one — inventing a reopen transition the BRD never describes would be scope creep. Per BRD §3.2, only the transition *to* `Closed` is role-gated (Manager/Admin only, via the existing `defect.close` permission); every other transition is available to any of the three roles that can otherwise access the defect (consistent with "Log Defects: Yes/Yes/Yes" and the matrix's silence on gating `Open`/`Fixed`/`Verified` specifically — BRD Journey 4 shows a Manager performing `Verified`→`Closed`, but nothing in the RBAC matrix restricts Tester from the earlier transitions, so this implementation doesn't invent that restriction either).

## ADR-027: Reporting/Dashboard scope, metric definitions, and the "assignee" dimension
**Status:** Decided

Several things FR-DASH/FR-REP leave unstated:

1. **Tester's viewing scope on the Dashboard.** The RBAC matrix's only explicit qualifier is on the *Reporting* row ("View Executive Reporting & Charts: ... Tester Restricted to Assigned"); the Dashboard FRs carry no such qualifier. **Decision:** apply the same assigned-projects restriction to both, for consistency with every other module in this codebase (ADR-019 et al.) — a QA Director-style "organization at a glance" view for a Tester role would otherwise be the one inconsistent exception in the whole system.
2. **What "Status (Passed, Failed, Pending, Blocked)" refers to.** Those four values are `test_run_cases.status`, not `test_cases.status` (whose enum is `draft/ready_for_review/approved/deprecated` — a different lifecycle entirely, ADR-001). **Decision:** the `status` reporting metric aggregates `test_run_cases.status`.
3. **What "Assignee" means for the Defects grouping dimension.** `defects` has no assignee column (BRD's own schema for `Defect` doesn't include one) — the closest analogous person-dimension is `reported_by`. **Decision:** grouping defects "by Assignee" groups by `reported_by`. For the `priority` metric (test cases), Assignee is `test_cases.assignee_id`; for the `status` metric (test run cases), Assignee is `test_run_cases.assigned_to` (frequently `NULL`/"Unassigned," since no run-case assignment endpoint exists yet — not a gap, just an unused optional column).
4. **PDF generation (resolves GAP-08).** FR-REP-002's own acceptance criterion describes a "Printable view [that] strips navigation menus and formats tables cleanly across standard A4/Letter page bounds" — that is browser print-CSS behavior, a frontend concern, not a server-rendered PDF file. **Decision:** the backend generates the CSV compliance export only (`GET /reports/compliance-export`, CSV with a tenant/timestamp/reporting-officer header per FR-REP-002); no PDF-generation library is added to the stack. "PDF" is produced by the browser's native print-to-PDF against a print stylesheet, built when the Reporting screen's UI is implemented.

## ADR-028: `GET /users` is readable by anyone who can manage project members, not just `user.manage` holders
**Status:** Decided — found while building the Projects UI (Phase 10.2)

FR-PROJ-002 lets a Manager "Allocate Team Members to Projects," but `GET /users` was gated solely by `user.manage` (Admin-only, ADR-014's seed). A Manager assigning a teammate to a project has no way to see who exists in the tenant to pick from — the UI for a BRD-required feature was otherwise unbuildable.

**Decision:** `GET /users` accepts either `user.manage` (Admin) or `project.members.manage` (Admin/Manager) — a new `require_any_permission(*codes)` dependency (`app/core/auth.py`), analogous to the existing `require_permission`. This exposes only the same basic directory fields `UserOut` already returns (id, email, name, role, is_active, created_at — never `password_hash`), which is ordinary tenant-directory information, not a privilege escalation: a Manager already has tenant-wide authority over projects and test cases (ADR-019); knowing colleagues' names/emails/roles to assign them is strictly narrower than that. Tester still cannot list users (neither permission is seeded for Tester).

## ADR-029: Audit log read access is a new `audit.view` permission, Admin-only
**Status:** Decided — found while building the Administration UI (Phase 10.8)

BR-13 had a write path (every module appends to the hash chain, ADR-006) and one narrow read surface (`/dashboard/activity-stream`, the last 10 events for the Dashboard card), but no endpoint for browsing or filtering the full tenant audit trail — the BRD's "Administration → Audit Logs" screen (`docs/MASTER_SPEC.md` module map) had nothing to call. No existing permission code fit: `report.view` is granted to all three roles (Tester included, per the seed migration), but the BRD's RBAC line is unambiguous — "**Admin**: full tenant control, user/role management, **audit access**, all project/testing operations" names audit access as an Admin-specific capability, not a reporting one.

**Decision:** added `audit.view` as its own permission (migration `a3c9e1f2b4d7`), granted to `admin` only — not folded into `report.view` (wrong audience) and not into `user.manage` (orthogonal: an Admin managing users and an Admin auditing the tenant are different concerns that happen to share a role today, but modeling them as one permission would make a future "compliance auditor" role, who needs `audit.view` without `user.manage`, impossible without a migration). `GET /audit-logs` supports `action`/`entity_type`/`user_id` filtering and pagination (capped at 200/page); a separate `GET /audit-logs/verify-chain` endpoint re-walks the full chain and recomputes every hash server-side (the same algorithm `test_audit_integrity.py` already exercised against real data in Phase 9), surfacing tamper-evidence as a UI-visible pass/fail rather than only a test assertion — this is what makes the hash chain's value visible to an actual compliance officer, not just to the test suite.

## ADR-017: Login requires an explicit tenant identifier; there is no global email lookup
**Status:** Decided

`users.email` is only unique **per tenant** (`uq_users_tenant_email`, ADR-007/DATABASE_SCHEMA) — the same email may legitimately belong to different people at different carriers. Since `users` correctly keeps tenant RLS (ADR-007), a login request of just `(email, password)` can't resolve which tenant to even query: without `app.current_tenant` set, RLS returns zero rows for every tenant, and there is no RLS-exempt global email→tenant index to fall back on (deliberately — that would reintroduce a cross-tenant enumeration surface, ADR-007's whole point).

**Decision:** `POST /auth/login` requires `tenant_id` explicitly in the payload, alongside `email`/`password` (the same pattern as Slack's workspace URL or Okta's org-specific login page). The backend sets `app.current_tenant` to the supplied `tenant_id` *before* querying `users`; if the tenant, email, or password is wrong, the result is identical in every case ("Invalid credentials") — the RLS-scoped query simply returns no matching row, so no tenant/email enumeration is possible (satisfies FR-AUTH-002's "clear, non-leaking error feedback"). How the frontend obtains `tenant_id` before showing the login form (subdomain routing, a saved "organization" picker, a magic link) is a UI concern for a later phase, not a backend contract change.

## ADR-014: Roles and permissions are modeled as data, not hardcoded enums, without contradicting "no custom roles in v1"
**Status:** Decided

The BRD's RBAC matrix (§3.2) is fixed to exactly `Admin/Manager/Tester` with no mention of custom roles, yet §4 of the master prompt lists `roles`/`permissions` as tables to evaluate.

**Decision:** `roles` and `permissions` tables exist and are seeded with exactly the three BRD roles and their fixed permission grants (matching §3.2 verbatim), queried by the backend's authorization layer instead of hardcoding role checks in route handlers. Tenants cannot create custom roles or alter the seeded permission set in this phase — the tables exist for correctness/auditability of authorization, not for a role-builder feature. Any future custom-RBAC feature is a scope change requiring the BRD's formal change-request process (§13).

## ADR-030: Login/MFA rate limiting via `slowapi`, per-client-IP, in-memory storage
**Status:** Decided — found during a post-Phase-10 security hardening pass (GAP-16)

GAP-16 flagged that `POST /auth/login` had no throttling at all — only the post-login MFA code had a 3-attempt lockout — and explicitly required an explicit decision before adding anything, since no rate-limiting library was in the originally approved stack.

**Decision:** `slowapi` (a FastAPI/Starlette-native wrapper over the `limits` library), keyed by client IP via its built-in `get_remote_address`, at 10 requests/minute on both `POST /auth/login` and `POST /auth/mfa/verify` (`app/core/rate_limit.py`). A 429 response is normalized into the app's standard `{"data": null, "error": {...}}` envelope (`app/main.py`'s `RateLimitExceeded` handler), not slowapi's default plain-text response. In-memory storage was chosen over a Redis-backed one since no cache layer exists in the stack and this is a single-process deployment; the gap's own closing condition explicitly names per-IP as an acceptable option, with a Redis-backed limiter reserved for if this needs to scale to multiple processes. A per-`(tenant_id, email)` key would be more precise but isn't a drop-in `key_func` — slowapi's key functions read the request/connection, not the JSON body — so it's deferred rather than built speculatively.

Testing note: rate limiting is **disabled by default** for the whole backend test suite (`conftest.py`'s `_disable_rate_limiting` autouse fixture) — with it left on, 74+ tests' worth of logins against the same TestClient "IP" would trip the limiter well before the suite finishes. The one dedicated test (`test_rate_limiting.py`) explicitly re-enables and resets the limiter for just itself.

## ADR-031: Foundation hardening pass — logging, Docker health/restart, env-sourced DB credentials, UI shell completion
**Status:** Decided — found during a gap audit against the original foundation build prompt

A later audit against the original foundation task list (Docker Compose, health checks, logging, UI shell) found several items the fast-moving module-by-module phases had never circled back to: no backend logging at all beyond uvicorn's own access log; `docker-compose.yml` had a health check only on `db`, no `restart:` policy on any service, and hardcoded plaintext credentials (GAP-11); and the UI shell was missing breadcrumbs and a notification area, with the profile area being plain text rather than a usable control.

**Decisions:**
- **Logging**: plain stdlib `logging` (`app/core/logging.py`), one stream handler to stdout, configured once at import time from `settings.log_level`. An ASGI middleware (`app/main.py`) logs method/path/status/duration per request. No structured JSON/correlation-ID logging was added — this is a single-process dev/early-stage deployment with no log aggregator in the stack to justify it; revisit if a real log pipeline (e.g. shipped to a SIEM) is added.
- **Docker health/restart**: added `healthcheck:` to `api` (hits `GET /api/v1/health` via `python -c urllib.request`, avoiding adding `curl` to the slim image) and `web` (`wget --spider`), and `restart: unless-stopped` to all three services. Both new health checks target `127.0.0.1` explicitly, not `localhost` — Alpine/busybox resolves `localhost` to `::1` first, and both `uvicorn`/Vite only bind IPv4 by default, so a `localhost` health check connection-refuses forever even though the service is actually up (caught by driving the actual containers, not by reading the compose file).
- **Credentials**: `docker-compose.yml` now sources `POSTGRES_PASSWORD` as a required (`${VAR:?...}`) substitution and `APP_DB_PASSWORD`/`POSTGRES_USER`/`POSTGRES_DB` as defaulted substitutions, read from a new gitignored root `.env` (template: `.env.example`). The `qtesthub_app` role's password, previously hardcoded directly in the baseline/RLS migration, is now set by a new migration (`c1d2e3f4a5b6`) from `APP_DB_PASSWORD`, defaulting to the original value so existing dev/test setups are unaffected. This doesn't eliminate GAP-11's weak dev default (the `.env.example` placeholder is still `change_me_dev_only`) — it moves the *mechanism* from "hardcoded, uneditable without a code change" to "operator-configurable per environment," which is the actual gap that mattered.
- **UI shell**: added `Breadcrumbs.tsx` (derived from the route path, with a static segment→label map; dynamic id segments render as a generic "Detail" crumb rather than an extra per-route lookup), `NotificationBell.tsx` (an honest empty-state dropdown — no backend notification feed exists yet, so it says "No new notifications" rather than fabricating items), and `UserMenu.tsx` (the former static "name · role" text is now a dropdown with a sign-in confirmation line and the logout action, replacing the always-visible Logout button). All three are hand-rolled with local component state (no Radix/shadcn dependency was ever actually installed despite the `components/ui/` naming — matching the existing pattern in `dialog.tsx`), avoiding a new dependency for click-outside-to-close behavior.

## ADR-032: Auth/tenant hardening pass — tenant status enforcement, password reset, idle timeout, real MFA delivery, Platform Administration UI
**Status:** Decided — found during an audit against the original authentication/tenant/RBAC build prompt

A later audit against the original auth/tenant/RBAC spec (separate from the BRD feature phases) found several gaps the module-by-module phases never circled back to, the most serious being that tenant status was defined and mutable but never actually enforced.

**Decisions:**
- **Tenant status enforcement**: `auth_service.start_login` checks `Tenant.status == 'approved'` *after* credentials are verified, not before — so ADR-017's generic "Invalid tenant, email, or password" error still fires first for any wrong credential, and a non-approved tenant's status is never learnable without a valid password. `core/auth.get_current_context` performs the same check on every authenticated request (not just at login), so suspending a tenant immediately cuts off any already-open session rather than only blocking new logins. As a consequence, `platform_service.create_tenant_with_admin` now sets a newly-provisioned tenant's status to `approved` directly, rather than leaving it at the `pending` default: there is no self-service tenant signup flow in this system, so creating a tenant through the platform-admin-only endpoint already *is* the approval decision. `pending` remains a valid, reachable status (a platform admin can set it via `PATCH /platform/tenants/{id}/status`) for a future self-service signup path, but nothing currently puts a tenant into it automatically.
- **Admin password reset**: `POST /users/{id}/reset-password` (new, `user.manage`-gated) sets a new password hash and revokes every one of that user's existing sessions, so a reset can't be bypassed by a session opened before the compromise was discovered. No self-service "forgot password" flow was added — that needs its own token/expiry/email design and wasn't named as a requirement; only the admin-initiated path was built.
- **Idle session timeout**: `Settings.session_ttl_minutes` existed but was read nowhere. Added `sessions.last_seen_at` (migration `d2e3f4a5b6c7`), updated on every authenticated request; `get_current_context` now revokes a session whose `last_seen_at` is older than `session_ttl_minutes` (default 30 min), independent of and in addition to the existing absolute `expires_at` check (12h by default, set after MFA verification).
- **MFA "real" delivery mode**: previously schema/config-only (`mfa_delivery_mode: "real"` was a valid value with no code path). Added `app/core/mfa.send_mfa_code`, an SMTP email sender used only when `MFA_DELIVERY_MODE=real`; it fails loudly with a new `ConfigurationError` (500, `configuration_error`) if `smtp_host` isn't set, rather than silently not sending the code. No SMS/push/hardware-key provider was added — the stack never named one, and picking a specific third-party service needs real credentials this environment doesn't have. "Simulated" mode (the default outside production) is unchanged: the code is still returned directly in the API response.
- **Platform Administration UI**: added `frontend/src/routes/PlatformAdmin.tsx` at `/platform-admin`, linked only from a small footer link on the tenant Login page — deliberately not part of the main app shell/nav, preserving ADR-008's separation between Platform Administration (HTTP Basic against `platform_admins`) and tenant session auth. Credentials are held only in React component state for the duration of the page, never persisted to storage or cookies. Lists tenants with status badges, creates a tenant + first Admin, and approves/suspends tenants inline, all via the pre-existing `/platform/*` endpoints.

Testing note: the suite's `platform_admin` fixture and `_bootstrap_tenant` helper in `test_auth_flow.py` already exercised tenant creation, but every test that logged in right after bootstrapping relied on tenant status never being checked — once enforcement was added, bootstrap had to start tenants `approved` (see above) or essentially every existing auth test would have broken. New coverage: `tests/test_auth_hardening.py` (suspended/pending login rejection, mid-session suspension, password-reset session revocation, idle timeout, real-mode configuration-error).

## ADR-033: Project Portfolio hardening — list search/filter/sort/pagination, metrics, deletion-guard fix, optional manager FK
**Status:** Decided — found during an audit against the original Project Portfolio Management build prompt

An audit against the original project-portfolio spec found the list screen had none of the explicitly-requested search/filter/sort/pagination, no project-level metrics were surfaced anywhere, the deletion guard was narrower than it looked (and had a latent bug), and the "Manager" field had no relational identity. Two other findings from that same audit were **not** acted on because they are already-documented, deliberate decisions, not gaps: Manager's tenant-wide list visibility (ADR-018, FR-PROJ-002's own acceptance criterion) and `region` being free text (resolved during Phase 3, see the bottom of `KNOWN_GAPS.md`).

**Decisions:**
- **List search/filter/sort/pagination**: `GET /projects` gained `search` (case-insensitive name substring), `domain`/`status`/`priority` (exact-match filters), `sort` (a whitelisted column name, optionally `-`-prefixed for descending), `page`/`page_size` (capped at 100). The response shape changed from a bare array to `{items, total}` — this matches the pagination envelope `API_SPECIFICATION.md` already documented for list endpoints generally but which nothing had actually implemented yet. This is a breaking change to `GET /projects`'s response shape; every caller in the frontend and test suite was updated in the same pass (`DefectsList.tsx`'s project-filter dropdown now requests `page_size=100` to populate a complete list, since a filter dropdown has no pagination UI of its own).
- **Project-level metrics**: `ProjectOut` gained `test_case_count`, `approved_test_case_count`, `test_run_count`, `open_defect_count`. Computed via one grouped `GROUP BY project_id` aggregate query per module (test cases, test runs, defects) across all projects in a list response, not a per-project query — avoiding N+1 for what could otherwise be an expensive list endpoint.
- **Deletion guard fix**: the existing guard only checked for test runs with `finished_at IS NULL`. Since `test_cases`/`test_runs`/`defects` all FK to `projects` with no `ON DELETE CASCADE` (deliberately — physically destroying test history/audit-relevant data is never safe), a project with *finished* runs or any test cases at all would pass the guard and then hit a raw, unhandled `IntegrityError` from Postgres on the actual `DELETE` — a real bug, not just a narrower-than-documented check, found while writing the test the original audit flagged as missing. Fixed by checking for the existence of any test cases, test runs, or defects (any status) before attempting the delete, raising a clean `ConflictError` instead.
- **`manager_user_id`**: `manager_name` remains a free-text field (CSV import, external/contracted managers who aren't system users, and existing data all depend on it staying optional and simple), but a new nullable `manager_user_id` FK to `users` was added alongside it, validated to belong to the tenant when supplied. The frontend's project form shows an optional "Linked manager account" picker; leaving it unset is normal and expected for a manager who isn't a tenant user.

Testing note: because `GET /projects`'s response shape changed, `tests/test_rls_isolation.py`'s cross-tenant list check and two assertions in `tests/test_projects.py` needed updating to read `response["items"]` instead of treating the response as a bare list — this is a mechanical consequence of the shape change, not a behavior regression.

**Status:** Decided — found during an audit against the original Test Case Management build prompt

An audit against the original Test Case Management spec found the "repository" half of the module (search/filter/sort/pagination) was entirely unbuilt despite solid versioning/lifecycle/RBAC underneath, plus several smaller gaps: no step reorder/duplicate UI, no version diff, a missing `description` field, a dead `assignee_id` column, an unreachable `deprecated` status, and — the one finding with real security relevance — no file-type validation on attachments at all.

**Decisions:**
- **Repository search/filter/sort/pagination**: `GET /projects/{id}/test-cases` gained `search`/`priority`/`status`/`assignee_id`/`sort`/`page`/`page_size`, returning `{items, total}` — the same pattern as ADR-033's Project Portfolio list (and the same breaking response-shape change, handled the same way: every caller in the frontend and test suite updated, including the bulk-import test which now asserts `total` rather than fetching all 2000 rows through a paginated endpoint).
- **Step reorder/duplicate**: both were already correctly supported at the data level — `_write_version`/the in-place-edit path renumber steps sequentially from whatever order the client submits, so reordering was always just a matter of resubmitting steps in a different order. Only the UI was missing. Added move-up/move-down (`useFieldArray.move`) and duplicate (`useFieldArray.insert`) buttons to `TestCaseForm.tsx`, plus an Enter-key-on-the-action-field shortcut that inserts a new blank step immediately below, for faster entry.
- **Version comparison**: added `GET /test-cases/{id}/versions/compare?from=X&to=Y`, computing a title/description-changed flag and a per-step diff keyed by `step_number` (since steps are never referenced by array index, ADR-002) with change types `unchanged`/`added`/`removed`/`modified`. The frontend's Version History card became clickable (expand-to-view that version's full content and author) with a Compare Versions picker rendering the diff color-coded inline.
- **`description`**: added to `test_case_versions` (not `test_cases`) — versioned alongside title/steps per ADR-003's immutable-snapshot model, so an edit to an approved case's description forks a new version exactly like a title or step change does, rather than being a side-channel mutable field that would undermine the "complete historical snapshot" guarantee.
- **Assignee wiring**: `assignee_id` already existed as a real FK but had no form field, list column, or filter in the UI — all three were added. No RBAC change was needed since assignment was always just a plain field, not a permission gate.

Terminal: deprecating an already-deprecated case is a 409, not a no-op, so a caller can't silently "succeed" against a case that's already retired.
- **Attachment file-type allowlist**: `attachment_service.upload_attachment` now rejects any file whose extension isn't in an explicit allowlist (images + common documents) before even reading the file size — checked by extension, not the client-supplied `Content-Type` header, which a malicious or careless client can set to anything. Testing note: as with ADR-033, the `GET /test-cases` response-shape change required updating `TestRunsList.tsx`'s approved-case picker (now requests `page_size=100` to populate a complete list for bundling into a run) and several existing test assertions across `test_test_cases.py` and `test_csv_import.py`.

## ADR-035: CSV import hardening — duplicate detection, row-count cap enforcement, downloadable error report, file validation
**Status:** Decided — found during an audit against the original CSV bulk import/export build prompt

An audit against the original CSV import spec found the core parsing/row-validation/RBAC logic solid and precisely matching the spec (header format, step encoding, per-row errors), but five named functionality/rule items were missing: duplicate detection, server-side enforcement of the 2,000-row cap, a downloadable error report, meaningful file validation, and three of the spec's eight named test scenarios.

**Decisions:**
- **Duplicate detection**: implemented in-service, not as a DB constraint. `import_test_cases` preloads `(project_id, lower(title))` pairs for every project referenced in the file and tracks a `seen_in_batch` map while processing rows, flagging a row whose title already exists in that project (in the DB, or earlier in the same file) as an error naming the conflicting row number. Deliberately scoped **per-project**, not tenant-wide (the same title in two different projects is normal, not a duplicate) and **not** promoted to a DB-level unique constraint the way `projects.name` has one — that would change the ordinary single-test-case creation path's behavior too, which the spec doesn't ask for and which could block legitimate same-titled cases in different test suites within a project.
- **Row-count cap**: `import_test_cases` now materializes the full row list before validating anything (`rows = list(reader)`), checks it against `settings.csv_import_max_rows` (2000), and rejects the whole import with a clear message if exceeded — before any project/user lookups or DB writes, so an oversized file never does partial work.
- **Downloadable error report**: implemented entirely client-side in `ImportDialog.tsx` — a "Download Error Report (CSV)" button builds a CSV blob from the `ImportReport.rows` the API already returned and triggers a browser download. No new backend endpoint, no persisted import-batch record: the report data was already in hand, and adding server-side file generation/storage for it would contradict ADR-021's deliberate synchronous, non-staged design.
- **File validation**: added three checks ahead of the existing UTF-8 decode check — a `.csv` extension requirement, an empty-file rejection, and a `csv_import_max_bytes` (5MB) size cap — all returning a clear `ValidationAppError` (422) before the upload is even parsed as CSV.
- **Test coverage**: added the three previously-missing named scenarios. Special characters: Unicode, emoji, embedded commas/quotes in both title and step fields, round-tripped through parse→store→retrieve. Concurrent imports: two real concurrent uploads (via `ThreadPoolExecutor`, two separate `TestClient` instances sharing the authenticated session cookie) against the same project with distinct titles, asserting both succeed independently and the final count is the exact sum — this checks for gross corruption/deadlocks under genuine concurrent access, not full database-isolation-level guarantees, which is adequate confidence for this deployment's scale.

Testing note: the existing bulk-import performance test (`test_bulk_import_2000_rows_under_2_5_seconds`, NFR 8.1) is pre-existing flaky infrastructure, not a consequence of this pass — confirmed by re-running it in isolation (passes consistently in under 1s) every time it failed under full-suite parallel load; left as-is per this project's standing discipline of not touching a passing/pre-existing test on a hunch.

## ADR-036: Test Execution Engine hardening — console context display, live timer, run editing/add-remove cases, assignment, pause/resume, a real concurrency bug fix
**Status:** Decided — found during an audit against the original Test Execution Engine build prompt

An audit against the original spec found the core verdict-rollup/version-pinning/timing logic correct, but the Execution Console displayed almost none of its named context fields, in-progress timing state was preserved server-side but never shown, runs were immutable after creation, the `assigned_to` column was unused, no run-level pause/resume existed, and the console had no keyboard shortcuts or sticky controls. Writing the concurrency test the audit flagged as missing also surfaced a genuine, previously-undiscovered race condition.

**Decisions:**
- **Console context**: added `GET /test-run-cases/{id}/context` returning run/project/case identity in one call (run name, project name, test case title, priority, version number, assignee), fetched alongside the existing steps query rather than folded into it, since the steps endpoint's shape is already relied on elsewhere and a stable, narrow context endpoint is easier to reason about than overloading it.
- **Live timer**: purely a frontend fix — `ExecutionStepOut.opened_at` was already returned by the API; the console simply never rendered an elapsed-time readout for the in-progress step. A `LiveElapsed` component now computes elapsed seconds from the server's `opened_at` and ticks every second, so a browser refresh correctly resumes showing accurate elapsed time rather than nothing.
- **Run editing / add-remove cases**: `PATCH /test-runs/{id}` is blocked once any run case has `started_at` set, matching the spec's own "before execution" qualifier precisely (not an arbitrary stricter or looser rule). Adding cases reuses the same approved-only/same-project validation as initial run creation (refactored into a shared `_validate_bundlable_cases`/`_bundle_case_into_run` pair). Removing a case is blocked if any of its steps have `opened_at` set, to avoid silently discarding recorded execution state — a case can be removed cleanly only if nothing has touched it yet.
- **Assignment**: `PATCH /test-run-cases/{id}/assign` validates the assignee belongs to the tenant (not necessarily the project — consistent with how `test_cases.assignee_id` is validated elsewhere) and is gated by `testrun.create` (the same authority tier that can create/edit runs), not a new permission.
- **Pause/resume**: scoped deliberately narrow, per the spec's own "where supported" qualifier. `test_runs.paused_at` (migration `b6c7d8e9f0a1`); `open_step`/`record_verdict` both reject with 409 while paused. Gated by `testrun.finish` (Admin/Manager only) rather than `testrun.create` (which Testers also hold) — pausing affects every participant on a run, not just the actor, so it's treated as the same tier of authority as finishing one. An explicit run-level "start execution" action was **not** added: the existing implicit-start-on-first-step-open semantics already work correctly and weren't independently identified as a gap worth inventing a new state transition for.
- **Keyboard shortcuts + sticky controls**: P/F/I keys act on the current step (disabled while the defect dialog is open, to avoid keystrokes leaking into its text inputs, or while the run is locked); the action buttons moved from inline-per-card to a `fixed` bottom bar showing the current step's action text, visible regardless of scroll position.
- **Concurrency bug found and fixed, not just documented**: `_recompute_run_case_status` (ADR-024) re-reads every step's verdict and overwrites `test_run_cases.status` from scratch on each call, with no locking. The new concurrency test — three verdicts submitted concurrently for three different steps of the same run case — exposed a real race: each transaction could read the verdicts list before the others' commits, and whichever committed last would overwrite the correct final status with one computed from its own stale read (observed directly: `passed_count` correctly showed 3, but `status` incorrectly stayed `in_progress`). Fixed with a `SELECT ... FOR UPDATE` lock on the run case before recomputing, serializing concurrent verdict submissions for the same case — the identical pattern already used for the MFA attempt-count race (GAP-17). This is a genuine correctness fix, not a test-environment artifact: confirmed by the test failing before the fix and passing after, run repeatedly.

## ADR-037: Defect Management hardening — visible Fail-time prepopulation, link-to-existing, evidence fields, history, traceability deep links, reporter/date filters, explicit close confirmation
**Status:** Decided — found during an audit against the original Defect Management build prompt

An audit against the original Defect Management/traceability spec found the lifecycle state machine, version pinning, and standalone/step-level creation all correctly implemented, but the Fail-time dialog showed nothing visually to the user (ids only), "link to existing defect" was backend-only with zero UI exposure, three named fields (Actual/Expected Result, Environment) didn't exist, there was no history/timeline, the defect detail page had no execution evidence or step-level navigation, filters were missing a reporter and date-range dimension, "closing requires verification confirmation" was satisfied only by the Verified status existing earlier in the sequence (no distinct gesture), and reverse navigation (test artifact → its defects) only existed at the step level inside the Execution Console.

**Decisions:**
- **Visible Fail-time prepopulation**: `ExecutionConsole.tsx` now builds a `FailedStepContext` (project/run/test-case names already available from the console's own context query, plus the failing step's number/action/expected) and passes it into the dialog, which renders a summary panel and an editable title input defaulting to the same auto-suggested string the backend already computed — the backend default is kept as a fallback (still applied if the client sends no title), but the user can now see and change it before submitting.
- **Link to existing defect**: the dialog gained a "Create New"/"Link Existing Defect" toggle; the existing mode lists open defects in the project (reusing `GET /defects?project_id=`) and calls the pre-existing `POST /defects/{id}/links` endpoint rather than adding a new one. The harder part was making a linked defect still show the 🐞 badge on the originating run: `list_defects(test_run_id=...)` was broadened with an `OR` against a `defect_links` subquery (defects linked to any execution_step belonging to that run), and the frontend now checks both `test_case_version_step_id` matches (direct creation) and `links[].linkable_id` matches (linked-in) when deciding whether a step already "has a defect."
- **Actual Result / Expected Result / Environment**: added as plain nullable columns (migration `c7d8e9f0a1b2`). `expected_result` defaults from the originating version-step's own `expected` text when the defect is created from a failed step and the field isn't explicitly overridden — the common case needs no retyping, but an unusual defect (e.g. the expected behavior itself was ambiguous) can still override it.
- **History**: no new table — `get_defect_history` filters the existing hash-chained `audit_logs` table by `entity_type='defect'`/`entity_id`, since every defect mutation already goes through `record_audit_event`. This mirrors the same "reuse audit_logs rather than add a parallel history table" decision already made for audit trails elsewhere in this system.
- **Execution evidence & deep traceability**: `DefectOut` now resolves the originating `execution_steps` row (verdict/timestamps/duration/executed-by) by joining `test_run_id`+`test_case_id`+`test_case_version_step_id` back through `test_run_cases` — these three together uniquely pin the row even though `execution_steps` has no direct FK back to `defects`. Also exposes `test_case_version_number` and `test_run_case_id`, letting the detail page link directly into the Execution Console at the exact failed step rather than only naming it as text.
- **Reporter/date filters**: no assignee column exists on defects (confirmed, not an oversight — only `reported_by`), so per the spec's own "where supported" qualifier, only a `reported_by` filter was added, alongside `created_from`/`created_to` date-range filters.
- **Explicit close confirmation**: `DefectStatusUpdateRequest` gained `verification_confirmed: bool`, required (422) when the target status is `Closed` — a deliberate, distinct gesture beyond the existing Admin/Manager role gate and beyond the mere existence of `Verified` earlier in the sequence. Frontend: a checkbox rendered only for the Closed transition, gating the same "Advance to" button rather than inventing a separate confirm dialog.
- **Reverse navigation**: added a `test_case_id` filter to `GET /defects` and a "Linked Defects" card to both `TestCaseDetail.tsx` and `TestRunDetail.tsx`.

Testing note: the existing `journey4-defect-lifecycle.spec.ts` E2E test needed a one-line update (check the new confirmation checkbox before clicking "Advance to Closed") since the Closed transition's behavior genuinely changed, not because of an unrelated refactor.

## ADR-038: Dashboard and Reporting hardening — report filters, execution trends, pie/line charts, missing KPIs, compliance detail/print view, assignee disclosure
**Status:** Decided — found during an audit against the original Dashboard and Enterprise Reporting build prompt

An audit against the original Dashboard and Enterprise Reporting spec found the core aggregation logic (tenant/role scoping, no duplicate counting) correct, but seven named items missing or incomplete: no report filters existed at all on `/reports/aggregate`; no PDF and no print view existed — not even the browser-print-to-PDF fallback ADR-027 itself had promised; no Pie/Donut or Line chart existed and Execution Trends had no backing data; Active Projects, Approved Test Cases (count), Critical Defects, and per-domain Pass % were missing or buried in status-breakdown text instead of being explicit KPIs; the CSV compliance export lacked a Reporting Period header and had aggregate-only tables with no per-test-case/per-defect detail; "Assignee" grouping's per-metric meaning (set by ADR-027) was undisclosed in the UI; and the compliance export's numeric accuracy was untested against a known dataset.

**Decisions:**
- **"Active" project count**: defined as any project whose status is not `Completed` — the only status in the fixed BRD status set (`On Track`/`At Risk`/`Delayed`/`Completed`) that represents finished work, so this needed no new column or enum, only a `status != "Completed"` count over the data `get_dashboard_summary` already fetches.
- **Report filters compose via a filtered-subquery pattern, not per-metric bespoke WHERE clauses**: `get_aggregate_report`'s five metric branches each build structurally different base queries (different joins, different "value" columns). Rather than duplicating filter logic five times, every branch's base `select()` additionally labels `project_id`/`domain` (always present via the `Project` join), `tc_priority`/`tc_status` (`TestCase.priority`/`.status`, via an `outerjoin` for the two defect metrics since `Defect.test_case_id` is nullable), and a per-metric `created_at`. `project_id`/`domain` filter directly on the base select; the remaining four filters (`assignee_id`, `date_from`/`date_to`, `priority`, `status`) apply on a `.subquery()` wrapping it, before the final `GROUP BY`. A standalone defect (no `test_case_id`) is naturally excluded by a `priority`/`status` filter rather than erroring or being wrongly included, since the `outerjoin` leaves `tc_priority`/`tc_status` `NULL` for it.
- **New `test_case_status` metric, kept distinct from `run_status`**: the existing `run_status` metric (per ADR-027 decision #2) aggregates `test_run_cases.status` (`Passed`/`Failed`/`Pending`/`Blocked`), a different lifecycle from `test_cases.status` (`draft`/`ready_for_review`/`approved`/`deprecated`, ADR-001). Rather than overload `run_status` or relabel it, a genuinely new metric was added so both lifecycles remain independently reportable.
- **Execution Trends**: new `get_execution_trend` groups `ExecutionStep` verdicts by `func.date(closed_at)` over a trailing window (`func.make_interval` for the Postgres-native rolling cutoff), respecting the same tenant/role/project scoping as every other reporting query. Rendered as a `recharts` `LineChart` — the first line chart in the system — since a day-bucketed trend is the one reporting shape bar/pie can't represent well.
- **Print/PDF view finally completes ADR-027's deferred fallback**: ADR-027 decision #4 explicitly deferred "PDF is produced by the browser's native print-to-PDF against a print stylesheet, built when the Reporting screen's UI is implemented" — that promise was never kept until this pass. Rather than add a server-side PDF library (which ADR-027 explicitly rejected and this pass does not revisit), `get_compliance_report`/`compliance_report_to_csv` were split so the same structured report data backs both the existing CSV export and a new `GET /reports/compliance-detail` JSON endpoint; a new `/reporting/print` route (outside `AppShell`, so it renders full-bleed with no sidebar) consumes the JSON endpoint and renders tenant name/generation timestamp/reporting officer/reporting period/summary/detailed tables with `@media print` high-contrast styling and a `window.print()` button.
- **Assignee disclosure is a frontend-only fix**: the underlying per-metric "Assignee" semantics were already decided correctly in ADR-027 (test case's `assignee_id` for test-case/run metrics, `reported_by` for defect metrics) — only the UI never told the user which one applied. `Reporting.tsx` shows a one-line hint under the Group By control whenever "By Assignee" is selected, naming the exact dimension for the currently-selected metric; no backend change was needed.
- **No new migration**: every field added this pass (`active`, `approved_count`, `critical_count`, `pass_percentage`, execution-trend points, compliance detail rows) is computed at query time from existing columns — the first hardening pass in this project that needed none.

Testing note: 9 new tests were added to `test_reporting.py` covering active/approved/critical counts, per-domain pass percentage, the `test_case_status` metric, all 6 new aggregate filters, the execution-trend endpoint, and compliance detail/CSV numeric accuracy against the existing `_full_scenario` fixture — directly closing the audit's "compliance export's numeric accuracy untested" finding. All 8 pre-existing reporting tests needed zero changes, confirming the schema/service changes are additive, not breaking.

## ADR-039: System Administration and Audit Management hardening — audit detail/export/filters, self-service account history, reactivate control
**Status:** Decided — found during an audit against the original System Administration and Audit Management build prompt

An audit against the original spec found user CRUD, last-Admin protection, password reset with session revocation, all 11 named audit-engine recording sites, the audit record's 10-field shape at the DB/model level, DB-level `REVOKE` hardening, the SHA-256 hash chain, and the verify-chain endpoint all solidly implemented and matching prior ADRs (ADR-006, ADR-016, ADR-029). Six gaps remained: the `AuditLogOut` API response omitted `metadata` and `prev_hash` entirely, so an admin could never see what an entry actually recorded; there was no row-level detail/expand view; `/audit-logs` had no `entity_id` or date-range filter, and the backend's existing `user_id` filter wasn't exposed in the UI; there was no audit-log-specific export (only a derived compliance-summary CSV existed); users had no way to see their own account's history; and the Users & Roles screen had no control to reactivate a deactivated user, even though the backend already supported it via the same `PATCH` endpoint.

**Decisions:**
- **Return the full audit record, not a projection of it**: `AuditLogOut` already matched the BRD's 10-field shape at the DB/model level (ADR-006) — the gap was purely that the API response schema omitted `tenant_id`/`metadata`/`prev_hash`. Since "do not expose sensitive information in audit metadata" is already enforced at write time (`record_audit_event` call sites never pass passwords/tokens/hashes into `metadata`, confirmed by audit), there was no reason to keep metadata out of the read response — withholding it only hid legitimate investigative detail from the one UI surface built to show it. All three fields were added to the schema and to `audit_service._to_out`.
- **Audit-log filters compose the same way the aggregate-report filters do (ADR-038 precedent)**: `entity_id` and `date_from`/`date_to` were added alongside the existing `action`/`entity_type`/`user_id` params on `list_audit_logs`, factored into a shared `_build_filtered_query` helper reused by both the paginated list and the new CSV export, so the two surfaces can never drift out of sync on what "the same filters" means.
- **Export is a separate, uncapped-by-pagination endpoint, not a param on the list endpoint**: `GET /audit-logs/export` reuses the same filters and the same `audit.view` permission, but is deliberately not limited by `MAX_PAGE_SIZE` (capped instead at `EXPORT_ROW_CAP = 50_000` as a sanity ceiling) — a compliance export is a full-dataset dump for archival/review, not a UI page.
- **Self-service history needs no new permission, only a narrower query**: `GET /users/me/history` uses `get_current_context` (any authenticated session), not `require_permission("audit.view")`, because its query is hard-scoped to `entity_type="user", entity_id=ctx.user_id` — the caller can only ever see events recorded against their own account, which is strictly narrower than what `audit.view` already grants an Admin. This reuses the exact same `AuditLog` rows rather than a parallel table, consistent with how defect/entity history already works elsewhere in this system.
- **Self-service history legitimately includes the user's own login/MFA events, not just profile/role/password changes**: `auth_service` already records `auth.login_attempted`/`auth.mfa_verified`/`auth.logout` with `entity_type="user", entity_id=<the authenticating user>`. Rather than filter those out to keep the feature narrowly scoped to "account edits," they were kept — a personal activity history that excludes a user's own logins would be a strange, incomplete answer to "what happened to my account."
- **Reactivate is a one-line frontend addition, not a backend change**: `UserUpdateRequest.is_active` already accepted `true`, and `update_user`'s last-Admin guard only fires on demotion/deactivation, never on reactivation — so `UsersRoles.tsx` only needed a visible "Activate" button wired to the same `updateUser(id, {is_active: true})` call the role/deactivate controls already use.

Testing note: 6 new tests were added to `test_audit_api.py` (metadata/prev_hash in the response, entity_id + date-range filtering, CSV export contents, Tester forbidden from export, and self-service history scoping) plus one to `test_auth_flow.py` (reactivation via `PATCH .../is_active: true`, appended to the existing last-Admin-guard test). All pre-existing audit/auth tests needed zero changes. Live-verified against the real tenant, including an actual deactivate→reactivate cycle via the UI.

## ADR-040: Idempotency-Key dedup and project optimistic-concurrency version, as opt-in fixes for GAP-66/67/68
**Status:** Decided — a targeted fix pass against three findings from the QA engagement's security/reliability testing

The QA engagement (`Security_Test_Report.md`, `E2E_Test_Report.md`) found and deliberately left undecided three real gaps: file uploads were validated by extension only (no content-sniffing), no create endpoint had duplicate-submission protection, and a concurrent same-field `PATCH /projects/{id}` was a silent lost update. A follow-up request asked for GAP-66/67/68 specifically fixed (GAP-69, the performance findings, was left for separate investigation since it needs root-causing, not a code fix).

**Decisions:**
- **Content-sniffing is signature-based, not a new dependency.** Rather than add `python-magic` (a new runtime dependency with a system `libmagic` requirement that complicates the Docker image), `attachment_service.py` checks the first bytes of the upload against a small hardcoded table of real magic-byte signatures for every binary type already in the allowlist (PNG/JPEG/GIF/BMP/PDF/legacy-OLE .doc+.xls/ZIP-based .docx+.xlsx/WEBP), and a "looks like text" check (no NUL bytes, valid UTF-8) for .csv/.txt/.log, which have no fixed binary signature. This closes the specific attack the QA pass demonstrated (an ELF+shell-script payload disguised as `.txt`) without adding deployment complexity.
- **Idempotency is opt-in via a header, not a default dedup window.** A client-supplied `Idempotency-Key` header, checked against a new per-tenant-per-user-per-operation `idempotency_keys` table (`app/core/idempotency.py::with_idempotency`), returns the original entity on a repeat request with the same key. Omitting the header preserves the exact prior behavior (always creates a new record) — this was a deliberate choice to avoid silently changing the behavior of every existing caller that doesn't yet send the header (e.g. the frontend doesn't send one today; a future pass could add it to `apiFetch`'s POST calls for a true always-on guarantee). Applied to the three create endpoints the QA pass's finding named as likely affected by the same pattern: `POST /defects`, `POST /projects`, `POST /projects/{id}/test-cases`.
- **Idempotency-key recording needed a tenant-context re-assertion.** `create()` (the wrapped service call) commits its own transaction; since `app.current_tenant` (ADR-007's RLS GUC) is transaction-local, it resets after that commit, and the subsequent `INSERT INTO idempotency_keys` would otherwise run with no tenant context and fail its RLS `WITH CHECK` clause. `with_idempotency` re-asserts `set_tenant_context` before that insert.
- **Project optimistic concurrency is opt-in via `expected_version`, not a mandatory version on every PATCH.** `ProjectOut.version` (new integer column, incremented on every update) is always returned so a client *can* track it; `ProjectUpdateRequest.expected_version` is optional — a PATCH without it keeps the exact prior last-write-wins behavior. Supplying it makes a stale write a 409 instead of a silent loss. This is the standard optimistic-concurrency (ETag-like) pattern rather than mandatory pessimistic locking on every PATCH, since forcing every caller to track and send a version would be a breaking API change for a problem that (per the QA finding) only matters under genuine contention.
- **The `expected_version` check needed a row lock to actually be race-safe, not just a plain SELECT-then-compare.** A naive "read the project, compare `expected_version` to its `version` attribute, then update" is itself racy — two concurrent requests can both read `version=1` before either commits, both pass the check, and both overwrite (the exact bug being fixed, just moved one level up). `_get_project_or_404` gained a `for_update: bool = False` parameter; `update_project` passes `for_update=True`, taking a `SELECT...FOR UPDATE` row lock so a concurrent second request blocks until the first commits, then re-reads the now-current `version` under that lock and correctly 409s if it no longer matches. This mirrors the same `SELECT...FOR UPDATE` pattern already used for the two previously-fixed races (GAP-17 MFA attempt-count, GAP-49 run-case rollup) — the first time this codebase has applied it to a plain field edit rather than a recomputed aggregate.
- **A rollback-then-reference-the-expired-object bug was found and fixed while building the fix.** The 409 error path originally called `db.rollback()` (to release the row lock / discard the no-op transaction) and then referenced `project.version` again inside the exception message's f-string — but `db.rollback()` expires every object in the session, and SQLAlchemy's lazy-reload of that expired attribute ran in a now-tenant-context-less transaction, failing RLS and raising a confusing `ObjectDeletedError` instead of the intended 409. Fixed by capturing `current_version = project.version` into a local variable before the rollback.
- **Scoped to `projects` only, not generalized to every resource.** The QA finding was specifically demonstrated and tested against `projects`; the same `version`+`expected_version`+`for_update` pattern is not assumed to apply to test cases, defects, or other mutable resources without separately confirming the same lost-update class exists there (GAP-68's "Open" follow-up note).

Testing note: `test_reliability.py`'s three GAP-66/67/68 tests were updated in place to demonstrate the fix (the previously-documented "FINDING" tests now show both the fix working with the new opt-in mechanism, and the legacy no-header/no-version behavior preserved unchanged for backward compatibility) rather than duplicated into new files. `test_security_hardening.py`'s file-upload test was similarly updated from "documents the gap" to "confirms the fix," plus two new assertions (a genuine file with a matching extension is still accepted; the same bytes under a mismatched extension are rejected). Full regression: 225/225 backend tests passing (one pre-existing, confirmed-flaky-under-full-suite-load hash-chain-ordering test, unrelated to this fix, passes cleanly in isolation — same category as the already-documented CSV-import timing flake). `ruff`/`mypy` clean. Frontend unaffected (no UI surfaces the new header/field yet) — `typecheck`/`lint` confirmed clean, same pre-existing benign warnings.

## ADR-012 addendum: test case attachments implemented (GAP-15 closed)
The schema and storage design below were decided in Phase 0 but not built until a post-Phase-10 pass. Implementation matches the decision as written: `app/services/attachment_service.py` writes bytes to `{attachments_dir}/{tenant_id}/{test_case_id}/{uuid}_{filename}` (capped at 10MB, rejecting empty uploads), computes a SHA-256 checksum, and stores only metadata in `attachments`. Scoped to `owner_type='test_case'` only for this pass, though the table's polymorphic design (`test_case_version`/`defect`/`execution_step` are also valid owner types) was left unchanged for future reuse.
