# QTestHub — Database Migration Guide

Written for: whoever is running a schema migration against a real
deployment. Uses Alembic, the same tool used throughout development — there
is no separate "production migration tool."

## 1. Generating a migration

From `backend/`, with a local dev database running and up to date:
```bash
alembic revision --autogenerate -m "short description of the change"
```
Autogeneration compares the current models to the database schema and drafts
a migration — it is a draft, not a guarantee. Always review it (step 2)
before trusting it.

## 2. Reviewing a migration before applying it

Open the generated file under `backend/alembic/versions/` and check, in
order:
1. **Does `upgrade()` match the intended change?** Autogenerate sometimes
   misses things it can't infer (renamed columns show as a drop+add, which
   loses data unless you hand-edit it to an `op.alter_column` rename).
2. **Is a backfill needed?** A new `NOT NULL` column on a table with existing
   rows needs a default or an explicit backfill step before the constraint is
   added, or the migration fails outright against real data. This project's
   own history has several examples (e.g. the `Environment`/`Build`/`Release`
   migration in Tier 2, which matched existing free-text defect-environment
   values into new lookup rows rather than dropping the data) — follow that
   pattern for any future enum-to-table promotion.
3. **Is `downgrade()` safe, or at least honestly destructive?** See §4.
4. **Does it touch a tenant-scoped table?** Confirm `TenantScopedMixin` and
   the matching RLS policy are present for any genuinely new table — a new
   table without RLS is invisible to this project's entire tenant-isolation
   test suite until that's fixed, and a real cross-tenant leak until then.

## 3. Applying a migration

**In development**: migrations run automatically as part of
`docker compose up` (the `api` container's entrypoint runs
`alembic upgrade head` before starting `uvicorn`).

**In production**: the same thing happens automatically on `api` container
start (`docker-compose.prod.yml`/`backend/Dockerfile`'s `CMD`) — there is no
separate manual migration step for a normal deploy. For a deploy you want to
control more explicitly (e.g. running the migration before cutting traffic
over to new application code), run it standalone first:
```bash
docker compose -f docker-compose.prod.yml run --rm api alembic upgrade head
```
**Always back up first** (`docs/deployment/BACKUP_AND_RESTORE.md`) — no
migration here, autogenerated or hand-written, is exempt from that rule.

## 4. Rollback — and its real limitations

```bash
docker compose -f docker-compose.prod.yml run --rm api alembic downgrade -1
```
`downgrade()` is only as safe as what the migration author wrote for it.
Concretely:
- A migration that only **adds** a column/table has a safe, lossless
  downgrade (drop what was added).
- A migration that **drops** a column, **renames** something, or
  **backfills data into a new shape** (the enum-to-lookup-table pattern
  above) has a downgrade that is itself destructive or lossy — it can put the
  schema back, but data written after the upgrade, in the new shape, is
  generally not recoverable by the downgrade alone. **Read the specific
  migration's `downgrade()` before relying on it** — do not assume Alembic
  makes rollback universally safe just because the command exists.
- The only fully reliable rollback for a destructive migration is restoring
  the pre-migration backup (§3's "always back up first" is not boilerplate).

## 5. Production migration checklist

- [ ] A recent backup exists and has been verified restorable
      (`deployment/scripts/verify_backup.sh`).
- [ ] The migration has been reviewed per §2, including its `downgrade()`.
- [ ] If the migration backfills data, it has been tested against a
      realistic (non-empty, non-trivial) copy of the schema first, not just
      an empty test database.
- [ ] A maintenance window or low-traffic period is used if the migration
      takes an exclusive lock on a large table (e.g. adding a `NOT NULL`
      column with a backfill on a large existing table can lock writes for
      the backfill's duration — size this against your actual row counts).
- [ ] `alembic upgrade head` is run and its output confirmed clean
      (`docker compose -f docker-compose.prod.yml logs api | grep -i alembic`).
- [ ] `GET /api/v1/ready` returns 200 after the migration.
- [ ] The application's own test suite covering the changed area still
      passes against the new schema (re-run `pytest` in a staging
      environment pointed at a copy of production data where that's
      feasible, before touching the real thing).
